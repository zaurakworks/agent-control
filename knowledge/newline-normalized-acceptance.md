# K6：跨端文件一致性验收必须先规范化换行

> 状态：正式当前公共知识。
> 最近核验：2026-08-11。
> 适用对象：本机 Windows 环境下版本化来源与各运行端安装副本（入口文本、Skill 等文本文件）的一致性验收。
> 环境：Windows 11；Git 换行策略与各工具写盘策略混合，导致 CRLF/LF 并存。
> 版本边界：与单一产品版本无关，属本机文件生态事实。

## 回答的问题与价值门

能否用原始字节哈希验收「安装副本与版本化来源一致」？

三端 Skill 安装验收与入口同步验收每批都要做；混合换行符已实际让字节哈希成为无效一致性信号，本结论在每次验收时复用，并解释 entry_sync 采用规范化比对的设计，通过价值门。

## 可直接复用的结论

不能直接用原始字节哈希：本机安装副本与仓库来源之间存在 CRLF/LF 差异，内容相同的文件字节哈希不同，会把「一致」误判为「不一致」。正确做法是先规范化换行再比对：把 CRLF 规范化为 LF 后取 SHA-256（或使用 `python -B -m scripts.entry_sync check` 的规范化比对）；规范化后仍不同，才是真实内容差异。已验证实例：三端 Skill 安装验收按「LF 规范化后 SHA-256」核验运行端实际加载副本与来源一致（issue-workflow/SKILL.md 三端与来源同为 `8c318cf9e732…`）。

## 第一方来源

- PR Eridanus117/agent-control[#47](https://github.com/Eridanus117/agent-control/issues/47) 正文：「Mixed CRLF/LF in installed copies also made byte hashes an invalid consistency signal」，及据此实现的规范化比对；
- agent-control[#44](https://github.com/Eridanus117/agent-control/issues/44)「Skill 维护批次二交付」评论（2026-08-11）：三端 LF 规范化 SHA-256 核验记录；
- `scripts/entry_sync/core.py` 与 `tests/test_entry_sync.py` 中的换行规范化比对实现与用例。

## 例外、未知和不能推出的结论

- 规范化只消除换行差异；BOM、行尾空白或字符编码差异不在已核验范围，遇到时需另行判断。
- 不能推出「哈希验收总是错误」——两端换行策略一致且有保证时，原始哈希仍可用；本结论只约束本机混合换行生态。
- 对换行本身敏感的文件（二进制、以换行为语义的数据文件）不适用规范化比对，规范化会掩盖真实差异。

## 失效条件

1. 所有写盘端统一换行策略并有强制保证；
2. 验收对象扩展到对换行敏感的文件类型。

## 下次最少复核步骤

任取一份安装副本与其版本化来源：分别计算原始 SHA-256 与 LF 规范化后 SHA-256。原始不同而规范化后相同，结论仍成立；原始已一致，则检查换行策略是否已统一（触发失效条件 1）。
