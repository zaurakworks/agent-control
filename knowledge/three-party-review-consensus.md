# K18：三方审阅只替代已授权决定，且必须三席一致后落地

> 状态：正式当前公共知识。
> 最近核验：2026-08-12。
> 适用对象：负责人已经明确授予替代决定权，且待决定事项落在已批合同内低风险、可逆实施取舍或承载位置的 Agent 系统任务。
> 对象与环境：Windows 11；Orca 1.4.180；GitHub.com；`orchestrated-collaboration` 0.2.2 所含 CF-6 0.2.0；agent-plugins 当前提交 `3baccec0d83115bb3123382b34fb0ec944512741`。
> 证据上限：P0-1 与 P0-3 两个真实自然样本均完成“发现缺陷 → 修复 → 三席复核一致 → 落地”；这支持“两个自然样本有效”，不支持产品采用、长期依赖、长期错误率下降或负责人注意力收益已经成立。

## 回答的问题与价值门

什么情况下值得启动三方审阅，它与常规交付验收的预授权谓词怎样分界；启动后，怎样保证三张票来自正确而互异的运行身份、没有被公开顺序锚定，并且只有三席一致时才消费决定？

三方审阅成本高，且会代替一次原本需要负责人批准的决定；误触发会增加协调税，误消费则会改变长期资产。今夜两个自然样本又证明它能挡住起草席与协调者都漏掉的真实缺陷。该边界和执行顺序会在以后每次替代决定中复用，因此通过价值门。

## 先分流：决定机制与常规交付验收不是同一件事

### 1. 只有“本来需要负责人决定”的事项才可能进入 CF-6

CF-6 是**决定机制**，不是通用质量检查。进入前必须同时满足：

1. 负责人已经对这类事项给出明确替代授权，并人工点名使用三方审阅；
2. 决定包已冻结决定 ID、目标 Issue、revision、选项、推荐、最强反方、翻转条件、授权类别和包哈希；正文变化即换 revision 与哈希；
3. 事项只属于已批合同内低风险、可逆的实施取舍或承载位置，即 CF-6 的 C3=A 边界；
4. 起草／实施者回避计票，三席身份、密封与机械映射均可核验。

产品采用、长期依赖、父目标满足、根诉求状态、授权变化、不可逆动作、真实支出以及 CF-6 本身的规则变化仍由负责人决定。三张一致票不能自行创造替代授权，也不能把负责人专属类改写成 C3=A。

### 2. 常规交付验收按当前合同证据判断，不启动 CF-6

普通交付、实验或摩擦类 Issue 的成功条件已经写在当前合同时，验收是在判断**既定谓词是否有证据成立**，不是在替负责人选择新方向。直接交付路径要求：

1. 每条成功条件都有远端可核验证据，悬置项也明确列出；
2. 未消费的负责人动作、开放子项和被依赖事项没有被静默当成已完成；
3. 验收只判断现有合同，不据此选择新的目标、产品取舍或授权边界。

三项都成立时，持有合同的 Session 可以报告逐条验收证据；关闭、合并、安装、删除、宿主环境变化或其他生命周期动作仍需当前合同或负责人明确授权。任一项不成立，或边界拿不准，就回到负责人决定路径。

可复用的分界句是：**“证据是否满足已经批准的成功条件”属于常规验收；“应当选择哪个会改变产品、授权或长期边界的方向”属于决定。** 前者不因多找两个评审席就升级为 CF-6，后者也不能借“验收”名义绕过负责人或替代授权门。

## 机制要点：联合身份、密封、机械映射与一致消费

### 1. 三席联合类型保留各自真实生命周期身份

协调者和受派评审不是同一种运行对象，不能强迫三席都填写 Task／Dispatch，也不能把 terminal 当作持久身份。机械映射使用带 `seat_kind` 的联合类型：

| 对象 | 联合身份 | 角色说明 | 不能替代 |
| --- | --- | --- | --- |
| 协调者席 | `run_id + consumer_generation + observed_terminal_handle` | 稳定键是 Run 与消费代次，terminal 只作落点交叉核验；协调者占席前必须回避且先密封 | terminal 不能单独证明当前协调消费者 |
| 受派评审席 | `task_id + dispatch_id + observed_terminal_handle` | Task 定义工作，Dispatch 定义本次尝试，terminal 交叉核验实际落点 | Task 或 terminal 都不能单独证明本次评审尝试 |
| GitHub 判定 | `decision_id + role_id + comment_url` | 连接公开判定、目标 Issue、可信作者和编辑水位 | 同一账号的三条评论不能证明三个独立 Session |

三席分别承担 R1“授权与边界”、R2“执行与身份”、R3“ROI 与维持现状”，都审同一个完整决定包。默认三席来自独立 Dispatch；协调者若占一席，必须在读取其他评审 Delivery 前先密封自己的完整判定，否则只能主持、不计票。三席至少一席使用异族模型，且起草／实施者不计票。

### 2. 先密封后揭示，避免先票锚定

顺序固定为：

```text
冻结决定包与哈希
→ 三席分别提交完整判定并取得密封消息 ID／哈希
→ 三封齐且身份预检通过
→ 原封公开三席判定
→ 比较公开载荷与密封哈希
→ 对 Run、Dispatch、评论做两轮机械回读
→ 三席全部认可且授权类别合规，才可消费决定
```

评审席通过自身 Dispatch 的 `ask` 密封“判定＋理由＋反方回应＋翻转条件”；公开前不把任何一票写入目标 Issue，也不向其他席转述。密封提供程序性的顺序隔离和可回查哈希，不是密码学保密，也不能隔离拥有本机高权限的恶意观察者。

### 3. 映射按稳定键生成，三席一致才落地

验证器从 Orca `run-show`／`worker-show` 与 GitHub 评论 API 两轮只读取证，以 `decision_id + role_id + stable_runtime_key` 连接并规范排序，直接生成 JSON 与 Markdown 映射；不得按数组顺序、评论时间或人工记忆换序抄写。

以下任一情况都使本轮只保留为审阅证据：身份或 terminal 重复、角色或 URL 错配、起草／实施者入席、缺异族模型席、代际过期、两轮来源变化、公开载荷与密封哈希不一致、否决、存疑、授权类别越界，或工具／远端状态未知。只有三票认可、身份与密封硬门全部通过且事项确属 C3=A，协调者才可消费决定；首轮被否决后修订正文，必须形成新的 revision／哈希并重新完成一致复核，不能在原轮手抄修补。

## 两个自然样本给出的真实教训

### P0-1：结构成立不等于逐条核验了“忠实实现”

在[关联 #139（P0-1 迭代回执地基）首轮否决](https://github.com/Eridanus117/agent-control/issues/139#issuecomment-5262113488)中，协调者席先判断方案“忠实于[关联 #135（自我迭代优化循环设计）](https://github.com/Eridanus117/agent-control/issues/131#issuecomment-5261868325)的十字段”，但实际只确认了承载结构、控制器边界、测试和预算，没有把被断言的十字段逐项与来源协议比较。独立评审席逐字段核验后发现：来源为 `trigger/object/finding/route/authority/validation/landing/acceptance/recheck/roi`，实现却重定义字段、折叠 `validation` 与 `roi`，又新增未获授权的概念；符合性测试只固定了改写后的清单，不能证明忠实性。

协调者随后复核并确认否决成立；修订恢复原十字段和独立的 `validation`／`roi`，原否决席与另一独立席再次核验后，三席才一致落地。这里被证伪的不是整体结构，而是一个未经逐条验证却被写成事实的“忠实”断言。

### P0-3：有通用门不等于具体故障路径已经闭合

在[关联 #140（P0-3 类型化派发与写后核验门）首轮否决](https://github.com/Eridanus117/agent-control/issues/140#issuecomment-5262142536)中，协调者席和一名评审席都认为通用的放置合同与写后回读能够处理 Issue 标题错配。否决席沿具体故障路径证明：合同没有在建项前冻结期望 Issue 标题或等价语义标识，写后回读也没有把实际标题与独立期望值比较；因此编号、父级、五字段和一般回读可以全部通过，P0-3 仍可能被误写成 P0-1，而 [#140](https://github.com/Eridanus117/agent-control/issues/140) 当夜恰好发生过这一故障。

修订把期望标题／语义标识冻结进 `contractRepo`，创建后回读实际标题并独立断言，再用 `p03-title-mistransmitted-as-p01` 负向夹具证明“其他门全绿，标题门仍能拦下错配”。原否决席与另一独立席复核后，三席一致落地。

### 可迁移的检查法

两个否决都成立，并且都指向已经发生或会直接复现的真实故障；这说明三方审阅在当前边界不是橡皮图章。可迁移的做法是：

1. 把决定包里的每个事实断言拆成可观察主张；
2. 为每个主张写出直接证据动作，而不是用“结构存在”“已有测试”“有通用门”代替；
3. 声称“忠实于来源”时逐字段、逐约束比对来源；声称“直接修复事故”时沿事故路径走到目标后态，并设计“其他门全绿仍会失败”的负向夹具；
4. 若某席证明一条受支持主张为假，即使命题其他部分都成立，也按整轮未一致处理；修订后重新密封和复核。

## 两道准入门逐项判定

| 准入项 | 判定 | 依据 |
| --- | --- | --- |
| 价值门 | 通过 | 替代决定会重复需要触发边界与一致消费门；两个自然样本已挡住真实缺陷。 |
| 1. 明确回答的问题 | 通过 | 只回答三方审阅何时进入、如何执行、样本证明到哪一级。 |
| 2. 可直接使用的结论和必要解释 | 通过 | 给出决定／验收分流、联合身份表、密封流程、一致门和事实核验法。 |
| 3. 第一方来源或可重复验证过程 | 通过 | 现行 Skill、远端审计、两条否决—修订—复核链均可直接回读。 |
| 4. 对象、版本、环境和核验时间 | 通过 | 页首记录 Orca、GitHub、Plugin／CF-6 版本、提交和日期。 |
| 5. 例外、仍未知内容和不能推出的结论 | 通过 | 明确排除负责人专属类、产品采用、长期依赖、跨后端泛化和量化 ROI。 |
| 6. 明确的失效条件 | 通过 | 下节列出授权、身份语义、密封、样本反证、成本和普通验收谓词变化。 |
| 7. 下次最少复核步骤 | 通过 | 只需重读现行 CF-6／谓词、两条样本水位，并在下一自然样本保存同一证据链。 |
| 8. 人容易理解、Agent 足以复用的表达 | 通过 | 先分流，再给身份与状态机，最后用两个真实故障说明检查粒度。 |

## 例外、未知与不能推出的结论

- `verified=true` 只证明身份、映射、密封载荷和三票满足合同，不证明评审论证必然正确、选项完整或决定值得；本包的两个样本之所以有效，还依赖否决点后来被独立复核为真实故障。
- 三席一致不能产生授权。没有负责人明确替代授权，或事项属于负责人专属类时，普通路径仍是负责人直接决定。
- 常规 PR 审查、合同成功条件复核和满足三条件预授权谓词的生命周期回收不需要 CF-6；它们也不能借预授权谓词作产品取舍。
- 程序性密封只降低公开顺序锚定，不提供密码学保密或恶意管理员隔离。
- 两个样本不能证明长期错误率下降、假阳性率可接受、平均墙钟优于负责人直接决定，或负责人问询已经减少。
- 本包绑定 Orca 的 Run／consumer_generation、Task／Dispatch／terminal 和 `ask` 语义；其他后端必须先定义等价稳定身份与密封见证。

## 失效条件

出现以下任一情况时，受影响结论停止直接复用并先做最少复核：

1. 负责人改变替代授权、C3=A 边界、席位构成、回避规则或负责人专属类别；
2. Orca 改变 Run、consumer_generation、Task、Dispatch、terminal、`ask`、`run-show` 或 `worker-show` 的对象与恢复语义；
3. CF-6、验证器 schema、规范化哈希、两轮取证或密封—公开状态机发生变化；
4. [#139](https://github.com/Eridanus117/agent-control/issues/139) 或 [#140](https://github.com/Eridanus117/agent-control/issues/140) 的后续远端证据推翻“否决成立”“修订消解”“三席一致闭合”任一环；
5. 自然样本出现 `verified=true` 的错消费、身份仍可错绑、先票可见改变判断，或否决后来被证明确属假阳性；
6. 连续样本显示三方墙钟与负责人注意力成本高于直接决定，且没有减少问询、返工或故障外溢；
7. 本仓项目入口或当前合同改变常规验收与负责人专属决定的边界。

## 下次最少复核步骤

1. 读取当前安装版本与 agent-plugins 当前提交中的 CF-6；确认 C3=A、联合身份、先密封后公开、机械映射和“三席一致才消费”语义未变。
2. 读取本仓当前项目入口与目标 Issue 合同；确认“只判断既定成功条件”和“关闭／合并等动作仍需明确授权”的分界未变。
3. 回读 [#139](https://github.com/Eridanus117/agent-control/issues/139) 与 [#140](https://github.com/Eridanus117/agent-control/issues/140) 的首轮否决、协调者裁决、原否决席复核及三席一致回执；若出现后续反证，只重查被影响的结论。
4. 下一次已授权自然样本保存：冻结包与哈希、三席联合身份、三封、公开评论、规范映射、首轮判定、修订 revision、原否决点复核和最终消费回执；逐项确认被断言事实都有直接证据动作。
5. 至少再出现一轮自然样本或成本反例后，复核假阳性、墙钟、负责人问询和返工方向；没有新证据时不把两个样本外推为产品采用或长期依赖。

## 不适用范围

- 没有负责人替代授权的普通多人意见收集；
- 只需按既定合同证据验收并满足三条件预授权谓词的常规交付回收；
- 产品采用、长期依赖、父目标满足、根诉求状态、授权变化、不可逆动作、真实支出或 CF-6 规则变化；
- 自动投票、自动消费决定、自动合并或以评论数量代替论证质量；
- 尚未定义等价稳定身份、密封见证与公开回读的非 Orca 后端。
