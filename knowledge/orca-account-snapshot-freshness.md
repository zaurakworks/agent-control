# K13：Orca 账户快照必须以 updatedAt 前进判定新鲜度

> 状态：正式当前公共知识。
> 最近核验：2026-08-11。
> 适用对象：本机 `orca account list --json` 返回的 Codex 账户窗口与权益快照；需要比较两个时点或把账户变化与 Token 消耗配对的只读观测。
> 环境：Windows 11；Orca 1.4.177 packaged；`resource-observability 0.2.1`；America/New_York。
> 版本边界：结论来自两次预注册实验中的账户快照链；Orca 的账户采集、缓存、字段或时间戳语义变化时必须重新核验。

## 回答的问题与价值门

连续调用 `orca account list --json` 得到相同的周窗口百分比，能否说明账户真实值没有变化？怎样判定前后两个读数足够新鲜，可以用于额度趋势或 Token→账户窗口映射？

账户快照会反复用于模型、并发和实验投入判断；把缓存读数当成实时账户状态，会把测量失效误写成“没有消耗”或错误换算。因此本结论会被后续资源观测和实验重复使用，通过价值门。

## 可直接复用的结论

### 1. `updatedAt` 是快照新鲜度判据，命令调用时刻不是

`orca account list --json` 返回的是账户快照。顶层 `ok=true`、Provider `status=ok` 和一次新的命令调用，只能说明这次读取成功，不能证明服务端账户状态已经重新采集。

在[关联 #99（Token 周限映射低并发复测）收口卡](https://github.com/Eridanus117/agent-control/issues/99#issuecomment-5259308470)中，17:46:33–17:53:09 EDT 的 8 次探针全部返回 `updatedAt=17:40:37.283`；最后一次调用距快照时点约 12 分 33 秒。此前[关联 #67（Token 消耗到周限映射与刷新券语义实证）收口卡](https://github.com/Eridanus117/agent-control/issues/67#issuecomment-5257206600)记录的快照为 14:17:39.796，说明该字段会在后续采集周期前进，但不会因每次 CLI 调用而前进。

因此，把“约 15 分钟缓存”理解为当前样本给出的实用等待量级：快照已直接观察到至少可陈旧 12 分 33 秒，15 分钟可作一次有界观测的等待预算；它不是经验证的固定 TTL、刷新保证或精确周期。

### 2. 同一 `updatedAt` 下的重复值只能复述同一快照

两个样本的 `updatedAt` 相同，即使 `usedPercent`、`resetsAt` 或券字段也相同，只能得出“读取到同一份最后已知快照”，不能得出真实账户没有变化。报告这类读数时，应同时写明：

- 快照自己的 `updatedAt` 与实际采集时刻；
- Provider 状态、窗口长度和 `resetsAt`；
- 这是当前值、新鲜样本，还是带陈旧标志的最后已知值；
- 字段为 `null`、缺失或状态异常时保持未知，不写成零。

### 3. 跨时点比较要求时间戳严格前进，并确认窗口身份不变

需要把 A、B 两点用于账户趋势、券前后对照或 Token 消耗配对时，最小接纳门是：

```text
A、B 读取成功且 Provider 正常
→ B.updatedAt 严格晚于 A.updatedAt
→ windowMinutes 与 resetsAt 表明仍是同一账户窗口
→ 再计算账户字段差值
```

时间戳没有严格前进时，本轮账户差值不可解释；本地 Session Token 即使明显增加，也不能与陈旧账户百分比配成换算商。`updatedAt` 前进只解决快照新鲜度，仍不能排除同账户其他 Session、整数百分点量化、套餐分母和 Provider 归因等混杂因素。

## 第一方来源与证据映射

1. [关联 #99（Token 周限映射低并发复测）收口卡](https://github.com/Eridanus117/agent-control/issues/99#issuecomment-5259308470)：保存 8 次探针的采集时刻、同一 `updatedAt`、周窗口与券字段，并按预注册门判定 A/B 样本未成立；直接支持结论 1–3。
2. [关联 #67（Token 消耗到周限映射与刷新券语义实证）收口卡](https://github.com/Eridanus117/agent-control/issues/67#issuecomment-5257206600)：保存更早的 `updatedAt`、三次同快照读取、本地 Token 增量与测量失效判定；与 [#99](https://github.com/Eridanus117/agent-control/issues/99) 合看，支持“快照会在后续采集周期前进，但单次调用不保证刷新”。
3. [K9（Agent 资源的六个观测面不可互相代替）](./resource-observability-boundaries.md)：提供账户窗口、Session Token、时间戳和未知值的既有边界；本包只增补账户快照的新鲜度判定，不替代 K9。

## 例外、未知和不能推出的结论

- 当前证据没有测得缓存的精确 TTL、刷新事件、服务端采集周期或 CLI 是否能主动刷新；“约 15 分钟”不是协议保证。
- `updatedAt` 前进只证明获得了较新的快照，不证明变化由当前 Session 造成；同账户不可见活动与 Provider 归属仍未知。
- 相同 `updatedAt` 下字段相同不能证明真实值未变；字段不同而时间戳未变则应先视为协议异常，不直接解释账户变化。
- 本包不能把 Session Token 换算成周窗口百分点，也不能推出套餐总量、账单、券消费顺序或整数百分比的量化规则。
- [#99](https://github.com/Eridanus117/agent-control/issues/99) 的 8 次探针和 [#67](https://github.com/Eridanus117/agent-control/issues/67) 的 3 次采样是两个本机实验窗口，不足以给出长期刷新概率或服务等级。

## 失效条件

出现以下任一情况时，受影响结论停止直接复用：

1. Orca 改变 `account list` 的缓存层、采集方式或 `updatedAt` 定义；
2. 新版本为快照增加明确的新鲜度、缓存年龄或强制刷新字段，并与本包判据不同；
3. 只读复测显示每次调用都会取得严格前进的时间戳，或同一时间戳不再代表同一快照；
4. Provider 状态、账户窗口或权益字段不再与 `updatedAt` 共享同一快照边界；
5. 任务转到未核验的 Orca 版本、远程环境或其他账户 Provider。

## 下次最少复核步骤

1. 先读取一次 `orca account list --json`，只记录 Codex 的 `status`、`updatedAt`、周窗口 `windowMinutes/resetsAt/usedPercent` 和任务确实需要的权益字段。
2. 在自然需要第二个观测点时再读一次；只有 `updatedAt` 严格前进且窗口身份一致，才接纳为 B。未前进时标记为缓存探针并停止差值解释。
3. Orca 版本或字段协议变化时，先读取版本匹配的当前指南或 schema；只有变化影响本包结论时才做一次有界双点复测，不为复核制造 Token 消耗。

## 不适用范围

- 自动额度调度、自动模型切换、提醒或定时采样；
- Token→周窗口百分比换算、订阅账单或最大容量推断；
- 刷新券的消费、过期与恢复机制；
- Orca 以外的账户接口或未核验 Provider。
