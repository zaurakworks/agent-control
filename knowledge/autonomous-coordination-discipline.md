# K20：自治协调以事实、活跃绑定、单一来源与装端可追溯性守住边界

> 状态：正式当前公共知识。
> 最近核验：2026-08-12。
> 适用对象：Agent 系统中的协调者、交付复核者与路线图派发者；覆盖事实断言复核、Orca worktree 清理、共享单一来源的并行编排，以及 Plugin／Skill 的装端范围与版本审阅。
> 对象与环境：Windows 11；Orca 1.4.180；GitHub.com；`agent-control` 与 `agent-plugins` 在 2026-08-12 凌晨的自然任务。
> 证据上限：五条纪律分别来自 P0-1 忠实性误判、一次 worktree 误删事故、P0-2／P1-2 并行后出现语义双源，以及 P0-2 返修装端漏项与内容变更未递增版本的自然样本。它们支持当前窄边界内的协调纪律，不证明长期错误率、负责人注意力收益、所有共享文件都必须串行，或仅靠五条纪律即可保证自治协调安全。

## 回答的问题与价值门

自治协调中，怎样避免用五个容易误导的代理信号替代真正需要核验的事实：用“结构看起来成立”替代逐条事实核验，用分支名替代活跃执行绑定，用文件路径无交集替代语义落点无重叠，用派发者印象替代装端范围枚举，以及用内容审阅通过替代版本身份核对？

五类误判都会在后续多 Session 工作中重复出现，并可能分别造成错误裁决、执行现场损失、并行返工、已合并能力漏装和回退取证混乱。五条结论都能降低高代价协调错误，通过价值门。

## 可直接复用的结论

### 1. 逐条核验被断言的事实，不用结构成立代替内容忠实

#### 触发条件

协调者或评审者准备作出含下列任一语义的判定时触发：

- “忠实于来源”“逐项满足”“完整覆盖”或“没有能力回退”；
- 实现直接处理了某个既有事故、协议或合同缺口；
- 测试通过、承载结构存在或整体设计自洽，被用来支持一条更具体的内容断言。

#### 最短可执行结论

把判定中的每条事实断言拆成可观察主张，为每条主张写出来源对象与直接核验动作，再逐项比对。若断言是“忠实于十字段”，就列出来源十字段与实现十字段逐一核对；结构、测试和预算只能证明各自检查过的内容，不能替代字段忠实性。

任一主张缺少直接证据时，只能标为“尚未核验”或据此给出否决，不能把整体印象写成事实。

P0-1 的首轮样本中，协调者密封判定声称实现忠实于来源十字段，实际只核验了承载、控制器、测试与预算。独立评审逐字段比较后发现实现重定义字段、折叠 `validation` 与 `roi`，又加入未获授权的概念；这直接证伪了“忠实”断言，却不否定其余结构检查已经通过。

#### 失效条件

出现以下任一情况时，停止直接套用现有核对表，先重建本次主张与证据映射：

1. 来源协议、schema、合同 revision 或授权边界已经改变；
2. 断言只涉及可直接观察的结构存在性，不含忠实、完整、覆盖或事故路径语义；
3. 来源身份、版本或正文无法可靠取得，此时结论保持“尚未核验”；
4. 后续自然样本证明逐项比对仍系统性漏掉决定性语义，需要增加新的核验维度。

- [关联 #139（P0-1 迭代回执地基）首轮否决](https://github.com/Eridanus117/agent-control/issues/139#issuecomment-5262113488)：保存来源十字段、实现字段、具体差异与“其他检查通过仍不足以抵消忠实性失败”的逐项证据。
- [K18（三方审阅只替代已授权决定，且必须三席一致后落地）](./three-party-review-consensus.md)：保存协调者误判、独立否决、修订与一致复核的完整自然样本链；本包只提炼协调者的事实核验纪律，不重复三方机制。

### 2. worktree 清理按活跃绑定，不按分支名识别生命周期

#### 触发条件

任何准备删除 Orca worktree 的动作都触发，包括孤儿巡检、Worker 交付后的资源处置、失败任务回收和旧起草现场整理。分支名、任务短名或显示名“像旧对象”不能降低触发门。

#### 最短可执行结论

直接执行 [K19（自治运营以 Token 日聚合测燃烧，以活跃路径排除集守住 worktree 清理）](./autonomous-ops-measurement-and-cleanup.md) 的清理程序：先从当前 terminal 运行面构造非空 `worktreePath` 活跃排除集，再逐个核对任务终局、远端持久化、干净工作树、精确对象身份和删除连带影响。任一项未知就保留；分支名只用于人类辨认，不能作为删除匹配键。

本包不复制 K19 的完整四项证明、事故细节与 Orca 版本步骤，避免形成第二份清理规则。

#### 失效条件

K19 列出的任一失效条件命中时，本条同步停止直接复用，包括 terminal 不再提供可靠 `worktreePath`、远程 placement 无法由当前列表覆盖、Worker 释放或删除副作用语义改变，以及新事故证明现有证明链仍会误伤有主对象。此时回到 K19 的最少复核步骤，不在本包另造替代程序。

#### 一手来源

- [K19（自治运营以 Token 日聚合测燃烧，以活跃路径排除集守住 worktree 清理）](./autonomous-ops-measurement-and-cleanup.md)：已核验并保存 2026-08-12 凌晨 §49 误删两个活跃 Worker worktree 的事故链、一手来源映射、失效条件与最少复核步骤。

### 3. 改动同一共享单一来源的路线图项必须串行

#### 触发条件

准备并行派发两个或更多路线图项时，先检查它们是否满足任一条件：

- 都要改变同一个生命周期、经营维护、协议 schema 或其他共享单一来源的语义；
- 一个项目正在稳定另一个项目必须读取或承载的来源结构；
- 文件路径虽无交集，但两项会定义同一事件、状态、所有权、触发或终局语义；
- 任一项目的正确实现依赖另一项目尚未落定的决定、落点或回退结果。

#### 最短可执行结论

命中任一条件，就把两项建立为真实依赖并串行：先让上游项完成实现、独立复核与既定整合，或按合同进入失败回退；随后重新读取已经稳定的单一来源，再派发下游项。**文件交集为空只证明物理落点不同，不能证明语义所有权互不重叠。**

只有同时证明写入所有权排他、语义落点互不重叠、彼此不依赖尚未落定的来源结构，才允许并行。无法证明时按串行处理，不用并行后的冲突返修来换取表面吞吐。

2026-08-12 凌晨，P0-2 与 P1-2 被并行派发：前者试图增加生命周期事件的可重入收口，后者正在收敛生命周期／经营维护的行为资产单一来源。P0-2 虽刻意避开 P1-2 的文件路径，却另建了同域事务语义并与在途单一来源重叠，因而被否决；协调者复核后把返修重排到 P1-2 落定之后。

#### 失效条件

出现以下任一情况时，重新判断依赖图，不机械延续串行结论：

1. 经批准的架构已经把原单一来源拆成边界清楚、互不定义同一语义的独立来源；
2. 两项的语义落点与所有权可由直接证据证明互不重叠，且没有基座依赖；
3. 共享来源提供并经自然任务验证了等价的隔离、事务或冲突检测能力，足以在并行时守住唯一语义；
4. 新样本证明串行并未减少冲突或返工，需要重新界定真正的共享语义。

这些失效条件不会把“文件不同”单独升级为并行证据，也不会授权未经批准地拆分现有单一来源。

#### 一手来源

- [关联 #63（P0-2 生命周期事件可重入远端交接；agent-plugins）协调者裁决](https://github.com/Eridanus117/agent-plugins/pull/63#issuecomment-5262912066)：保存 P0-2 与 P1-2 并行、语义双源、否决成立、根因确认和改为串行重排的完整裁决。

### 4. 装端范围以 PR 全量改动为准，不以派发者印象为准

#### 触发条件

PR 合并后或准备进入三端安装验收时，只要改动涉及任一 Plugin、Skill、其 reference 或安装后会被运行端读取的配套资产，就触发本条。返修在原方案之外触及了更多 Plugin／Skill，或安装派发只点名了一个组件时，不能降低触发门。

#### 最短可执行结论

安装前执行 `gh pr view <pr> --json files`，或对最终 head／合并提交做等价 diff；把每个改动文件映射到所属 Plugin，并列出其中被改动的全部 Skill。逐个重装每个受影响的 Plugin，再逐个对被改动 Skill 做仓库源、Claude 缓存与 Codex 缓存的 LF 规范化指纹核验；具体卸装、重装和目标版本目录选择沿用 [K4（Claude Code 与 Codex Plugin 维护、验收的已验证陷阱）](./claude-plugin-maintenance.md) 与 [K6（跨平台文本验收统一使用 LF 规范化指纹）](./newline-normalized-acceptance.md)。安装动作可以按 Plugin 聚合，覆盖证明必须落到本批每个被改动 Skill。

P0-2 返修同时修改 `github-collaboration` 的 `issue-workflow`、`operating-ledger-maintenance` 和 `orchestrated-collaboration` 三个 Skill；落地回执却只派发安装 `orchestrated-collaboration`。协调者据此执行后漏装 `github-collaboration`，P0-2 核心路径一度没有进入运行端，直到版本异常复查才发现。故“我记得这次只改一个 Plugin”不是装端范围证据。

#### 失效条件

出现以下任一情况时，停止直接套用“PR 文件路径 → Plugin 目录”的当前映射，改从实际发布清单或构建产物重建覆盖关系：

1. 安装单元不再是当前目录型 Plugin，Skill 改为独立发布、生成或由其他清单装配；
2. 实际安装来源不是该 PR 的最终 head／合并提交，或合并过程带入了文件清单之外的发布内容；
3. 平台提供并经自然任务验证了原子化全量安装，且能直接证明本批所有改动 Skill 都进入各运行端；
4. 新样本证明仅靠文件路径枚举仍会漏掉生成资产、跨 Plugin 复制或其他真实运行入口。

这些失效条件只改变覆盖关系的取得方式，不把安装命令成功或 Plugin 名称印象升级为覆盖证据。

- [关联 #65（P0-2 生命周期事件可重入收口返修；agent-plugins）三方一致回执](https://github.com/Eridanus117/agent-plugins/pull/65#issuecomment-5263427117)：落地指令只写“装 `orchestrated-collaboration` 到三端并指纹核验”，与 PR 全量改动范围形成可重复核对的漏项样本。

### 5. 发布内容变化必须递增版本，审阅同时核对版本与指纹

#### 触发条件

任一 Plugin 内会进入运行端的 Skill 正文、description、reference 或其他发布内容发生变化时触发；三方审阅、合并前复核和装端验收各自都必须检查。只改仓库外说明、测试或不进入发布包的资产时，先证明它不改变发布内容，再决定本条是否适用。

#### 最短可执行结论

逐个受影响 Plugin 比较 base 与最终 head：发布内容改变时，`plugin.json` 版本必须按仓库版本策略递增；内容已变而版本未变，审阅即否决，不能等到装端阶段再凭缓存状态猜测。三方审阅的检查表必须同时包含“改动文件覆盖了哪些 Plugin／Skill”和“每个受影响 Plugin 的版本是否递增”。

版本号提供可辨认的发布身份、缓存选择与回退取证；内容指纹仍是证明运行端内容正确的真门。版本递增不能替代三端 LF 规范化指纹，指纹一致也不能容许同一版本号先后对应不同内容；二者分别守住可追溯性与内容正确性。

P0-2 返修改变了 `github-collaboration` 与 `orchestrated-collaboration` 的发布内容，但两份 manifest 仍分别为 `0.3.11` 与 `0.2.2`，三席审阅均未指出。结果是同一版本身份在前后时点指向不同内容，污染版本—内容映射，也放大了漏装发现与回退取证成本。

#### 失效条件

出现以下任一情况时，停止直接要求当前 `plugin.json` 字段递增，先核验新的不可变发布身份与回退机制是否已经取代它：

1. 平台改用内容寻址、不可变 revision 或等价机制，并经自然安装与回退样本证明同一身份不可能对应不同内容；
2. 发布清单或版本来源迁离 `plugin.json`，且当前安装器、缓存目录和审阅面都以新的单一来源为准；
3. 变更经直接 diff 证明完全不进入发布包，此时只保留普通审阅，不制造空版本；
4. 仓库版本策略改变了递增粒度或生成方式，此时沿用新策略，但每个已变发布物仍须取得新的唯一身份。

版本策略改变不会取消指纹真门；若新的身份机制不能同时支持内容定位与回退取证，本条保持适用。

## 守恒与置换对象

本次净增第 4、5 条，置换两项已经在 P0-2 自然任务中失效的隐含做法：以派发者对改动范围的记忆决定装端清单，以及只审内容与指纹、不把版本身份列为合并前硬门。K20 只承载协调者怎样枚举、派发和审阅；卸装、重装、缓存目录与指纹算法仍分别复用 K4、K6，不复制其机制正文。

## 变化、冲突与缺口

- **直接复用**：第 1 条的完整样本链已在 K18，第 2 条的完整程序已在 K19；两者仍在各自失效条件内，本次不重复完整机制。
- **直接复用**：第 4、5 条复用 K4 的安装与目标版本目录语义、K6 的 LF 规范化指纹方法，只补协调者的范围枚举与版本审阅门。
- **新增缺口**：第 3 条补齐“文件无交集但共享单一来源语义重叠时能否并行”；第 4 条补齐“安装派发怎样覆盖返修实际触及的全部 Plugin／Skill”；第 5 条补齐“内容正确时仍须怎样保持版本—内容映射可追溯”。
- **没有证据冲突**：五条一手链都支持“不能用低成本代理信号替代目标事实”的共同边界；第 5 条也与 K4“指纹是真门”的结论一致，只增加与其职责不同的版本身份门。
- **仍未知**：共享单一来源串行、装端漏项与版本漏增都各只有一组自然样本，尚无跨仓、跨后端的错误率、吞吐收益或审阅成本对照；因此结论保持在当前 Agent 系统路线图编排与目录型 Plugin 发布边界。

## 两道准入门逐条判定

| 结论 | 价值门 | 可信门 | 判定依据 |
| --- | --- | --- | --- |
| 1. 逐条核验被断言事实 | 通过 | 通过 | 后续复核会反复出现；P0-1 保存了具体断言、逐字段证据、误判与后续一致复核。 |
| 2. 清理按活跃绑定 | 通过 | 通过 | 后续 worktree 处置会重复出现；K19 已保存误删事故、完整程序、边界与最少复核步骤。 |
| 3. 共享单一来源串行 | 通过 | 通过 | 路线图组波会重复出现；上述 P0-2 协调者裁决保存并行、语义重叠、否决和重排链。 |
| 4. 装端按 PR 全量改动枚举 | 通过 | 通过 | 每批 Skill 发布都会复用；P0-2 文件清单、落地指令与真实漏装结果构成可重复核对的范围缺口链。 |
| 5. 内容变化递增版本 | 通过 | 通过 | 每批 Plugin 发布与回退都会复用；P0-2 commit、两份 manifest 与三席回执共同保存内容变化、版本未变和审阅漏检。 |

五条结论均给出明确问题、最短动作、对象与核验时间、不能外推的范围、失效条件和一手来源链；表达足以供 Agent 在自然检查点直接判断，满足八项可信门。

## 下次最少复核步骤

1. 事实断言复核时，只重读本次断言对应的来源 revision，并逐项保存“主张—证据动作—结果”；来源或 schema 未变时，不重做整套三方机制调研。
2. worktree 清理时回到 K19，动态读取当前 Orca 指南并执行其最少复核步骤；不为复核另造待删对象。
3. 路线图组波前列出每项的**语义单一来源、排他所有者与基座依赖**，而不只比较文件路径；下一次自然命中时记录串行或并行选择、冲突、返工与关键路径影响。
4. 每次装端前从最终 PR head／合并提交重新枚举文件，记录“改动 Skill → 所属 Plugin → 各端目标版本目录 → 指纹结果”；任一项没有覆盖证据就停止验收。
5. 每次三方审阅逐个比较受影响 Plugin 的 base／head 版本；内容变化而身份未变时记录否决，版本递增后仍继续执行 K6 指纹核验。
6. 只有新证据改变五条结论之一时才增量更新对应段；K4、K6、K18 或 K19 失效时，本包的引用结论同步退出直接复用。

## 不适用范围

- 不含忠实、完整、覆盖或事故路径语义的普通结构存在性检查；
- worktree 清理的完整执行协议，仍以 K19 为唯一知识承载；
- 语义落点、写入所有权与依赖均有直接证据证明互不重叠的并行工作；
- 不进入发布包的测试或仓库说明变更，以及已有不可变发布身份机制直接证明覆盖与回退的安装系统；
- Plugin 的卸装、缓存目录定位和 LF 规范化指纹算法，仍分别以 K4、K6 为唯一知识承载；
- 自动组波、自动派发、自动清理、常驻监控或新的协调后端；
- 修改 `authority/`、改变现有单一来源边界，或代替负责人作产品采用与长期依赖决定。
