## 回答的问题与价值门

协调者等待 Claude Worker 完成时，事件驱动唤醒当前处于什么生效状态？它能提供什么保证、以什么方式退化？迭代这条链路时，哪些设计不变量已经过实测与独立核验？

每个并行波次协调者都要选择等待策略（`check --wait`、cron 兜底、事件唤醒），而把「仓里已合并」误当「运行时已生效」、或把「没收到唤醒」误当「没有完成」都会直接造成误判；桥后续迭代（新增事件源、改聚合参数）也会重复用到已验证的设计不变量。通过价值门。

## 可直接复用的结论

### 1. 事件唤醒是「前台 listener 在场时的加速」，不是保证；缺席静默退化、不产生负事实

链路形状：已安装的 Claude Hook 二进制把 `Stop`／`TaskCompleted` 投递到固定 loopback `127.0.0.1:43127`；只有当有一个**前台** `wake` listener 进程在跑时，事件才会变成显式 Orca Run 的观察性 `status` 消息。listener 缺席实测：已安装 Hook 在 85 ms 内返回 0、stdout 为空，只在 stderr 记录 loopback 拒绝——事件被静默丢弃，系统自然退回既有 cron／人工精确 Dispatch 核对。Hook 缺席、token／schema 错误、Orca 写入失败、进程退出同样都不产生负事实。

因此：协调者不得把「没收到唤醒」解释为「Worker 未完成」；依赖事件唤醒前必须先确认 listener 进程确实在前台运行，否则按 cron 兜底节律（本仓对照口径：最坏约 20 分钟）安排核对。唤醒消息本身是观察性 `status`，不改变生命周期——真实样本中协调者收到唤醒后仍核对 Dispatch 为 `dispatched` 才 ack，未误判生命周期。

### 2. 合并不等于安装；本机聚合版已经 225-D1 批准并同路径覆盖安装

聚合版 `wake` 模式随关联 [#233（事件唤醒回执桥 PR）](https://github.com/Eridanus117/agent-control/issues/233)合入 `main` 后，负责人已消费 225-D1（A）：从当时当前 `main` 构建，覆盖 `%LOCALAPPDATA%\agent-control\claude-receipt-bridge.exe`，三个既有 Hook 配置零改动。[关联 #225（事件驱动唤醒端到端接通）225-D1 决定回执](https://github.com/Eridanus117/agent-control/issues/225#issuecomment-5282372040)记载安装件 SHA-256 前缀 `a5ef9ea14f5154ac`；2026-08-13 本机最少复核得到完整值 `A5EF9EA14F5154ACFA77E152481370AEADFD4A0B644C5193E927073C0AB2D65E`，与回执一致。旧逐条转发版保留为同目录 `claude-receipt-bridge.exe.bak-pre225`（复核 SHA-256 `8B21486C2BBB006723A5C6AABDFD11A9DCB753F0B314B32C380CC9D24DF5967D`）；需要回退时用该备份替回原路径，仍不改 Hook 配置。

同一决定回执还承载**已批准安装件的同路径版本更新预授权**：仅当更新同时满足「同路径覆盖、配置面零改动、留旧版可回退、经非参与者核验的已合并 `main` 构建」时，协调者可直接执行并留回执，不再逐次请求。它不覆盖全新安装、配置面变更、OS 服务／开机自启或公网端口；这些动作仍归负责人。后续使用这项预授权时必须引用远端决定回执并逐项核对条件，不能从本知识包或一次既有安装外推新授权。

### 3. 聚合桥设计不变量（已实测＋独立核验，供迭代复用）

- **只消费正向完成事件**：`Stop`／`TaskCompleted`；不给失败、缺席或超时制造负事实。
- **250 ms 聚合窗口**：同批多回执合并，每批只向显式 Run 投递一条 `status`（payload `agent-control.claude-receipt-wake` v1）。
- **按 `taskId + dispatchId + event` 做 2 分钟 TTL 去重**，且 TTL 只在 Orca 回读到目标 Run 的非空真实消息 ID（正确 Run、`status` 类型）后才登记；发布失败不登记成功 TTL，后续同键回执仍可再到达。
- **只做前台进程**：不是 OS 服务、开机启动项或调度器；只写显式 Run 的观察性 `status`，不选任务、不派发、不确认 Delivery、不改 Orca Task 或 GitHub 生命周期。

### 4. 单样本时延：Claude 启动到协调者可见 6.504 秒

真实端到端样本：Claude 最小 `-p` worker 自然 `Stop=2026-08-13T06:29:44.244Z`，桥 `observedAt=06:29:44.496Z` 形成 Run `status` `msg_4e3eff649b46`，协调者同秒可见并回读 `receiptCount=1`；从 Claude 启动到协调者可见 6.504 秒，对照 cron 兜底最坏约 20 分钟。这是一个样本的量级证据，不能外推为稳定时延或命中率。

## 例外、未知和不能推出的结论

- 未运行多 worker 长时自然样本、主机休眠／重启或 Orca runtime 离线保证；6.504 秒不是稳定时延承诺。
- 结论 2 是本机 2026-08-13 的时点事实；安装件或备份哈希变化、决定回执被纠正／替代时，必须重新核对，不能沿用本包。
- 同路径版本更新预授权只覆盖四项条件同时成立的已批准安装件更新；不能推出全新安装、配置变更、OS 服务／开机自启、公网端口或其他宿主能力已经获准。
- 桥只覆盖 Claude Hook 事件源；不能推出 Codex 或其他 Provider 有等价链路。
- 事件唤醒不替代精确 Dispatch 核对：唤醒只是提示协调者去读运行面，不是生命周期证据。

## 失效条件

出现以下任一情况时，受影响结论停止直接复用并先做最少复核：

1. 已安装二进制或 `.bak-pre225` 备份哈希与本包不一致，或者 225-D1 决定回执被纠正／替代；
2. 桥代码、`wake` 模式语义、聚合窗口、TTL 键或 loopback 端口变化；
3. 用户级 Claude Hook 配置或 Hook 事件（`Stop`／`TaskCompleted`）语义变化；
4. Orca Run `status` 消息语义或回读接口变化。

## 下次最少复核步骤

1. 读取[关联 #225（事件驱动唤醒端到端接通）](https://github.com/Eridanus117/agent-control/issues/225)当前状态与 225-D1 最新决定回执，确认没有后续纠正或替代。
2. 依赖事件唤醒前确认 `wake` listener 进程确实在前台运行；缺席时直接按 cron 兜底节律安排核对，不等待唤醒。
3. 需要判断运行版本或回退能力时，比对 `%LOCALAPPDATA%\agent-control\claude-receipt-bridge.exe` 与 `.bak-pre225` 的哈希；与本包不一致时停止复用安装态结论并追溯新的远端回执，不按文件名猜版本。
4. 执行已批准安装件的同路径更新前，按 225-D1 决定回执逐项确认同路径、配置零改动、旧版可回退、非参与者核验且已合并 `main` 四个条件，并在执行后留远端回执；任一项不成立就不套用预授权。
5. 下一次自然唤醒样本顺手记录端到端时延与协调者是否需要纠正生命周期误判；不为复核制造人工事件。

## 不适用范围

- 全新安装、配置面变更、OS 服务／开机自启、公网端口，以及不满足四项预授权条件的替换或卸载（仍归负责人）；
- 把唤醒消息当作任务完成、交付验收或生命周期判定依据；
- 新增 OS 服务、开机启动、公网端口、自动派发或自动合并；
- 非本机环境、其他 Provider 事件源与未核验的 Orca 版本。
