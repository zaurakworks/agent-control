# K23：机械窄任务的 headless 车道已有单波次样本，Orca 窄战术消费者前件仍不成立

> 状态：正式当前公共知识。
> 最近核验：2026-08-13。
> 适用对象：在现有任务合同与写入所有权内，为验证、窄复审或巡视类机械任务选择 Orca 交互 Worker、受限 headless advisory，或判断是否值得重开 Mode B 战术消费者前检。
> 对象与环境：Windows 11 Pro build 26200；Orca packaged 1.4.181；Codex CLI 0.147.0；Claude Code 2.1.229；本仓 `tools/codex_liveness` 与 `tools/claude-headless`。
> 证据上限：一次 Orca 1.4.181 只读 P0 前检、一个含 2 个自然 Dispatch 的影子样本、一个含 5 个 headless 任务的真实机械波次及负责人第二道门验收；不支持全迁、长期依赖或严格性能优越。

## 回答的问题与价值门

当前版本能否把常驻战术层实现成最窄 Orca 消费者？如果不能，受限 headless 是否已经有足够证据承接一部分机械窄任务，它相对 Orca 丢失什么？

负责人已经把这组证据消费为下一波的实际车道选择：机械的验证／窄复审／巡视优先走 headless，交互、长程和需要负责人观察的任务留在 Orca。后续每个波次都会重复使用该边界，而错误外推可能造成越权常驻控制器、不可清理 Run、观察缺失或把单波次优势写成产品迁移，因此通过价值门。

## 可直接复用的结论

### 1. Orca 1.4.181 不具备本次 Mode B P0 所需的最窄消费者前件

关联 [#207（Mode B P0 前检）](https://github.com/Eridanus117/agent-control/issues/207)对当前公开运行面与动态指南的直接核验只得到一个局部能力：当前 Dispatch 可用 `peek + wait` 做不消费 Delivery 的阻塞读。以下完整前件均未成立：

- `run-create`／`run-use` 只提供协调者终端绑定，没有“只读 Delivery＋同键 ticket 写＋固定 reconcile 激活”的最窄 consumer 角色或权限参数；
- 没有单 Run 安全移除／销毁入口，活跃协调中也不能用全库 `reset` 冒充清理；
- 没有领域幂等 wake ticket 或业务幂等键；
- 没有把非战略调用者限制到预注册 Task、固定参数和同作用域入口的 capability；
- automation 只有定义／历史读取入口可见，重启后正向持久性、重叠、禁用传播、在跑实例和资源回收均无正样本。

因此当前结论是“回 B，不进 P1”：不在 1.4.181 证据上建设常驻战术消费者。这里的“前件不成立”是版本绑定的接口与可清理性事实，不证明 Orca 永远不能提供这些能力，也不否定协调者协议中的 Delivery 重放语义。

### 2. Codex 三态机器验活取得首个自然影子样本，只有 `0/2` 分歧证据

关联 [#216（Mode C 混合试点第一阶段）](https://github.com/Eridanus117/agent-control/issues/216)的 S 阶段旁观两个真实 Codex 高层 Dispatch。`tools/codex_liveness` 以精确 `taskId + dispatchId` 判定两例均“已开始”，协调者人工观察也为“已开始”，分歧 `0/2=0%`；影子侧没有发送输入、补提交、重派或修改 Orca 状态。

这证明该双任务波次中机器标签与人工标签一致，且可在零干预下运行；它不证明长期准确率、误报／漏报为 0、其他 Provider 通用或任何两例都足以验收机器验活产品化。

### 3. 五件 headless 机械任务达到预注册阈值，同时暴露最高档观察损失

H 阶段并发运行 5 个无工具窄复核，每个调用使用固定对象 schema、1 个 agentic turn、`$0.10` 客户端预算、60 秒外层门、无会话持久化和无自动重试：

| 指标 | 本次结果 | 可推出／不能推出 |
| --- | --- | --- |
| 零人工介入完成 | `4/5=80%` | 恰好达到预注册阈值；1 件 60.278 秒超时，不能写成全成功 |
| 输入／错绑竞态 | `0/5` | 单调用、单进程、单回执下未观察到；不是长期发生率 |
| 周期 | 中位 44.282s，均值 40.696s，最大 60.278s | 均低于 965s 停止线；与 Orca 历史任务范围不同，只是方向性信号 |
| 成本 | 4 个成功项合计 `$0.076320`，均值 `$0.019080` | H1 超时成本未知，不能把未知记为 0 |
| 观察损失 | `5/5` 均为 2 | 没有独立 Orca Task 行、在工数和生命周期视图，这是明确代价 |
| 清理 | 无错绑、双写、孤儿或临时目录／进程残留 | 只证明本波次按包装器清理成功 |

同日四个 Orca 窄复审历史样本中位 482.5s，而 H 中位为其 9.18%；但 Orca 样本包含 Session 恢复、远端合同读取与 GitHub 交付，H 只是无工具窄语义判断，不能据此宣称严格性能优越或用 headless 替代完整交付链。

### 4. 当前生效实践是有界分流，不是全迁

负责人完成关联 [#216（Mode C 混合试点第一阶段）](https://github.com/Eridanus117/agent-control/issues/216)的第二道门验收后，明确消费为：后续机械的验证／窄复审／巡视类任务默认优先使用 `tools/claude-headless` 与 `tools/codex_liveness` 形成受限车道；交互、长程、需要负责人观察的任务继续使用 Orca。完整迁移问题保持开放，仍受关联 [#214（Mode C 可行性调研）](https://github.com/Eridanus117/agent-control/issues/214)的翻转条件约束。

这条实践只在当前任务已经有合同、授权和写入所有权时选择执行车道。Headless 模型输出仍是 advisory；外层确定性调用者负责路径隔离、权限、预算、超时、schema、结果消费与升级。它不产生跨 Issue 派发、GitHub 写入、产品决定或长期平台授权。

## 例外、未知和不能推出的结论

- Mode B 负向事实只绑定 1.4.181 当前公开能力面；未创建隔离 Run 或 automation，因为最窄权限与可清理性已命中停止门。
- S 只有两个 Codex 自然样本；`0/2` 分歧不能估算长期准确率。
- H 只有 5 个 Claude Haiku 无工具窄复核；1 件超时且成本未知，任务类型和 Orca 历史基线不等价。
- Headless 的观察损失在本批 5/5 都是最高档 2；当前实践不能用于需要持续 steering、ask/reply、负责人观察或完整 Orca 生命周期的任务。
- 负责人批准的是有界车道选择，不是全迁、产品采用、长期依赖、拆除 Orca、常驻控制器或自动派发。

## 失效条件

出现以下任一情况时，让受影响结论先退出直接复用：

1. Orca 升级并新增可核验的最窄 consumer 权限、单 Run 安全清理、幂等 ticket、固定 reconcile capability，或明确 automation 的重叠／禁用／在跑实例／资源回收；
2. `tools/codex_liveness`、`tools/claude-headless`、Codex／Claude 事件 schema、预算／超时或清理语义变化；
3. 自然 headless 波次出现错绑、双写、孤儿、越权、成本超门、系统性超时或结构化输出不能消费；
4. Orca 增加与 headless 相当的无输入框 batch lane 且保留任务级观察，或 headless 获得可核验的等价观察面；
5. 负责人改变机械／交互任务分流或批准全迁、停止试点。

## 下次最少复核步骤

1. 选择车道前先确认任务已经有独立合同、授权、写入所有权和可判定的“机械／交互”边界；本包不替代这些前件。
2. 机械 headless 任务继续记录状态、周期、人工介入、竞态、成本、观察损失和清理；不为凑样本重试超时项或制造 Orca 对照。
3. 机器验活继续绑定精确 `taskId + dispatchId`，自然旁观时比较工具与人工标签；样本扩大后再评估误报／漏报，不从 `0/2` 外推。
4. 只有 Orca 版本／指南出现上述能力信号时才重开 Mode B P0；先只读核验权限与清理，再决定是否创建隔离对象。
5. 若任一停止门命中，保留回执和资源后态，退回 Orca 交互路径或请求现有合同定义的决定，不自行扩大工具权限。

## 不适用范围

- 需要持续交互、长程上下文、ask/reply、负责人实时观察或完整 Worker 生命周期的任务；
- 未经授权的跨 Issue 派发、共享写入、常驻控制器、automation 或宿主环境修改；
- 把单波次周期差异作为采购、迁移、长期依赖或拆除 Orca 的依据；
- 其他操作系统、远程 placement、未核验 Provider 或无等价外层边界的 headless 调用。
