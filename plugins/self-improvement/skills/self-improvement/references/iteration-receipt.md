# Agent 系统迭代回执协议

> 来源：[关联 agent-control#139（P0-1 迭代回执地基）](https://github.com/Eridanus117/agent-control/issues/139)的实施合同，以及[关联 agent-control#135（自我迭代优化循环设计）的设计交付](https://github.com/Eridanus117/agent-control/issues/131#issuecomment-5261868325)。当前资产最多证明实现完成；三方审阅、自然样本、产品采用与长期依赖各需独立证据。

## 地位与边界

迭代回执是一份跨机制共用的**证据协议**：让新的 Session 只读当前 Issue 中的一条自足评论，就能恢复本轮为何发生、处理了什么、证据到哪一级、结果去了哪里，以及何时复核。它不作触发、方法选择、授权、知识准入或生命周期决定。

- `adaptive-problem-solving`（APS）仍是唯一任务内控制器，负责恢复父目标、判断普通处理或方法介入、选择路线、调整路径与验收证据等级；回执只记录它已经作出的路由及结果。
- Issue 生命周期继续由现有 GitHub 工作流驱动者维护；回执字段不是状态机，不以“字段齐全”推导任务完成、Issue 状态或产品采用。
- `self-improvement` 只承载本协议正文。引用本协议不等于调用自我改进，也不扩大该 Skill 的纠正／抽象循环触发条件。
- `orchestrated-collaboration` 只在已经需要跨 Session 协作时提供所有权、派发、通信和独立验收；它不承载或解释回执协议。

低风险、容易回退、没有跨任务复发证据的局部错误只在当前任务修正，不建立完整回执。只有当前 Agent 系统任务已经登记一次迭代事件，或在自然里程碑需要跨 Session 恢复本轮因果时，才按需读取并使用本协议。

## 寄生载体与自然节律

每轮在**当前 Issue** 保留一条自足评论，标题写成“迭代回执｜本轮对象短题”；评论的稳定 URL 就是该轮身份。首次触发时填写当下已经知道的内容，未知项明确写“未知”和下一取证动作；后续只在自然里程碑更新同一条评论，使正文始终能被新 Session 独立恢复。被新证据替代的判断必须保留原来源和替代关系，不能静默改写历史。

自然里程碑包括：高影响 Agent 系统资产准备验收、父目标进入阶段验收、长任务恢复或交接、Issue 收口蒸馏、方法完成一次真实自然使用，以及 `recheck` 已登记的范围匹配真实任务。墙钟时间、额度、空闲 Agent、资产数量和空队列都不单独触发回执。

第一阶段只允许活跃 Session 在这些事件点人工写入或更新评论。不建立数据库、独立登记表、定时器、Hook、Webhook、离线唤醒、轮询或自动派发；日历式或常驻自动化需要新的证据、产品决定和授权。

## 最小十字段

字段名固定，正文可以用 Markdown 列表或表格表达；没有证据时保留字段并如实写未知，不用空白承担含义。

| 字段 | 必须回答什么 |
| --- | --- |
| `trigger`（触发） | 哪个即时事件或自然里程碑使本轮现在发生；给出稳定来源，并说明为什么低风险任务内修正已经不足或为什么需要跨 Session 恢复。 |
| `object`（对象） | 精确对象、版本／commit／PR head、父目标、对应成功条件、当前阶段、基线、适用环境、回退点与写入所有权；对象变化时明确旧、新版本。 |
| `finding`（发现） | 发现正文及其分类：已核验事实、推断或未知；再标明行为／技术缺口、证据冲突、方法样本、产品取舍或一次性摩擦，附严重度与最强可信反方。 |
| `route`（路由） | APS 选择的普通修正、`self-improvement`、实验、轻量／重型攻防、知识维护、方法卡证据或负责人决定门；说明选择理由、成本上限和退出条件，不复制被路由 Skill 的步骤。 |
| `authority`（授权） | 当前已授权、明确未授权、停止条件、下一责任人及其可执行边界；回执、审阅通过或发现本身都不产生新授权。 |
| `validation`（验证） | 开始前固定的预注册判据、实际运行及其结果、未运行项与原因、剩余验证缺口和可执行回退；不以“应该可以”或事后改写判据制造通过。 |
| `landing`（落点） | 结果实际进入的 Issue／PR、研发记忆、知识、方法登记面、入口或 Skill，以及可重读的稳定来源；计划落点与已写入事实必须分开。 |
| `acceptance`（验收） | 父目标贡献、能力回退、来源距离与当前证据等级，以及当前最多能声称的结论；低一级不得冒充高一级。 |
| `recheck`（复核点） | 会使结论失效或翻转的事实、下一次范围匹配的自然里程碑、最少复核步骤和下一责任人；没有日历任务时明确写“等待自然事件”。 |
| `roi`（投入产出） | 可见的返工、总周期、负责人注意力和维护税；使用高／中／低或可得近似，不伪造精确收益。 |

## 各机制如何引用而不复制

- APS 在阶段小合同、攻防裁决或父目标验收确实属于已登记迭代事件时，读取本协议并把路由与证据交给当前回执的唯一写入者；普通任务不为形式完整创建回执。
- 攻防的第一轮发现仍只是候选；在裁决或实验以前不能把发现数写成已确认缺陷。各视角只把新增证据交给当前回执的唯一写入者，不再建立一份攻防专用回执。
- `knowledge-maintenance` 只在迭代事件路由到知识出口时，把 `acceptance`、`landing` 与 `recheck` 的增量结果交给当前回执的唯一写入者；价值门与可信门仍是知识准入的唯一判断，不新增“迭代中知识”等状态。
- 自我改进分支把纠正、根因、被替代判断和行为载体写入同一回执，但仍按主 Skill 的触发与退出合同返回原始任务。

某个机制只回填自己实际产生的证据；它不替其他机制补写结论，也不复制本表。字段解释只在本文件维护，引用方只保留“何时读取、回填哪些结果、什么不因此改变”的最窄路由。

## 更新与收口

1. 写前确认当前回执评论的排他写入所有权，再重读当前 Issue、同一评论和本次要引用的稳定来源，避免多 Session 互相覆盖或用本地旧摘要覆盖远端新事实。
2. 每次里程碑只更新发生变化的证据，但评论更新后必须仍然十字段自足；事实、推断、未知和已被替代内容继续可区分。
3. 写后重读评论，确认目标 Issue、稳定 URL、正文、对象版本和下一责任人均为真实远端状态；结果未知时先核验再补写。
4. `validation` 如实保留实际运行、未运行与回退，`acceptance` 只陈述证据支持的水位；任务或 Issue 是否收口仍交给现有生命周期驱动者，产品采用和长期依赖仍需各自证据与负责人决定。
5. 到 `recheck` 指定的自然任务时更新 `roi`，记录复发、误报、返工、总周期、负责人注意力与维护税的可见近似。若两个异质自然样本都显示成本高于收益，或触发大量被驳回候选，退回分散机制；回执可以保留为证据格式，不据此建设自动化。
