# 经营总账维护

让 Agent 系统的重要诉求、投入、决定和证据在 GitHub 中保持可见、可恢复，同时避免把每句话、每个任务或每次实现都升级成正式产品诉求。

本 Skill 维护的是已经选定的观察面，不是新的权威、授权源、任务执行器或事件后端。它可以更新真实 GitHub 状态，但不能因为条目存在就启动工作。

## 一、判断是否进入

以下任一变化出现时进入：

- 负责人确认、修改、暂停、替代或取消 Agent 系统的目标、诉求或重要能力；
- 出现可能影响路线、投入或边界，且值得跨 Session 保留的重要候选；
- 一个 Agent 系统计划、实验、交付或维护事项进入就绪、进行、验收或完成节点；
- 新证据改变了诉求满足判断、证据等级或下一项投资决定；
- 任务恢复、交接或验收需要核对经营总账是否仍与远端事实一致；
- 用户直接要求查看、收件、整理或更新经营总账。

以下情况不进入：

- 与 Agent 系统无关的普通任务；
- 没有改变跨 Session 状态的一次性细节、普通工具调用或临时推理；
- 只是因为 Project、Issue 或 Skill 存在，就周期性全量扫描；
- 当前任务已经处理过同一变化且没有新证据；
- 需要后台监听 GitHub、主动唤醒 Session、自动规划、派发或调度。

如果是否值得保存本身会产生明显判断成本，先看它是否可能改变后续路线、授权、投入或恢复。影响低且容易重新获得时退出；影响可能高但尚未确认时只进入收件箱，不建立正式诉求。

## 二、恢复来源、授权和远端事实

1. 按当前 Agent 系统入口读取权威根、活动任务及其明确链接的经营总账权威；不从旧 Issue、旧 Project 或研发记录反向定义当前需求。
2. 从当前权威取得经营总账 Project、根目标、字段语义和状态授权边界；若入口缺失或权威与远端明显冲突，停止写入并报告。
3. 识别本次变化的来源：负责人明确决定、当前任务事实、远端交付状态、受控实验或 Agent 候选。把来源强度与将要写入的状态分开。
4. 写入前重新读取受影响的 Project 条目、Issue、父子关系、PR 和字段值。GitHub 是动态事实来源；聊天、本地草稿和旧工具输出不能替代当前远端状态。
5. 核对写入授权：
   - 已存在交付事项的普通执行状态可以按有效交付合同维护；
   - Agent 可以提出带证据的诉求满足判断；
   - 一级诉求、重要能力、产品采用、长期依赖和正式新诉求仍需负责人确认；
   - 收件箱草稿只保存候选，不授权实施，也不等于负责人认可；
   - 没有当前 GitHub 写入授权时保持只读，把建议交回当前任务。

## 三、先决定是否以及保存到哪里

只选择下列一个最小去向：

1. **退出，不保存**：低影响、一次性、容易重新获得，或与 Agent 系统经营无关；
2. **收件箱草稿**：可能影响路线、投入或边界，但尚未完成必要对齐；只写清原始观察、为什么可能重要、关键未知和升级条件；
3. **更新现有正式事项**：已经存在准确的目标／诉求、能力缺口、计划／实验或交付任务；优先更新，不创建竞争条目；
4. **建立正式事项候选**：负责人已经确认其产品地位且 GitHub 写入已授权；无论单一事项还是父／子交付图，凡需新建 Issue 都路由到 `objective-to-issues` 的第三节共享创建骨架，单一事项不再保留绕过分类、原生关系或 Project 投影的直建路径；
5. **只更新当前任务或研发记忆**：变化是当前授权、短期进度、失败或纠正，但不应成为经营总账条目。

登记摩擦时必须回答「本坑可否被一次能力面调研提前排掉」，并把结论用一句话写入摩擦正文；结论须指向对应工具。该结论只作为本节既有最小去向判断的证据，调研候选仍按上述收件箱准入形成；不另设欠账计数器，也不自动开工。

不要把研究步骤、组件清单、Agent 数量、每个 PR 或每条聊天机械转换成 Issue。一个下级事项必须能说明它怎样服务上级；横向贡献无法用一个主要父级表达时，正文说明即可，不为此建设多父知识图谱。

## 四、保持四种节点语义

七种标题前缀／类型 label 到本节四种节点、以及是否使用执行状态的**唯一映射**，只在 `objective-to-issues` 第三节“七类创建类型到四种经营节点的唯一映射”表维护。本 Skill 每次创建、恢复或维护条目前读取并逐行应用该表；不按标题语感重新分类，不建立第二张映射表。远端标题、类型 label 与表中同一行不一致时停止投影并报告分类冲突，不能任选一个字段覆盖另一个。

- **目标／诉求**：描述希望长期改变的现实结果；可以长期开放，不以子项关闭比例表示满足；
- **能力缺口**：当前缺少、会妨碍一个或多个诉求的能力；重要能力是否当前满足由负责人确认；
- **计划／实验**：为减少关键未知或验证假设而进行的有界投入；完成只证明实验合同已完成；
- **交付任务**：可独立实施、验证和关闭的工作；需要实际推进时统一路由到 `issue-workflow`，由它判定这是一个叶子还是一棵需要维护的子树，再决定进入交付、审查还是父级回收。不要从总账直接跳进某个交付段，那会在驱动者之外再开一条并行状态机。

仓库表示资产归属，不反向切割产品诉求。Project 只投影跨仓全局状态，不取代每个 Issue 的合同。

## 五、分开维护三类状态

### 执行状态 `Status`

只用于计划／实验和交付任务：

- `收件箱`：尚未完成正式准入；
- `待决定`：存在一个当前、明确且尚未消费的负责人决定动作；
- `就绪`：边界、依赖、授权和所有权足以开始；
- `进行中`：Agent 或执行者仍在工作或内部核验；负责人决定已经消费、下一动作回到执行者时也使用这一状态；
- `验收中`：证据已经形成，并且存在一个当前、明确且尚未消费的负责人接受／否决动作；它同时应出现在“等待负责人”；
- `完成`：交付合同已经关闭。

长期目标／诉求和重要能力默认不填执行状态。设置 `完成` 可能触发 GitHub Project 自动关闭关联 Issue；在写入前必须确认关闭已经获准，并在写入后复核 Issue 实际状态。

### 等待负责人和生命周期事件只回指唯一正文

投影或清除“等待负责人”、消费决定、同步来源事实／父级证据／Project、处理部分失败或重入以前，**必须完整读取** [`../issue-workflow/references/lifecycle-closure.md`](../issue-workflow/references/lifecycle-closure.md)。该文件唯一规定“当前、明确、尚未消费”三项门、恢复定位符、单写者、来源在先的固定顺序、Project 最后投影、四面回读与只补缺段；本 Skill 不再复述或重判。

本 Skill 的阶段增量只有 Project 适配：使用 `issue-workflow` 已核验的 typed fact，按本节执行状态映射写目标字段并回读。没有覆盖四面的排他所有权时整体交回合格驱动者，不拆给第二个 Session；状态不可得时保持未知并停写。

### 诉求状态

只用于目标／诉求和能力缺口：`待澄清`、`未满足`、`部分满足`、`当前满足`、`暂缓`、`不再需要`；计划和交付使用 `不适用`。

Agent 可以根据证据提出变化，但一级诉求和重要能力的任何诉求状态变化都需要负责人确认。实现、验收、样本或全部已列子项关闭都不能自动改变上层诉求。

### 证据等级

按实际证据只选择当前最高成立的一档：

```text
尚无实现 → 实现完成 → 当前交付验收 → 样本有效 → 产品采用 → 长期依赖
```

这不是必须逐级推进的流程。每一档需要自己的证据；前一档完成不自动推出后一档。`产品采用` 和 `长期依赖` 需要负责人决定。没有适用证据判断的事项使用 `不适用`，不要伪造数字或精度。

## 六、执行最小远端更新

1. 只修改本次变化要求的条目、关系和字段；不顺手清理其他历史。
2. 创建前搜索语义相同的开放 Issue 和 Project 草稿；优先复用或升级现有候选，避免重复。确需新建时统一应用 `objective-to-issues` 第三节共享创建骨架；本 Skill 不复制标题、label、正文、关系或字段写入规则。
3. 正式父子关系使用 GitHub 原生 sub-issue；正文链接只补充语义。创建关系不授权实施。
4. Project 字段与 Issue 状态可能通过 Workflow 互相影响。对关闭、重开、完成或删除等副作用，在动作前核对授权，在动作后读取远端结果。
5. 如果一次批量写入只部分成功，停止新增写入，先按稳定对象身份与目标值重读远端；列出已存在对象和最小修复，只补缺失步骤，不要盲目重试或制造重复。
6. 需要新的产品决定、范围扩大或明显不同的损失时，合并成一次负责人决定；授权内的客观状态偏差直接修正。

## 七、从远端复核经营视图

更新后至少核对：

- 条目 URL、标题、仓库、Issue 开关状态和 Project 是否正确；
- 父子关系、节点类别和主要父级是否成立；
- 执行状态、诉求状态和证据等级是否各自使用正确；
- `等待负责人` 是否只看见带当前、明确且尚未消费动作的 `待决定`／`验收中`，已消费动作是否在同一维护批次清除；
- `正在处理` 是否只展示就绪、进行中和验收中的真实工作；
- 决定回执中的下一责任人／动作是否与非等待执行状态或获准关闭结果一致；
- 是否发生自动关闭、重开、字段默认值、重复条目或范围外修改。

Project 视图可读不等于状态正确；API 写入成功也不等于真实界面满足负责人阅读需求。只有本次变化涉及视图或可读性时才做界面复核，普通字段更新不重复征收浏览器成本。

## 八、交付并返回原任务

只返回对下一步有用的内容：

- 新增、更新、退出或保留在收件箱的事项；
- 状态和证据为什么改变，以及来源；
- 已验证的远端关系与副作用；
- 仍需负责人决定的单一问题；
- 明确没有自动启动的工作。

把当前目标、授权和下一步写回任务状态；失败、纠正和实验理由进入研发记忆。然后返回原始任务。不要因为总账已更新就自动规划、派发、实施、合并或建设事件入口。
