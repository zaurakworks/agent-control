# PR 整合

把独立交付安全地变成可验收的整合结果，同时保持普通路径轻量。GitHub 保存持久任务与交付状态；本 Skill 只规定整合行为，不提供 Session 编排、锁或自动合并能力。

## 一、确认范围与三种状态

先确定本次对象：仓库、PR、目标分支、关联子 Issue、父 Issue，以及当前任务授予的审查、修复、合并和任务图更新权限。把以下三种状态分开报告：

- **执行完成**：Worker 已交付或 PR 已打开；这只是待核验声明。
- **验收通过**：当前 PR head 的实现与证据满足关联 Issue 和仓库门槛。
- **产品决定成立**：父目标、长期依赖、能力升级或退出等产品判断已经由有权负责人确认；一次合并或试验不能代替该决定。

普通路径只做一次当前状态快照、一次验收判断和必要的合并后复核。只有风险、不确定性、成本或决定价值明显增加时，才路由到 `adaptive-problem-solving`；需要多个 Agent、跨 Session 交接或共享写入协调时，路由到 `orchestrated-collaboration` 与当前任务选择的真实后端，不在这里复制后端命令。

本 Skill 是一段行为，不是驱动者。它**只返回事实与段结果**：验收或合并结束后，把当前 head 的事实交回 `issue-workflow` 由它收口；本段不反向调用驱动者，不自建切片选择循环，也不判定父级或本 Issue 是否完成（第六节）。

### 审查强度按风险分级

| 级别 | 判定信号（命中任一） | 本段需要的动作 |
| --- | --- | --- |
| 轻 | 改动可回退；只写本 Issue 拥有的文件；不改变契约、共享状态和产品边界 | 作者自审 + 可自动化的检查，一次当前-head 快照 |
| 中 | 跨文件或跨模块契约变化；改动共享分支或远端集成目标；其他切片会依赖这次结果 | 加一次针对受影响面的独立检查，可由同批次另一个执行者完成 |
| 重 | 改变方向或问题解释；修改共享状态、权威、入口或用户级配置；难回退或破坏性；涉及产品边界、长期依赖；由多个交付件组成的父目标即将被宣布完成 | 未参与实现的 Agent 做只读复核，并把需要负责人决定的内容合并成一次 |

低风险 PR 不因为“想更稳妥”被拉进重型审查；升级必须指出命中了哪一条具体信号。**进入合并阶段本身不是重风险信号**：每次合并都需要明确授权（第五节），但只有授权缺失、与当前 head 不匹配、需要一次新决定或会扩大授权时才因此升级；有效的条件式预授权已经覆盖当前 head 时，按改动本身的风险分级。全链共用的完整判据在 `issue-workflow`，本节只覆盖整合段，两处分歧时以那张表为准。

已有预授权时不重复索要批准：当前任务或 Issue 合同已经明确覆盖的检查、修复和条件式合并直接执行并记录，只有合同没有覆盖的新决定才升级。这与第五节“合并授权必须明确指向当前 PR”不矛盾——前者禁止重复询问已经给过的授权，后者禁止从无关授权推断出合并权。

## 二、绑定 PR 当前 head

读取 PR 的最新状态并记录：PR 编号、base 分支及其当前 SHA、head 分支、精确 head SHA、是否 Draft、review decision、仍在等待的 review request、required 与 optional checks、冲突与 merge state、顶层与 inline 反馈，以及读取时间。反馈同时标明来自人、bot 还是 GitHub App；来源类型帮助判断语义，不自动决定它是否阻塞。所有 CI、审查、差异和验收结论都必须注明它们覆盖的 head SHA 与 base 上下文。

在作出验收结论、执行合并或发布最终状态前重新读取 head。若 SHA 已变化：

1. 立即废止旧 head 上尚未重放的通过结论和合并动作；
2. 比较变化范围，重新运行受影响的检查并重新处理反馈；
3. 重新确认审查和授权是否明确覆盖新 head；不确定时停止并请求确认。

不要仅凭分支名、最近一次 Worker 报告、PR 页面缓存或旧评论推断当前提交。

若 base 在验收后前进，重新核验合并差异、可合并性和受影响的验证；base 变化不会自动让旧结论继续有效，也不自动要求无关检查全部重跑。

### Draft → ready 的唯一动作与前置门

只有**持有当前 PR 整合写入所有权的本段执行者**可以把 Draft 转为 ready。PR 作者、`issue-delivery` 交付者、只读审查者、协调者或生命周期驱动者的身份都不自动取得这个动作；其他段只能返回事实或请求本段处理。

执行转换前必须同时证明：

1. 关联 Issue 当前、必要，合同明确要求 PR 交付，目标分支和文件所有权无冲突；
2. 已重新读取并记录精确 current head，完整差异与 PR 正文准确对应；
3. 当前 head 所需验证已经通过，失败、运行中、缺失、未配置与未运行项均按仓库门槛得到明确处置；
4. 当前 head 的顶层与 inline 人／bot／GitHub App 反馈已经读取，可执行项已处理，没有未解决阻断；
5. 当前任务或合同明确覆盖“转为 ready”这一远端动作；该授权不等于合并授权。

任一项缺失就保持 Draft，报告缺口与下一责任人；不得用转换动作制造“已经验收”的表象。五项齐全时只转换一次，随后重新读取 Draft 状态、head 与反馈；远端仍为 Draft、head 变化或新反馈出现时，旧转换结论失效并按当前事实重新判定。

### 特性分支更新与冲突处理的安全链

需要把目标分支的新提交带入特性分支时，按顺序执行，不能从中间挑一步：

1. 确认当前 worktree 干净、分支写入所有权覆盖本次历史更新；存在未提交或未跟踪工作时先停止并保全归属，不自动暂存或夹带；
2. 从远端仓库状态动态识别实际默认分支、特性分支 upstream 和承载它们的 remote，不假设名称一定是 `main`、`origin` 或本地同名分支；
3. 先 fetch 相关 remote，再记录更新后的 base、upstream 和远端特性分支 SHA；认证、网络或查询失败时保持状态未知，不用本地旧引用继续；
4. 在合同允许变基时，把当前特性分支 rebase 到已读取的目标分支；逐个理解冲突两侧的合同含义后解决，不用整批 `ours`／`theirs` 或无差别脚本替代判断；
5. 冲突解决后运行与受影响面相称的验证，并重新建立当前-head 验收快照；
6. 只有需要更新**同一条已经推送的特性分支**时，才以刚记录的远端旧 SHA 作 lease 保护更新。lease 拒绝说明远端已变化：立即停止、重新读取远端和所有权，再决定重放或交回；不得改用无保护强推。

普通合并验收不要求为了形式重写分支历史；本链只在确实需要更新特性分支时运行。

## 三、建立最小验收快照

独立读取并交叉核验以下事实，不把作者或 Worker 的摘要当作证据本身：

1. **任务**：关联 Issue 的当前正文、最新决定、验收条件、明确不做事项、文件所有权和父目标；确认 PR 实际链接了正确 Issue。
2. **依赖**：读取 blocked-by、sub-issue 或任务正文声明的依赖，只阻塞真实前置条件。仍在并行推进且与本 PR 独立的兄弟任务不能被默认串行化。
3. **差异与范围**：检查 base 到当前 head 的完整差异、提交和修改文件；确认没有越过 Issue 授予的范围，也没有夹带其他执行者的工作。
4. **工程正确性**：服从仓库规范，并只扫描与差异相关的维度：正确性与边界输入、异步／错误路径、API 与兼容性、测试真实性、IO／数据／迁移、权限／安全／隐私、性能／资源、可维护性。发现按严重度排列并附可定位证据，同级再说明证据确定性；不为低风险改动强制跑完整 rubric。
5. **验证与 CI**：把结果绑定当前 head，分开记录 required 与 optional checks 的通过、失败、运行中、跳过、缺失和未配置；optional 不自动等于可忽略，是否阻塞由仓库与任务门槛决定。没有 required checks 只能记为未配置，不能写成“CI 通过”；认证、网络或查询失败只能记为状态不可取得，不能冒充通过、失败或未配置。验证摘要另列实际运行、未运行及原因、剩余验证缺口与开放问题。
6. **审查与反馈**：分别读取 review decision、仍在等待的 review request、当前 head 的审查，以及顶层和 inline thread 中来自人、bot、GitHub App 的反馈与未解决问题。review request 不等于批准或拒绝，自动化反馈也不因来源被自动忽略；每个可执行项都要有证据支持的处理结果。旧 head 上的批准只有在差异不影响其结论且审查者或当前规则允许时才能复用。
7. **可合并性与授权**：分别确认 Draft、冲突与 merge state、目标分支、仓库合并政策和明确合并授权。Draft 可以形成预验收事实，但在转为 ready 并重新读取以前不能进入合并动作；未知 merge state 不是可合并。

验收所需信息已经清楚时不要强制发布阶段评论、运行固定遍数审查或重复整套规划。只补查会改变本次结论的缺口。

## 四、判定与路由

### 可以验收

只有同时满足以下条件，才把**当前 head** 标为验收通过：

- 关联 Issue 仍必要、当前且范围清楚；
- 所有真实前置依赖已满足，或明确不阻塞本 PR；
- 完整差异符合文件所有权、验收条件和明确不做事项；
- 当前 head 的必要验证已通过，缺失或未配置的 CI 已如实记录；
- 可执行反馈已处理，剩余内容被明确判为非阻塞并保留理由；
- PR 若仍为 Draft 只标为预验收；正式验收通过时它已经转为 ready 并重新读取；
- PR 可合并，且没有未解决的权限、风险或事实冲突。

记录通过的 SHA 和证据。PR 已打开、Worker 已发送完成、子 Issue 被关闭、检查曾在旧 SHA 通过，都不能单独满足这些条件。

### 需要修复

列出阻断、证据和再次验收范围，并明确指定新的写入所有者。只读审查、Worker 报告接收者或协调者身份都不自动授予修复权限；原所有者是否继续也由当前任务合同或协调者明确决定。保持审查者只读时，把修复派给已有写入者或一个新获得互斥范围的执行者。

### 必须停止或升级

遇到以下任一情况时，不合并并请求相应决定：

- head 在验收或授权后变化，且新提交没有获得覆盖；
- 关联 Issue、依赖、验收门、目标分支或文件所有权含糊或冲突；
- CI 失败、仍在运行、来源不可信，或任务要求的检查无法取得；
- 有未解决的 actionable feedback、合并冲突或未知高损失风险；
- 只有普通的“继续”“同意”、旧任务授权或自动化默认值，没有针对本 PR 的明确合并授权；
- 下一步会改变父目标、长期依赖、产品边界或升级投入。

## 五、只在明确授权后合并

合并授权必须能够明确指向当前 PR，且在最终检查时仍有效。若授权绑定某个 SHA，head 变化后必须重新授权；若授权明确采用“满足列出的当前-head 门槛后即可合并”的条件式表达，则严格按其范围执行。不要把 review approval、CI 通过、issue closure、Worker 完成或创建 PR 的授权解释为合并授权。

执行合并前最后一次刷新并确认：

1. head SHA 与验收记录一致；
2. required 与 optional checks 的精确状态仍满足门槛；没有 required checks 时仍记为未配置，查询失败时停止为未知；
3. review decision、review request、顶层和 inline 的人／bot／GitHub App 反馈没有新增阻断；
4. PR 已离开 Draft，冲突与 merge state 显示仍可合并，base 与合并方式符合授权和仓库规则；
5. 明确授权仍覆盖这个 PR、这个 head 和这次动作。

任一条件不成立就停止，不尝试用自动修复、强制更新、管理员绕过或替代合并方式扩大授权。

## 六、合并后确认事实，然后交回驱动者

合并返回成功不等于整合完成。重新读取远端事实并记录实际合并提交、目标分支和时间，然后：

1. 确认已验收的 head 确实进入目标分支；
2. 按当前任务规则更新本 PR、关联 Issue 和被解除的依赖，保留失败、跳过、未配置检查与剩余项；
3. 把这批**事实**交回驱动者：实际合并提交、目标分支与时间、关联 Issue 的当前状态、父级关系是否存在、被解除的依赖、仍然阻塞的项、失败与剩余项，以及“当前是否还有可执行子项”这一事实本身。

### 合并后的默认分支维护

当前任务拥有本地分支维护范围时，先确认 worktree 干净，再动态识别远端默认分支、它的 upstream 与 remote 并 fetch；本地默认分支只做 fast-forward 同步，不用 rebase、reset 或强推掩盖分叉。同步后复核本地实际 commit 与远端默认分支一致，并确认远端记录的合并提交或已验收 head 可从该 commit 到达。不能 fast-forward、查询失败或本地分支另有所有者时，保留现场并报告，不把本地未同步写成远端整合失败，也不自动删除特性分支。

**本段不判定任何对象是否完成。** 逐条对成功条件找证据、确定回收对象（有父级时是父级，没有父级时是本 Issue 自己）、决定关闭、继续下一切片、报告阻塞还是请求决定，这些都只由 `issue-workflow` 的回收一节作出。本段自行重做一遍，就会在驱动者之外形成第二套完成状态机——它们迟早给出不同结论。

没有驱动者而本段被直接调用时，同样不要就地决定：如实报告上述事实并停止，明确说明状态判定尚未作出、应由谁作出。

子项列表为空、全部子 Issue 已关闭、子 PR 已合并、Worker 已发送完成回执、检查曾在旧 head 通过——这些都是事实，不是完成结论；照实交回，不要用它们推断完成。

子 PR 合并只能证明该交付进入目标分支，不能自动证明父目标完成，也不能证明 GitHub、Orca、某个 Plugin 或某套流程应成为永久产品选择。

## 七、交付可恢复的整合记录

最终记录至少包括：

- PR、base 上下文、已验收 head SHA，以及合并后的 commit（若已合并）；
- 关联 Issue、父 Issue 和真实依赖的状态；
- 当前 head 的差异范围、相关正确性维度、验证／CI、审查和反馈处置；
- 实际运行、未运行及原因、剩余验证缺口和开放问题；
- 验收结论、明确合并授权来源及其覆盖范围；
- 执行完成、验收通过和产品决定三种状态各自的结论；
- 修复所有者、失败、非预期副作用、仍未知内容和下一步。

只记录足以恢复和复核的摘要与链接，不复制完整终端输出，也不把运行后端状态伪装成 GitHub 的持久任务事实。
