# 生命周期收口与负责人动作投影

评论／证据、正文、PR、决定、来源状态迁移或关闭候选出现后，任何来源 Issue、父级证据或 Project 写入以前都必须完整读取本文。本文是生命周期事件批次、负责人动作、单写者、固定顺序、失败重入、关闭前蒸馏和关闭出口的唯一规范正文；`issue-workflow` 核心只保留判定权与触发，`operating-ledger-maintenance` 只补 Project 适配。

## 职责与输入

**生命周期判断只属 `issue-workflow`。** 它提供已远端核验的来源事实身份、生命周期意图、来源目标、当前负责人动作、下一责任人／动作、父级或顶层叶子证据、需要时的 Project 目标与关闭授权。`operating-ledger-maintenance` 不重判模式、成功条件或收口；决定消费仍先由 `issue-workflow` 绑定可信主体并解析，具体规则在 [`owner-decision-protocol.md`](./owner-decision-protocol.md)。

评论／证据、正文、PR、决定与来源状态迁移均进入本段，不以执行者是否继续为条件。事件只认远端回读的评论 URL／节点、新正文版本与恢复快照、PR 当前 head 或进入目标分支的提交、稳定决定回执、来源状态目标值；`worker_done`、本地检查、资源状态和工具回执只触发核验。事实不可得时保持未知并停写。

#### 等待负责人只投影当前未消费动作

“等待负责人”只是远端经营观察面的投影，不是可以长期滞留的来源状态。向 `operating-ledger-maintenance` 提供等待事实以前，必须从远端同时证明负责人动作：

1. **当前**：请求仍适用于当前 Issue、证据与范围，没有被后续决定、纠正、关闭或范围变化替代；
2. **明确**：有稳定决定编号、一个可直接回答的负责人动作、已知边界和最短回复；“请看看”“后续确认”或一般性背景不算明确动作；
3. **尚未消费**：没有已生效且未被纠正的决定回执，也没有完成该动作的其他可核验远端事实。

只有三项同时成立才写入等待状态，并输出一个当前负责人动作，在 Issue 中保存动作编号、所需回复和来源；同时注明它是尚未作出的决定，还是已有证据后的接受／否决动作。Issue 仍然开放、曾经请求过决定、已有证据、有人留下问题或 Project 旧字段仍为等待，都不能单独产生“等待负责人”事实。仍有另一个合格动作时可以保留等待，但必须把观察面改指向那个未消费动作，不能继续沿用已经消费的旧请求。

Project 字段取值与观察面维护全部交给 `operating-ledger-maintenance`；`issue-workflow` 只提供当前负责人动作、决定回执、下一责任人／动作与回收事实，不枚举或写入 Project 字段值，也不把观察面变成第二套状态机。

#### 消费决定沿用通用收口

无歧义决定的回执、消费、清除旧等待与回收是**同一个可重入的收口动作**：核对单一回执并标记编号已消费；重列负责人动作，交付“空”或下一稳定编号、类型与回复；写明**下一责任人**、**下一动作**及是否领取。`issue-workflow` 不选择 Project 字段值。

随即进入第九节。成功条件与关闭授权均满足时同事件执行；只缺关闭授权时创建稳定请求并作为当前负责人动作，不能先输出“空”。已有回执沿原事件补缺，不重复询问或消费。

### 生命周期事件的同批次收口

恢复定位符使用“来源 Issue 身份＋已核验来源事实身份＋生命周期意图＋需要时的 Project item 身份”并保存目标值，写入现有单一回执；它只定位同一事件，不新增状态、编号、字段、登记表或回执。

每个事件只有一个远端执行者：不投影 Project 时为当前 `issue-workflow` 驱动 Session；需要投影时为同一 Session 的 `operating-ledger-maintenance` 段，并由该段持有四面写入所有权。唯一执行者独占四面，不能分给不同 Skill 段或 Session；所有权不全则整体交给合格驱动者，不拆段。

唯一执行者先按原定位符回读已落盘步骤，再固定执行**来源事实 → 下一责任人／动作 → 父级证据（顶层叶子为自身证据）→ Project 投影 → 四面回读**；事件不涉及 Project 时，该步没有目标值且不产生写入。四面是来源事实与 Issue 生命周期、负责人动作与下一交接、回收对象成功条件证据、Project 状态与等待投影；Project 必须等前三面确认。进入写入前按同一定位符执行：

1. **写前四面重读**：读取来源事实与 Issue 状态、单一回执中的负责人动作和下一交接、父级或顶层叶子证据、Project item 与字段值，识别已经落盘的步骤；
2. **来源事实在先**：核对或持久化来源事实，再在同一回执写入**下一责任人**、**下一动作**及是否已领取。决定已消费时不得继续投影旧动作；成功条件和关闭授权覆盖时按 `issue-workflow` 目标更新来源状态，只有关闭授权缺失时保持来源开放并维持同批次稳定关闭请求；
3. **父级证据随后**：按 `issue-workflow` 已给出的逐条判定向回收对象写入最小增量证据：每个相关子项只保留稳定链接、已远端核验的当前状态、证据等级、`conditionId` 与 `sourceFactId` 的对应关系和足以判断成功条件的一句话结论（未知即标未知，只有来源已经进入终局时才写成终局状态），合同目标 Issue 已有的正文、逐步过程、完整证据表或交付性长文只链接、不跨 Issue 复制；顶层叶子写入自身证据，不从 Project 局部事实推导完成状态；
4. **Project 投影最后**：前三面均经远端回读确认后，重新枚举合格负责人动作。没有剩余动作时清除旧等待；仍有动作时只指向新的稳定编号。按下一真实责任投影：未领取的执行者动作 → `就绪`；已领取、正在实施或内部核验 → `进行中`；来源已按授权关闭 → `完成`；只有新负责人动作通过三项门才使用 `待决定`／`验收中`。若唯一缺口是关闭授权，使用同一收口的稳定请求，不得先投影成非等待状态；
5. **四面回读与单一回执**：重新读取来源事实与 Issue 生命周期、负责人动作与下一交接、父级／自身证据、Project 状态与等待投影，逐项核对目标值和授权边界；把实际后态、缺失步骤和定位符写回同一交付／决定／收口回执，已有回执只更新这一条。

任一步骤失败即停写并保留已落盘事实，在同一回执记录实际后态与缺段。重入先按原定位符回读四面，只补确实缺失的步骤；也就是只补远端确实缺失的步骤，不能凭本地回执猜测。来源事实、动作消费、父级证据、Project item 与回执均不得重复，状态不可得时保持未知并只读查证。四面一致前不生成下一事件或重复负责人请求，也不称系统已经收口。这个通用批次置换决定专用的“来源在先、Project 随后、双对象重读”清单，不新增 Project 字段，也不改变 `issue-workflow` 的唯一生命周期决定权。

## 先确定回收对象

**不预设一定有父级。** 没有未完成子 Issue 的叶子可能挂在父级下，也可能本身就是顶层 Issue：

- 本 Issue **有父级** → 回收对象是父级的成功条件；
- 本 Issue **没有父级**（顶层叶子）→ 回收对象是它自己的成功条件。

两种情况用同一套步骤，只是对象不同。没有父级不是跳过回收的理由——它只是把回收对象换成本 Issue 自己。

## 回收步骤

用远端事实而不是本地印象：

1. 确认这次结果确实进入了目标分支；有父级时同时确认它进入了父级子图；
2. 更新本 Issue、相关 PR、被解除的依赖和仍然阻塞的项；
3. **对回收对象的每一条成功条件重新找证据**，逐条标为已满足、未满足、被阻塞或需要负责人决定；
4. 检查逐项关闭授权；没有逐项授权时，检查下面的三条件预授权谓词；
5. 只有证据和授权已经把本次动作导向关闭时，执行下面的关闭前蒸馏检查；
6. 按下面五种情况之一收口。

### 关闭前蒸馏检查

这一步只在 Issue 即将关闭时运行，目标是避免评论里的可复用结论随收口被遗漏；它不是新的知识准入门，也不要求尚未满足成功条件的 Issue 反复扫描。

1. 浏览本 Issue 当前评论与交付证据，寻找值得交给知识流程复核的候选：可跨任务复用的事实结论、已经验证的工具或环境行为、反复适用的失败教训，以及需要长期解释重要决定的理由。只判断“是否值得过门”，不在这里判定它已经可信或应该进入知识库。
2. 没有候选时，在收口回执记为“本次未发现知识候选”并继续；这只证明检查做过，不证明未来不会从同一材料形成新结论。
3. 有候选时，至少登记候选结论、来源评论链接、适用范围、当前核验等级和仍未知内容，再交给 `knowledge-maintenance`。由它逐条执行价值门与可信门，并给出进入当前知识、保留为任务证据或待授权候选等去向；本文不复制两道门，也不自行写入知识。
4. 候选及其可恢复去向记录成功后即可继续关闭；知识条目尚未获准写入不把本 Issue 变成等待知识验收的长期阻塞。若候选已经发现却无法登记任何可恢复去向，停止关闭并报告缺失的载体或授权——“先登记候选再关闭”只要求不遗漏，不把候选伪装成已准入知识。

检查结果为“本次未发现知识候选”或候选已经取得可恢复去向时，蒸馏检查才算完成并进入关闭；候选登记未完成时进入停止，不允许绕过本节直接关闭。

### 三条件关闭预授权谓词

负责人已经预授权任何持有当前 Issue 合同的 Session 在以下三项**全部成立**时直接关闭回收对象，不再逐次请求关闭授权：

1. **成功条件有证据**：每条成功条件都有远端可核验证据满足，悬置项也已按既定程序收口为显式结论；
2. **没有未收口关系**：没有未消费的负责人动作、开放子项或被依赖的开放事项；
3. **对象属于允许类型**：对象是交付、实验或摩擦类条目；目标与诉求层、父目标、产品取舍或授权边界类 Issue 明确排除，仍需负责人决定。

谓词成立时，关闭动作必须附一条收口回执，逐条列出合同满足证据，并把 [关联 agent-control#44（规则只加不减的收敛实施）规则回执](https://github.com/Eridanus117/agent-control/issues/44#issuecomment-5255408590) 作为授权来源。拿不准对象类型、关系或证据是否落入边界时，按未满足谓词处理并走现有决定请求。本谓词不是开放授权，不扩大产品决定、合并、安装、删除、宿主环境或其他动作的授权；边界排除对象与任一条件不成立的对象保留原路径。

| 情况 | 动作 |
| --- | --- |
| 全部成功条件已满足，且已有逐项关闭授权或满足三条件预授权谓词 | 按覆盖本次动作的授权关闭回收对象，并留下逐条证据与授权来源回执 |
| **全部成功条件已满足，但既无逐项关闭授权也不满足三条件预授权谓词** | **明确停止**：报告逐条证据、说明关闭权归谁，并在同一次收口按第八节创建一个带稳定编号的关闭授权请求，作为当前未消费负责人动作交给 `operating-ledger-maintenance`；不自行关闭 |
| 有未满足条件，且存在可执行的下一切片 | 回到第六节继续推进 |
| **没有可执行子项，但成功条件未满足** | 先判断缺的是“切片没建”“依赖没解”还是“需要负责人决定”，然后分别补规划、报告阻塞或提出一次决定 |
| 证据不足以判断 | 如实报告不确定和缺什么证据 |

顶层叶子最常落在前两行：它没有子项，因此“回到第六节”和“补切片”通常不适用，收口只可能是按授权关闭、明确停止请求关闭，或报告未满足的条件。这条出口必须存在——否则一个独立叶子在获准合并后就没有终点。

**明确禁止**：子项列表为空、子 PR 已合并、Worker 已发送完成回执、子 Issue 已关闭、检查曾在旧 head 通过——这些都不能单独证明回收对象的成功条件已满足。

历史动机、事故反例与被替代做法统一见 [关联 agent-control#178（规则与 Skill 体系复杂度收敛）调研交付](https://github.com/Eridanus117/agent-control/issues/178#issuecomment-5267420521)。
