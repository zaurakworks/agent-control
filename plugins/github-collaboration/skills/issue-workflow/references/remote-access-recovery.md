# 远端访问语义与异常恢复

只在 `issue-workflow` 核心的三条远端选择规则不足以继续时读取：候选失败、所需语义变化、认证或写权限不明、或者所有候选都缺少一项必要语义。本节只决定**用什么读写远端**，不决定模式、切片顺序、回收对象或收口结论。

## 先核对所需语义

先确定这次真正需要哪些 GitHub 语义，再在当前 Session 实际可用且已认证的能力里选择能表达它们的候选：

| 本次需要的语义 | 选择时要确认的事 |
| --- | --- |
| 正文、评论、状态 | 能读到当前值，而不是缓存或转述 |
| 原生父／子与依赖关系 | 能读到**原生关系本身**；正文里的链接、清单或勾选框不是它 |
| PR 的当前 head、检查与审查 | 结果能绑定当前 head，而不是旧提交上的结论 |
| 写回（评论、正文、状态、PR） | 确实具备写权限，而不是只读能力 |

所需语义在推进中会变，例如从只读恢复进入写回，或进入审查需要当前 head。语义变化后按核心三条规则重新选择，不假设开局那个候选一直够用。

## 禁止降级与精确停写

命中任何一条都说明选择已经跑偏：

- 为了让某个候选可用就安装工具、修改 `PATH`、读取或写入凭据、改动用户级配置；这些是负责人的决定，不是恢复动作；
- 降级到未认证的抓取或公开页面解析，来代替已认证能力；
- 把只读能力当成可写用，或在写入没有真正成功时把结果说成已经写回；
- 把正文里的链接冒充原生父／子关系；
- 因为一个客户端缺失就宣布远端不可用，或反过来因为某个客户端可用就假设它具备本次所需的全部语义和权限。

一个候选失败时，先按核心规则改用另一个已认证且语义匹配的候选。只有全部候选都不能表达某项必要语义时才停止受影响路径：合并报告缺的是哪项语义、试过哪些候选、哪些读或写因此停住；其余有独立合同和所有权的路径继续。接口变化时重新读取对应工具的当前指南，不在 Skill 中保存命令清单，也不把本次可用候选固化为长期依赖。
