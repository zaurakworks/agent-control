# 受控协作

通过清晰分工增加执行容量，同时让协调成本、冲突和返工低于并行带来的收益。Skill 规定协作行为；通信、终端、任务状态和进程生命周期由真实工具提供。

## 零、共享写入先确定所有权

这一步用于防止多个 Session 在尚未建立协作关系时直接碰撞，不代表自动开始并行。

“共享单点”的唯一规范源是 `agent-control/authority/04-collaboration.md` 的“共享单点清单的唯一权威外延”。本节适用该规范源定义的完整六类，不在 Skill 中复列、合并、改名或增加第七类；判断对象是否属于某一类时回到规范源，而不是从本节措辞推导新外延。

阶段首次修改规范六类中的共享状态前，确认 Session 已有写入所有权。任务或有效 Dispatch 已给出互不重叠范围时继续且不重复检查；否则：

1. 保持相关范围只读，查看当前后端中仍在线的 Session、协调者和任务；
2. 只有“协调者仍在线”和“Run／任务合同明确覆盖该资源”同时成立，才把它视为有效占用；只有终端、旧 Run 或已完成任务不能单独证明所有权；
3. 已有其他协调者占用重叠范围时，加入该协调、取得明确分区，或保持只读；不要创建竞争 Run；
4. 没有重叠占用且任务允许写入时，当前 Session 可成为唯一协调者，并在当前任务和真实后端公布范围；
5. 公布后、首次写入前再检查一次。若近同时出现多个重叠声明，以较早建立且仍在线的协调者为准，其他 Session 退回只读并通知协调者。

Git worktree 只隔离工作目录中的文件。它不自动授予共享分支推送、当前任务、权威、用户级配置、Plugin 安装或 Orca 状态的写入权。

Orca 不可用或任务未选持久后端时，用当前任务文件明确一个写入者；其他 Session 只读或做完全隔离的工作。无法判断所有权时改为单 Session 或请求负责人决定。

## 一、人工选形态并判断是否进入协作

按已有授权人工、按需、可降级选形态；按需读[八卡索引](./references/collaboration-shapes/INDEX.md)，不自动选型。四条规则置换旧进入门：

1. **五项输入**：触发协作时核对工作图、写入可分性、独立上下文价值、风险／授权与净收益；不清先界定。
2. **一层拓扑**：直线 CF-0／1，无依赖 CF-2，递归／自治子树 CF-3／4；同层唯一，不可分则单写者。
3. **按需叠加**：高影响模型 CF-5；CF-6 先完整读取 `adaptive-problem-solving` 的 `references/pre-action-gates.md` 并取得 G3 合格结果；阶段依赖 CF-7。均不新增授权或伪造串行。
4. **CF-0 退出**：单一低风险、无需独立上下文或净收益不正即走普通路径；复杂、额度、空闲不构成理由。

碰撞时冻结重叠写入并只读盘点，不得各方同时回退、修复或提交。冻结按范围而不是按批次：只停冲突、依赖被推翻假设或会发布受影响结论的路径；有独立合同、所有权且结论不依赖该假设的路径继续。仅全局不变量、授权或共享一致性受损才整批冻结；停掉独立安全工作本身也是损失。

## 二、恢复当前目标和授权

按当前项目入口读取唯一活动任务和它明确链接的权威。开始派工前分开记录：

1. 用户要达到的结果和验收条件；
2. 用户明确提出的限制；
3. 当前权威、工具事实或高损失风险带来的必要约束，并注明来源；
4. Agent 为实现方便或保守而提出的假设、方案和偏好。

第四类不能静默升级成用户需求。发现新信息时，先判断它是否真的妨碍用户目标；不要仅因违反了 Agent 自加约束就启动恢复工作。

普通的“继续”不恢复已暂停事项，也不扩大协作范围。需要用户决定时，把会改变结果的选择合并成一次问询。

## 三、选择真实协调后端

本 Skill 不决定系统长期依赖哪个协调产品。当前任务没有选择后端时，先比较已经可用的真实能力、协调收益、切换和维护成本；需要新的产品决定时，提出一次最小选择。不要因为某个工具成熟就自动长期依赖，也不要因为希望可控就自动 Fork 或自建。

### 当前任务选择 Orca 时

Orca TUI 是观察面，`orca orchestration` 才是执行事实与协调后端。

任务已选 Orca，且需协调 Session、任务来源、交付或共享写入所有权时：

1. 派工前动态读取 `orca skills get orchestration --full`；
2. 直接控制终端或 worktree 时再读对应指南；只保留发现入口，不复制动态命令；
3. 创建或绑定 Run；继任前先读取[K12（协调者压缩存续与继任协议）](https://github.com/zaurakworks/agent-control/blob/main/knowledge/coordinator-succession-protocol.md)并通过双协调停止门，同一目标不建竞争 Run；
4. 使用当前指南的 Task、Dispatch、Delivery 与生命周期合同；
5. 保存 Run、Task、Dispatch、执行者和交付标识，不把其他工具冒称为 Orca；
6. 冲突时工具合同管命令与生命周期，本 Skill 管目标、授权、拆分、验收与综合。

不复制动态命令；CLI 变化即重读指南。

Orca 的当前能力与本机样本只用于以后比较“直接依赖、Fork／维护、自建或更换”，不代替负责人作长期决定。

### Orca 运行面：TUI 是观察面，`orca orchestration` 是执行事实与协调后端

**Orca TUI 是观察面。** 它让负责人看到终端、输出和输入，也可以帮助选择现有浮动终端；但它不承载协调状态，也不是编排协议，不能单独解决并发和恢复。

**`orca orchestration` 是执行事实与协调后端。** Run、Task、Dispatch、持久消息和交付来源链的执行事实以它为准，不以 TUI 上看到的画面为准；判断一次派发是否真的存在、是否已经完成、交付归谁，都读它而不是看界面。

### 当前任务选择其他后端或 Orca 不可用时

- 同一根任务内的原生子 Agent 可以使用其真实协作工具，但要如实记录后端，不能称为 Orca；
- 跨 Session 没有持久协调后端时，只派发只读或完全隔离的工作，或者明确一个写入者和互不重叠的工作树；
- 用当前任务文件记录临时所有权和交接，但明确它不提供实时消息、执行者生命周期或交付确认；
- 无法建立可靠隔离时停止并改为单 Session。

## 四、建立唯一协调者和写入所有权

“唯一”按共享资源和任务子树成立，并非全系统唯一。Session 可协调自己的子树，也可执行另一子树；角色由任务合同和写入所有权决定，不由供应商、终端或固定身份决定。

无需永久中央协调者：每项共享资源有唯一写入者、每棵子树有一个当前驱动者即可。子树驱动者由当前任务合同和写入所有权确定；本 Skill 只管跨 Session 所有权、派发、通信与验收，不接管 Issue 生命周期。

共享范围设协调者：

- 维护目标、授权与任务图；
- 拥有共享任务状态、权威、整合文件和共享分支的最终 Git 提交／推送；隔离 worktree 或独立仓只有在任务合同明确分配时才由执行者提交，任何两个执行者都不能推送同一分支；
- 处理冲突、决定、交付与综合；
- 独立核验执行者报告，不把 `worker_done` 当成自动验收。

执行者获得互不重叠的写入范围；不可分区域只允许一个写入者，其余只读。发现未提交改动先识别归属，不回退、不覆盖、不纳入自己的提交。

### 资源投入派发门（R1–R6）

唯一原则源是 [`authority/05`](https://github.com/zaurakworks/agent-control/blob/main/authority/05-resource-operations.md)“资源投入原则”；这里只投影动作顺序，不复制证据历史或动态阈值，不用额度或空闲 Agent 绕门。

1. **R1｜价值门。** 须有授权、稳定交付、独立验收，且无额度期限也值得完成、价值高于总成本；否则留在队列外，不为并发数或消耗比例造任务、拆单。
2. **R2｜就绪队列与排他所有权。** 只计依赖已解、无需猜偏好、互无依赖且写入排他的候选；执行者不超过此可并行深度。交付后扫描新解锁项，但扫描解锁不扩大授权。
3. **R3｜资源新鲜度。** 额度会改变排序时，先证明 Provider 正常、窗口一致且采集时间前进；否则保持未知并撤销额度扩产理由，不妨碍合同支持的工作。
4. **R4｜额度只作加速条件。** 先按父目标、可执行性与 Provider 适配排序，最后才用临期额度区分同价值候选；Issue、Session、Token 或利用率不单独触发派发，并保留协调验收余量。
5. **R5｜验收容量与实验干扰。** 加派不超过验收整合容量，不破坏实验并发／隔离门、顺序、审查独立性或负责人决定；碰撞、失败、返工或注意力成本上升时维持或停止新增派发。
6. **R6｜加派、维持或减派。** 有真实任务、排他所有权、验收余量且能缩短关键路径，或新鲜读数支持同价值任务时加派；任务均已领取或增员只添成本时维持；队列空、瓶颈转移、实验需保护或唯一理由是未知额度时停止新增派发。只在任务、队列／所有权、负责人、资源、实验或质量事件变化时复核，不建设固定轮询或自动调度。

R1–R6 置换原三条散规则，保留解锁、非伪串行与不凑数语义。无决策价值、记录过重或诱发质量反噬时退回逐案判断；退出不产生撤销合同、中止 Session、自动消费权益或其他破坏性权限。

## 五、用派发合同骨架把子任务写成可执行合同

派发前先从远端任务合同恢复当前正文、状态、原生关系、仍有效的评论决定、授权和成功条件；运行期消息、本地摘要与协调者记忆只帮助定位，不能代替远端合同。

### 类型化放置合同

Task 创建前核对五字段并原样送入 Worker：

- `contractRepo`：合同仓库身份、Issue 编号、原生父级及建项前冻结的期望 Issue 标题／语义标识；
- `executionRepo`：实际读写／推送的仓库身份；
- `worktree`：精确身份、路径、分支与基线；
- `ownedPaths`：排他可写的非空路径／资源集；
- `delivery`：唯一适配器、目标对象与完成判据。

重读并断言 Issue 编号／原生父级／授权存在，`executionRepo` 与 `worktree` 归属一致，`ownedPaths` 属于该仓且无活动重叠，`delivery` 唯一且相容。Issue 编号、父级、唯一交付形态或五字段任一缺失、歧义、冲突即停止创建 Task；跨仓边界不清则拆分或升级，不猜落点。

合同含目标／来源／阶段、必读证据、范围／不做事项／允许操作、硬约束与停止／升级路径，以及唯一交付物、可独立核验的产物判据和验收条件；负责人面用信达雅专业中文，Issue／PR／决定编号首次出现附对象标题压缩的中文短题；禁用全部 GitHub 关闭关键词及其否定式。完成汇报先用三句执行摘要依次说明做了什么、发现什么、还剩什么；再列修改、检查、失败、未运行、副作用、缺口与稳定链接。

硬约束有缺或冲突，只冻结受影响路径并升级。只保存跨后端稳定语义，不把协调工具版本命令写进合同；仅派发独立、所有权排他的任务。

## 六、派发前后都核对状态

输入前核对 Run／协调者、执行者、Task 就绪和所有权；派发后重读活动 Dispatch 并核对 Task、执行者与合同身份。活动 Dispatch 缺一即停；接口回执不替代，也不另建 Dispatch 猜测恢复。

### 派发落点核对与提交恢复

派发接口返回 `input_accepted` 只证明输入被接收，不证明任务已经提交给 Agent；即 `input_accepted` ≠ 已提交。按同一 Dispatch 核对 Task、执行者、五字段，再确认终端标题与目标 Agent／任务相符、实际 `executionRepo`／`worktree` 符合合同、任务正文已经离开待输入状态并出现提交后活动；标题和路径不能替代稳定身份。

正文仍在输入区或无提交后活动时，只对原派发补发一次提交动作（例如语义上的回车）并重读；在核清原派发以前不创建第二个 Task、Dispatch 或执行者。落错或补交仍无活动即停。

Worker 启动后以自身 Task／Dispatch 重读同一 Dispatch，把实际仓库、worktree、路径所有权和交付目标对照五字段；不符即停文件与远端写入，报告合同值、实际值和稳定身份。心跳不证明落点或结果正确。

### 远端写入报错后的核验与恢复

任何远端写入都以回读后态为准；成功回执同样不能代替远端复核。GitHub 瞬时错误或 EOF 可能呈现两种远端事实：未写入，或调用报错但写入已经落盘，故须**先核验再重试**：沿原事件／决定编号、对象身份与目标值重读，以稳定对象身份、目标值、事件或当前 head 判断原动作是否已经生效。

创建 Issue 后回读实际标题，与 `contractRepo` 冻结值断言；不符即停，终端标题不能替代。已生效则继续且不重复写；远端证明确实缺少时，才沿原身份幂等补齐并再回读；状态仍不可取得则保留“未知”，停写并沿原身份只读查证。回执不允许换新 Issue、PR、评论、Dispatch 或决定编号“重试”。

## 七、破坏性操作先核验工具语义

删除、移动、重写 Git、修改配置、远端或权限前：解析精确对象并确认授权；只读记录前态；核对连带变化；优先更窄、可恢复的动作；完成后复核验收与安全条件。出现副作用时，只对破坏用户目标、明确限制或有来源约束的结果恢复；若只违反 Agent 自加假设，保留观察并交协调者判断。

## 八、处理交付并独立验收

收到交付后：

1. 在确认前完整处理当前交付批次，避免丢失可重放消息；
2. 核对执行者声明的范围、文件、结果、失败、副作用和剩余项；
3. 运行与风险相称的独立检查，尤其检查共享状态、Git、权限和删除结果；
4. 区分“执行完成”“验收通过”“产品决定成立”；三者不能互相替代，更细的证据等级由 `adaptive-problem-solving` 判定；
5. 交付可能改变 Issue 生命周期时，不论是否复用同一执行者，`worker_done` 只触发远端来源核验；把稳定来源身份、定位符和交接事实返回当前合同持有者。只有当前合同或负责人明确授权相应动作时，合同持有者才可续派、结束或变更远端生命周期；否则只报告证据。

执行者报告不自动成为结论；分歧保留双方证据与取舍。

### 低层派发完成后的资源收口

优先使用当前协调后端提供的高层受监督生命周期；只有高层能力不适用或不可达，且当前合同允许低层路径时，才由协调者显式承担终端与 worktree 的生命周期。现场出现过的失败状态只作为观察事实，不固化为工具合同。

低层路径的完成通知只证明执行者已经报告交付，不代表资源生命周期已经结束。协调者先按动态读取的当前指南尝试标准释放并读取完整回执，再用三个判据逐个处置相关对象：对象是否被回执覆盖并确认释放、回执是否要求必须执行的恢复动作、四项证明是否齐全。判据按对象成立而不是给整次释放贴一个类别，同一份回执里的不同对象可以落到不同处置，因此下面的分类不声称互斥或穷尽。

- **回执覆盖并确认已释放的对象**：资源生命周期已经结束，记录结果即可，不需要显式收口；不得把回执未覆盖的对象一并宣称为已经清理。
- **回执要求恢复动作的对象**：结果待定、未知，或以其他方式要求后续动作时，必须按回执给出的恢复动作处理，并保留对象直到恢复完成；不得用显式关闭或删除替代回执要求的恢复动作，也不得强制删除。
- **其余需要协调者处置的对象**：包括标准释放成功但未覆盖的 worktree、回执说明因预先存在或复用等文档化原因而保留的终端，以及标准释放不适用、或返回未文档结果且没有要求任何恢复动作的对象。只有下面四项证明同时齐全，才可以进入显式资源收口；任一证明缺失就保留对象，记录缺少的证明和下一责任人。

当前指南的标准释放可能只结束终端而从不删除 worktree，因此“释放成功但 worktree 未被覆盖”是常态而不是例外；这类残留 worktree 按上面第三类处置，在四项证明齐全时才可以显式删除。未文档的失败结果只作为现场观察记录，不写成工具合同，也不因为它未被记载就免除恢复动作或四项证明。

显式资源收口前必须同时证明：

- **远端持久化**：交付已进入远端，提交或 PR 的当前 head 可精确定位；若命中 Issue 生命周期事件，还须有来源事实身份、原定位符与下一责任人／动作；
- **干净工作树**：对应 worktree 没有未提交、未跟踪或其他尚未持久化的文件；
- **唯一精确身份**：Dispatch、整个终端 tab 与 worktree 的稳定身份能够唯一对应；短名称只能帮助辨认，不能替代精确身份；
- **删除连带影响**：已经核对关闭整个 tab 对其中其他 pane／进程的影响，以及删除 worktree 时归档 Hook 是否会被跳过等当前指南记录的副作用。

四项证明齐全后，精确关闭整个终端 tab、删除对应 worktree，再重新读取终端与 worktree 列表，确认目标对象已经消失且无范围外资源受影响；全程不得使用强制删除。Task、worktree 和终端使用简短、可辨认的中文显示名或注释，但资源选择仍以稳定且唯一的精确身份为准。

### 高价值父目标需要另一个 Agent 只读复核

协调者参与目标拆分或方案设计时，其验收只能证明计划被执行，不能独立证明没有遗漏；子 PR 审查也不能替代父目标复核。

同时满足以下条件时，在综合和宣布完成前安排一次父目标级只读复核：

- 交付对象是 Agent 系统能力或工作流替代，会改变长期行为；
- 父目标由多个 PR 或多个交付件组成；
- 当前协调者参与了目标拆分或方案设计。

复核者必须未参与拆分和实现，至少检查父目标贡献、基线与被替代方案的能力回退、当前证据等级、负责人可见 ROI，以及完成结论是否符合证据；详细判据与缺口分类由 `adaptive-problem-solving` 的阶段结束与最终验收检查提供，本 Skill 不重复。

复核者只读：不修改交付、不推送分支、不合并，也不代替负责人作产品决定。它的结论是协调者综合的输入；授权内的客观缺口按 `adaptive-problem-solving` 判定 `revise` 并修正，产品取舍、风险偏好和扩大授权仍合并成一次负责人决定。

普通单 PR、低风险、容易回退的任务不强制增加这一层。派发复核者仍使用当前任务已经选择的真实后端和第五节的子任务合同；不新建审查平台、评分系统或常驻审查角色，也不因为一次复核有效就把它升级成长期依赖决定。

## 九、综合而不是堆叠报告

最终交付应让负责人容易复查，至少包括：

- 用户目标和实际完成结果；
- 使用的协调后端以及 Run／Task／Dispatch 等来源标识；
- 执行者、职责和写入所有权；
- 被采纳、拒绝和仍有分歧的结论及理由；
- 独立验收结果，以及父目标级复核（如果适用）的结论和处理方式；
- 非预期副作用、恢复动作和其中哪些来自 Agent 自加约束；
- 剩余未知、成本观察和下一步。

只把改变方向、授权、决定、实验结果或长期资产的过程写入当前任务或研发记忆。不要用完整终端转录代替可读综合，也不要声称恢复了模型未外显的内部推理。

## 十、退出协作并返回原任务

任务完成、收益不再高于协调成本、边界无法可靠隔离或需要负责人决定时，停止新增执行者。说明当前状态、仍在运行的 Session、未确认的交付和下一步所有者，然后返回原始任务。
