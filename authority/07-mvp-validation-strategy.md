# 首个 MVP 的低成本验证策略

> 状态：本次 Session 已确认，现为当前权威。  
> 适用对象：首个 MVP“最小防漂移闭环”。  
> 核心约束：不把一次成功试运行解释成“漂移已经被消灭”。
> 当前水位：早期试运行和后续窄实施已经发生；当前证据最多支持“当前交付验收”。

## 原总图早期验证摘要（搬迁）

> 迁移来源：以下段落由 [`00-map.md`](./00-map.md) 原“当前首个 MVP 方向”按 [关联 #44（规则只加不减的收敛实施）总图索引化决定](https://github.com/Eridanus117/agent-control/issues/44#issuecomment-5258111511)原文迁入；只置换承载位置。

**共同确认**：MVP 的早期验证不追求证明“漂移已经被消灭”。验证只需以低成本检查：已知漂移模式是否更难发生、是否能更早暴露，以及发生后是否更容易恢复。验证工作应附着在真实任务上，不单独建设评测平台。

## 验证目标

早期验证只获取初步证据，判断：

1. 已知漂移模式是否更难发生；
2. 漂移或权威冲突是否能更早暴露；
3. 出现问题后是否能以更低成本恢复正确方向；
4. 控制机制本身的成本是否可能低于它减少的返工和监督成本。

## 早期验证方式与当前证据

早期计划是不单独制造大型评测项目，而把“比较最小实现方案及其 ROI”作为一次真实任务试运行。该阶段后来已经完成，并进入了窄实施与交付：版本化权威和入口、GitHub 持久合同、Orca 活跃运行面以及按需行为资产已经形成；当前实施事实分别由 [`04-collaboration.md`](./04-collaboration.md) 与 [`08-mvp-implementation-direction.md`](./08-mvp-implementation-direction.md) 承载。

这些事实只支持“当前交付验收”。它们不能证明自然任务中的长期收益、产品采用、长期依赖，也不能证明未知漂移不会发生；后续验证继续附着在范围匹配的真实任务上。

同时回放本次 Session 已经发生过的三个错误：

1. 局部任务不能压过原始诉求；
2. 普通的“同意”不能恢复已经暂停或需要重新授权的事项；
3. 未经确认的分析、推论或实验结果不能进入权威。

回放只能说明控制规则对已知错误是否有效，不能证明未知漂移不会发生。

## 观察信号

本次只观察四项：

1. 追溯性：关键行动是否能追溯到当前权威和任务目标；
2. 授权正确性：授权是否发生静默扩大、恢复或转移；
3. 可读性：负责人能否通过一份短记录理解关键行动、决定、实验、证据和未知；
4. 可恢复性：新的 Session 能否从短交接信息恢复正确目标、状态、边界和下一步。

## 早期试运行的成本上限

- 只试一个真实任务；
- 只回放三个已经发生过的错误；
- 不编写自动化；
- 不建设评测平台或仪表盘；
- 试运行过程中最多增加一个额外的人类决策点；
- 评测记录保持为一份短文档。

如果为了获得某项数据需要明显突破这些边界，应保留为未知，而不是扩大试验。

## 允许的结论

试运行结束后，只允许得出以下一种结论：

- 有初步正向证据；
- 控制成本过高，需要缩减；
- 暂无足够证据；
- 已发现失败，需要修改或放弃。

即使试运行没有发生漂移，也不能宣称“已经防止漂移”。后续真实任务出现的新错误，可以成为新的回放案例，但是否扩充验证仍需比较 ROI。

## 当前验证边界

- 不为验证而调用多个 Agent 制造样本；
- 不自动运行重复试验，也不为此建设专用评测框架；
- 不以验证名义扩大 Agent 配置、仓库、现有工作流或权限；已经由后续明确合同授权并交付的窄实施不受这条早期限制倒推否定；
- 不把当前交付验收写成样本有效、产品采用或长期依赖；
- 新的实现、自动化或产品边界仍需各自的当前合同和授权。
