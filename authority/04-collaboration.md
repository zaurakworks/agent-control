## 当前问题

单 Session 限制吞吐，直接增加模型又会产生上下文、冲突和交接问题。

## 期望结果

GPT、Claude、DeepSeek 等执行者能够分工、并行、交接和恢复，且协调成本低于收益。

## 已确认的完整产品模型

负责人要建设的不是单点的“多 Session 防冲突”，而是一种可管理的多 Agent 长程执行能力：在与人低成本对齐后，不同模型和 Session 能围绕同一个长程目标持续分工、并行、交付、审查、整合、恢复和继续推进。

完整能力至少需要同时回答：

1. **执行产能**：目标如何拆分，任务如何并行，结果如何交付、审查、合并和恢复；
2. **方向与治理**：目标、优先级、依赖、授权、决定点和验收如何被持续传递；
3. **持久可恢复性**：中断、压缩、换 Session、换模型或换主机后如何继续；
4. **实时执行与可观测性**：谁正在做什么，何时需要消息、交接、终止或人的决定；
5. **安全属性**：文件、分支、配置和共享资源如何隔离，冲突如何发现和恢复。

共享写入保护属于第 5 项，是完整协作能力的必要属性，不能单独代表协作 MVP。方案验收必须同时比较有效产能、人工对齐成本、Agent 判断税、返工、维护和恢复成本。

## 当前候选组件的地位

- **GitHub** 不只是远程备份或最终合并工具，已经作为当前持久协作主干承载目标、Issue 关系、规划、任务合同、依赖、审查、PR 和整合；这不把它决定为不可替换的永久依赖。
- **`issue-to-merge`** 是冷启动阶段安装的外部 Plugin 和历史工作流样本。当前生命周期已经由自有 `github-collaboration` 工作流承载；外部 Plugin 不再定义现在时质量门，也不因历史安装而获得长期依赖地位。
- **Orca** 已证明能在本机提供实时 Run、Task、Dispatch、消息和 Delivery，但长期依赖、Fork、自建或退出尚未决定。如果 GitHub 主干已能以较低成本完成协调，Orca 可以只是实时 Session 和本机执行适配层，也可以不进入最终方案。
- **Git worktree／分支** 是可选的文件和交付隔离机制，不承担完整协作产品。
- **Agent 行为 Skill 与系统入口** 可以约束执行方式，但不应伪装成任务状态、通信后端或强制协调器。

## 当前边界

当前已经决定并交付首个可逆工作流的职责分层与联邦式入口；详细生命周期由自有 GitHub 协作 Skill 承载。仍未决定的是永久平台、长期依赖、自动调度器、强制共享状态、固定 worktree 策略、运行环境、执行者数量或供应商组合；当前实现不能反向把这些未来取舍写成既定需求。

这次验证只回答“最小交接能否工作”，不批准自动调度、多 Session 并发或正式评测系统。

## 第一次正式 Orca 协作

负责人随后要求两个已经存在的浮动 Session 使用 Orca 协同。本次真实任务使用了 Orca Run、Task、Dispatch、持久消息和可追踪 Delivery；一个 Session 执行工作区清理，另一个 Session 负责协调、实施两个最小 Skill 并综合独立审查结果。这证明 Orca 当前的协调能力可以用于生产化任务，但一次成功不能决定长期产品依赖。

清理任务还暴露了一个合同问题：负责人的目标只是移除 Orca 侧边栏中无用的 worktree；“保留被工具连带删除的本地分支”是 Agent 自加的限制，不是用户需求。Agent 因此做了不必要的分支恢复。后续协作任务必须分别写明：

- 用户目标；
- 用户明确限制；
- 完成任务所必需且有来源的约束；
- Agent 的假设。

Agent 假设不能静默升级为交付义务，尤其不能因此增加破坏性操作或恢复工作。

## 后续最小行为实现

负责人明确要求协作行为形成 Skill，并批准、验收了后端中立的 `orchestrated-collaboration`。它只在并行或交接的预期收益高于协调成本且授权清楚时使用，要求：

1. 指定唯一协调者；
2. 划分任务、写入所有权和停止条件；
3. 对破坏性操作先核对准确目标和权限；
4. 保留可追踪的派工、交付和决定来源；
5. 由协调者独立验收并形成负责人可读的综合，不把子任务输出直接升级为决定。

最终 Skill 已进入版本化的 `agent-plugins`，并安装到普通 Codex、Orca Codex 与 Claude。它不复制任何协调产品的命令或状态，也不把 Orca 写成默认后端。当前任务选择 Orca 时，执行 Agent 动态读取 Orca 的现行协调指南；Orca TUI 是观察面，不等于编排协议，`orca orchestration` 才是执行事实与协调后端（见「运行面与协调后端的语义精确化」）。

本权威只固化该行为资产的职责、授权边界与失效条件；具体版本、提交和三端安装水位属于当前 Plugin 清单与实际安装面，不在这里形成第二份易漂移版本表。

Orca 是本机已经验证且当前成熟的可选后端。是否直接依赖、Fork 后维护、自建或更换，需要以后根据自然运行中的协调成本、故障恢复、跨供应商覆盖、锁定和退出成本作产品决定。本次实施不授权自动调度平台、长期监控或无任务收益的并发。

## 已暴露的共享工作区冲突

本次又确认了一个尚未解决的实际问题：新 Session 可以在不知道其他 Session 正在工作的情况下操作同一个工作区或同一组 Orca／Git 资源。当前的单一 `work/current.md` 和协作 Skill 能说明任务方向与行为要求，但还不能可靠公布多个同时活动的任务、写入所有权或共享资源占用。

因此，当前系统只适合一个主写入协调者，或由已建立协调关系的 Session 在明确分区后写入；不能假设任意新 Session 会自动避开正在使用的文件、worktree、分支、配置或 Orca 状态。文件隔离、共享资源独占和方向层单写入是三个不同问题，后续不能只用 Git worktree 解决全部冲突。

负责人已经把这个问题标记为“问题求解治理优化”之后的下一优先问题。当前只登记问题和优先级，不在本任务中实现注册表、锁、调度器或新的工作区结构。

## 首个完整协作 MVP 的确认

负责人于 2026-08-10 批准 GitHub Issue [`#1`](https://github.com/Eridanus117/agent-control/issues/1) 的完整方案，确认首个完整协作 MVP 采用：

**GitHub 持久协作主干 + Orca 薄运行适配 + 自有轻量工作流 Plugin。**

当前确认的职责边界：

- GitHub Issue／PR 保存长程目标、任务图、派发合同、交付、审查、整合和中断恢复依据；
- 任何已经获得明确 Issue 合同和写入所有权的 Session，都可以在该合同边界内协调父 Issue 子树或端到端交付叶子 Issue；角色不由 Provider、终端或固定“协调者／Worker”身份决定；
- Orca 只负责活跃 Session 的启动、消息、监督、Delivery 和回收，并显式链接 GitHub 任务；没有 Orca 时仍可从 GitHub 手工恢复；
- Codex／Claude Worker 在独立分支或 worktree 交付，通过 PR 接受绑定当前提交的独立审查；
- 自有 Plugin 重新实现当前需要的窄工作流，只选择性吸收 `issue-to-merge` 的有效模式，不直接 Fork 整个外部 Plugin。

首版由负责人启动或恢复任意一个带有明确 Issue 的 Session；父 Issue Session 可以在授权内维护自己的子树并派发，叶子 Issue Session 可以直接交付。局部结果、失败、成本和证据写回远端 Issue／父级后，Session 返回当前任务，不保留永久协调者身份。Actions Runner、强制锁、独立登记中心、Hook 和常驻自动调度器在第一次真实验收前不建设；普通 GitHub Actions、任务内自主并行派发、GitHub + Orca 两层状态和必要的共享资源单写者仍属于 MVP。

这项决定选择的是可逆的首个 MVP，不把 Orca 或 GitHub 确认为不可替换的永久平台。完成一次真实并行交付后，必须根据人工介入、协调成本、吞吐、返工和恢复效果复盘投入产出，再决定保留、修改、退出或升级。

## 当前交付水位

首个完整协作 MVP 已经进入实施；GitHub 持久协作主干、Orca 薄运行适配、联邦式 Issue 子树路由和自有轻量工作流已经建成并完成真实交付验收。当前证据最多支持“当前交付验收”：它证明现行入口、合同恢复、派发、交付与回收链在当前版本上可用，不证明产品采用、长期依赖或长期低成本运行。

## 联邦式 Session 入口的后续确认

负责人在 [计划／实验 `agent-control#19`](https://github.com/Eridanus117/agent-control/issues/19) 中指出：此前方案虽然分层正确，却仍默认由中央 Session 串联建图、交付和整合，把“最小可逆资产”错误泛化成产品交付策略。当前更稀缺的是负责人注意力、有用吞吐、并发启动能力和纠错闭环速度，因此本轮要交付最小完整能力，而不是只做最小差异。

当前确认的联邦式边界是：

1. 全局只统一长期诉求、重要能力、权威、产品状态和跨任务不变量；
2. GitHub Issue 是可恢复的局部目标和持久任务合同，但不能覆盖当前权威、负责人更新的明确指令或有效协作派发；
3. Session 先识别“无 Issue／父 Issue／叶子 Issue”：无 Issue 且需要续航时从未满足诉求返回问题求解，父 Issue 在授权内协调子树，叶子 Issue 端到端交付；
4. 父 Issue 与叶子 Issue 都由 `github-collaboration:issue-workflow` 维护详细状态机、风险门、合同压缩和父级回收；全局入口只负责识别模式并加载 Skill；
5. `work/current.md` 只保存短活动协调快照，纠偏、被替代判断、实验和决定理由进入可按需读取的研发记忆；
6. 纠偏只冻结依赖被推翻假设、存在共享写入冲突或会改变产品决定的路径；独立、安全、有明确合同和所有权的工作继续；
7. 没有可执行子项但父级成功条件未满足时，局部协调者补规划、报告阻塞或提出一次产品决定，不能把空队列当成完成。

这一确认替代“首版必须由一个永久中央协调 Agent 串联全部工作”的理解，但不取消每个活动协作批次中的唯一协调者、共享资源单写者和写前所有权检查。它也不授权自动调度、强制锁、Hook、Webhook、自动合并或把 Orca／GitHub 升级为长期依赖。

## 当前生命周期与质量治理路由

详细生命周期与风险门以当前 `github-collaboration` 工作流为唯一行为承载：

1. `issue-workflow` 唯一决定 Issue 子树的模式、切片、交付路由与回收；
2. 版本化资产由 `issue-delivery` 形成可核验 Draft PR，只读研究由其形成自足证据评论；
3. 实现者自审始终绑定当前 head，是否增加独立检查按 `issue-workflow` 的统一风险表决定；
4. 当前 head、审查、检查、反馈、授权和整合由 `pr-integration` 负责；交付者不审查或合并自己的 PR；
5. 父目标贡献、能力回退、证据等级与负责人可见 ROI 由 `adaptive-problem-solving` 在相应验收节点检查。

这一路由按风险运行：低风险、容易回退的普通任务保持轻量路径；权威、共享状态、长期行为或授权出现高影响变化时增加未参与实现者的只读复核。工作流的当前版本与安装差异由 Plugin 清单和运行入口按需核验，不在权威中固化端别版本表。

**守恒律置换记录（P0-4／A4）**：被替代的原文位于本文件原“当前候选组件的地位”“当前边界”和“首轮验收后的质量治理决定”，包括把 GitHub 与完整工作流继续写成候选、`issue-challenge → objective-to-issues／issue-delivery → pr-self-review → pr-review → pr-integration` 的临时组合、`github-collaboration 0.1.0` 和 `issue-to-merge` 端别限制。新结论以上述当前组件地位和生命周期路由为唯一承载；历史临时组合及安装差异保留在[关联 #2（协作 MVP 投入产出与质量治理）](https://github.com/Eridanus117/agent-control/issues/2)的远端证据与 Git 历史中，不再定义现在时行为。

## 运行面与协调后端的语义精确化

负责人于 2026-08-11 批准 D1（来源：[计划／实验 `agent-control#43` 最终综合](https://github.com/Eridanus117/agent-control/issues/43#issuecomment-5253961205)、[决定回执](https://github.com/Eridanus117/agent-control/issues/43#issuecomment-5254154780)；实施合同 [`agent-control#44`](https://github.com/Eridanus117/agent-control/issues/44)）。当前确认：

1. **Orca TUI 是观察面**：供人观察和输入，不承载协调状态，也不是编排协议；
2. **`orca orchestration` 是执行事实与协调后端**：Run、Task、Dispatch、持久消息和交付来源链的执行事实以它为准；
3. **执行状态从运行面派生**：需要知道“谁正在做什么”时按需读取运行面（例如 worker／dispatch 列表），不把执行状态回灌 GitHub Issue 或 Project。

这只是把本轮已经发生的事实写准：本轮全部派发都由 `orca orchestration` 完成。该精确化**不解禁任何自动化**——自动组波、自动派发、轮询、Webhook、常驻调度器和自动合并继续明确不做；也不把 Orca 升级为长期依赖，也不把运行面升格为权威或授权源。

**被替代的表述**：「Orca TUI 只承担需要时的观察和输入，不等于编排协议」，以及同义的「Orca TUI 只作为观察和输入界面」。它们只说明 TUI 不是什么，没有指明执行事实由哪个面承载，因此与“派发实际经由 `orca orchestration` 完成”长期字面冲突。现由上述三条替代。

**同步完成事实（2026-08-11）**：Skill 描述及正文已同步为“Orca TUI 是观察面，`orca orchestration` 才是执行事实与协调后端”，版本化来源与普通 Codex、Orca Codex、Claude 三端安装副本均已核验；来源见 [`agent-control#44` 交付回执](https://github.com/Eridanus117/agent-control/issues/44#issuecomment-5254855723)。本事实替代此前“旧表述仍存在于 Skill 描述、等待维护分片同步”的中间状态；具体版本由当前 Plugin 清单与安装面承载。

## 产品事实三分

负责人于 2026-08-11 批准 D2。本节固化其前半（事实语义三分）；`work/current.md` 降级为指针壳属后半，由 [`agent-control#44`](https://github.com/Eridanus117/agent-control/issues/44) 的 S2 分片实施。当前确认三类事实各有唯一承载面：

1. **意图、授权、决定、验收 = GitHub Issue／PR**：这是唯一持久合同面；任何新建或恢复的 Session 只读 GitHub 就能恢复合同；
2. **过程执行态 = Orca 运行面，不投影**：谁在跑、跑到哪、终端与派发状态只存在于运行面，不复制到 GitHub、Project 或仓内文件；
3. **跨层绑定与阶段边界回执 = GitHub 持久评论**：父子绑定、派发与交付结论、阻塞、验收和波次收口写成持久评论，不依赖聊天上下文、本地草稿或协调后端状态。

两条可检验推论：过程执行态过期不需要清理，因为它从不被复制；持久面缺失的信息不得以“协调后端里有”为理由省略。

**被替代的表述**：把 `work/current.md` 当作“唯一活动任务的目标、授权、状态、关键过程和下一步”的做法，实际让同一份文件同时承载上述三类事实，形成双写热点与开工税。该做法由本三分替代；文件的具体形态按 D2 后半降级，本节不授权在本次修改中删除或重写它。

## Orca 依赖策略

负责人于 2026-08-11 批准 D6。当前确认：

**长期不可替代依赖面枚举封顶**——产品方案只把以下五类能力语义视为需要稳定保留的 Orca 依赖；它们不是当前实际调用面的穷举，也不把某一版命令名固化为权威：

1. `dispatch:` 前缀的唯一寻址（持久文本中不使用 `term_` 前缀标识执行者）；
2. worktree 级别的文件隔离；
3. 高层 `worker-*` 生命周期的完成与资源收口：原生 `worker-stop`／`worker-abandon` 的 fence 是生命周期权限维度，`worker-release` 的 released／retained 与 residual 是资源维度；这些维度不互斥、不互相代替，且不授权自建 fence／租约；
4. decision gate 的镜像（gate 只镜像负责人决定，本身不是决定权威）；
5. 远端 placement（选择运行主机／环境）。

`linkedIssue` 不在依赖面内。它只是活 worktree 的可选、易失便捷索引，可用于 `issue:<n>` 发现或选择；它不是授权、锁、排他领取、跨 Run 持久合同或高层派发的前置条件，离线恢复仍以 GitHub 持久合同为准。

**当前实际调用面**——活跃协作可以按版本匹配的 Orca 指南使用 Run、Task、Dispatch、持久消息、Delivery、问答、worker 生命周期及其恢复回执。它们是当前后端把上述产品能力落到执行面的协议，不因被调用就各自成为新的长期锁定类别；命令、字段或生命周期语义变化时，执行者重新读取当前指南，而不是从本权威猜测接口。

**升级路径**——依赖面内出现缺陷或语义缺口时，先向 Orca 上游提交 issue；只有在上游拒绝或无法表达所需语义之后，Fork 才作为升级项进入产品决定。Orca Fork 主运行时当前不进入方案前沿：高层收口路径的当前样本为 13/13 正常；可复现的输入提交缺陷已于 2026-08-11 通过 [stablyai/orca#13821](https://github.com/stablyai/orca/issues/13821) 进入上游并在当日获得源码级分析，不能再以“上游路径从未尝试”支持 Fork。

本节收窄而不推翻「当前候选组件的地位」中关于 Orca 的表述：长期依赖、自建或退出仍未决定，但“遇到问题就考虑 Fork”不再是可选起点，Fork 只在上游路径失败后成为候选。依赖面封顶也不授权自动调度、常驻监控，或把运行面状态当作持久合同。

**守恒律置换记录（P0-4／A3）**：被替代的承载包括本文件原 `orchestrated-collaboration 0.1.1／0.1.6` 与 `github-collaboration 0.1.0` 现在时版本号；新承载只保留稳定职责，版本与安装水位交由 Plugin 清单和实际安装面。

**守恒律置换记录（P0-4／A5）**：被替代的原文是本节“只依赖以下五类 CLI 动词语义，超出即不进入方案”，其字面把长期锁定面误作实际调用面的穷举；新结论明确区分五类产品能力语义与版本匹配指南中的实际协议，五类长期依赖边界本身不变。

## Mode A／B 协调者操作模式六原则

**后续确认**：负责人于 2026-08-12 批准 172-D2 选 A（来源：[决定回执](https://github.com/Eridanus117/agent-control/issues/172#issuecomment-5269250532)；证据基础见 [验收案卷](https://github.com/Eridanus117/agent-control/issues/172#issuecomment-5269208567)），操作模式六条全部进入当前权威：

1. **A1｜Session 可丢弃**：逻辑协调者的连续性来自持久权威、运行事实和 generation／lease；推理 Session 是有预算、可退出的执行缓存。
2. **A2｜单调度权**：同一 Issue 子树、Run 或共享资源在任一时刻只有一个活动 reconcile 权；事件、周期和人工唤醒只是输入，不是独立调度器。
3. **A3｜事件优先、周期兜底**：正事件即时触发；周期只核对负事实、超时和漏事件，不能续命战略 Session。
4. **A4｜战术无决定权**：战术操作器可消费、投影、去重和升级，但不能扩授权、改变产品决定、跨所有权派发或成为第二真相。
5. **A5｜有界战略执行**：战略协调者每次只完成一个决定、一个波次或一个里程碑；达到预算或边界即写回结构化回执并退出。
6. **A6｜按权威作用域分片**：需要扩容时优先按 Issue 子树分片，并显式维护跨分片依赖；不能仅按终端或 Provider 数量拆分。

条款正文逐字采用 [关联 #171（长程协调者操作模式研究）Authority 候选节](https://github.com/Eridanus117/agent-control/blob/main/learning/operating-mode/coordinator-operating-mode.md)（172-D2 批准对象即该组候选）；运行机制的具体承载（D9 租约、K12 继任协议、验活纪律等）是这些条款的实现细节，由各自载体维护，不在本节复述。

**证据边界（如实标注，2026-08-12 案卷口径）**：A1–A3 已有部分自然样本（重启恢复、租约去重、信箱事件流）；A4 为单一逻辑班次样本；A5／A6 当前为实现旁证。真实易主让位、操作器交班、fresh 有界退出三个样本仍按 [#172](https://github.com/Eridanus117/agent-control/issues/172) 继任采样计划采集；条款先于完整样本入权威是负责人 172-D2 的明确选择，样本补齐前不得据此宣称产品采用或长期依赖。
