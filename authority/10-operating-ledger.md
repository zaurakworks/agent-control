## 当前问题

短期实施 Issue 关闭后，负责人仍需要看见 Agent 系统的长期诉求、未满足能力、当前投入、等待决定事项、证据和父子关系。只保存在权威、活动任务或历史记录中，会让“当前一批交付完成”被误读成“整个系统已经完成”，也会提高跨 Session 恢复和人工纠偏成本。

## 期望结果

负责人能够在一个低维护、跨仓、可追溯的观察面中看清：

- 当前有哪些目标、诉求和能力缺口；
- 哪些未满足、部分满足、正在投入或等待负责人；
- 哪些计划、实验和交付正在处理；
- 它们怎样服务上层目标，当前证据最多支持什么；
- 哪些只是待评估候选，尚未进入正式产品边界。

第一版只提供可信观察面和人工触发的 Agent 维护行为，不自动经营公司。

## 已确认的组合边界

长期可以有一个统一入口，但“建设 Agent 系统”和“使用 Agent 系统完成实际工作”必须保持清楚分区。当前 Project 只覆盖 Agent 系统建设组合；未来实际业务组合是否进入同一 Project、另一个 Project 或其他产品，需要新的证据和负责人决定。

仓库只表示资产归属，不能反向切割产品诉求。Project 可以跨 `agent-system`、迁移期间的 source 仓和未来相关仓观察事项；它不是新的仓库边界或永久平台决定。

## 总账准入

经营总账只保留三类内容：

1. 负责人已经确认的目标、诉求和重要能力；
2. 可能影响路线、投入或边界，值得继续评估的重要候选；
3. 真实存在的计划、实验、交付和维护事项。

零散想法先进入 Project 收件箱草稿，不能自动升级成正式诉求。低影响、一次性、容易重新获得或与 Agent 系统经营无关的内容可以不保存。不要把每句话、研究步骤、组件清单、Agent 数量或每个 PR 机械转换成 Issue。

## 四种正式节点

- **目标／诉求**：希望长期改变的现实结果；可以长期开放；
- **能力缺口**：当前缺少、会妨碍一个或多个诉求的能力；
- **计划／实验**：为减少关键未知或验证假设而进行的有界投入；
- **交付任务**：可独立实施、验证和关闭的工作。

每个下级节点必须能说明怎样服务上级。GitHub 原生父子关系只保留一个主要父级；横向贡献可以在正文说明，不为此建设多父知识图谱。子 Issue 完成比例只表示已列工作进度，不表示上层诉求满足，也不证明没有遗漏能力。

## 三类状态必须分开

### 执行状态

只用于计划／实验和交付任务：

```text
收件箱 → 待决定／就绪 → 进行中 → 验收中 → 完成
```

- `待决定` 表示下一步确实依赖负责人；
- Agent 内部工作或核验仍是 `进行中`；
- 证据已经形成并等待负责人接受时才进入 `验收中`；
- “等待负责人”视图同时包含 `待决定` 和 `验收中`；
- 长期目标／诉求和重要能力默认不填执行状态。

Project Workflow 可能让字段变化影响 Issue 开关状态。把条目设为 `完成` 前必须确认关闭已获授权，写入后重新读取实际 Issue 状态。

### 诉求状态

目标／诉求和能力缺口使用：`待澄清`、`未满足`、`部分满足`、`当前满足`、`暂缓`、`不再需要`；计划和交付使用 `不适用`。

Agent 可以根据证据提出判断，但一级诉求、重要能力和产品边界的状态变化由负责人确认。实现完成、当前交付验收、样本有效或全部已列子项关闭，都不能自动把上层诉求标为 `当前满足`。

### 证据等级

```text
尚无实现 → 实现完成 → 当前交付验收 → 样本有效 → 产品采用 → 长期依赖
```

箭头只表示证据强度增加，不是必须逐级完成的流程。每一档需要自己的证据；前一档不自动推出后一档。`产品采用` 和 `长期依赖` 必须由负责人决定。没有适用判断的事项使用 `不适用`，未知值不得伪造。

## 三类载体的职责

- **产品政策文件**：保存负责人确认的长期产品边界、原则和不变量；不保存当前工作；
- **GitHub Issue／PR**：保存公开、自足且经明确激活的目标、合同、授权、决定和验收；带迁移标签的事项默认只作索引；
- **GitHub Project**：若后续建立公共观察面，只投影跨仓状态和视图，不成为授权源。

Project、Issue 与产品政策冲突时不能静默猜测。条目存在、状态为开放／就绪或历史上曾被批准，都不自动授权实施。

## 维护行为

当前任务只按已激活的 Issue／PR 合同写入目标、决定、交付与验收，不为同一事实再维护一份独立经营回执。只有负责人明确要求查看、整理或更新经营组合时，才执行以下步骤：

1. 恢复当前权威、授权和远端事实；
2. 分开执行状态、诉求状态和证据等级；
3. 在明确写入所有权内更新现有公开对象，写后回读远端事实；
4. 需要新父／子交付图时先提交有界 proposal，取得明确激活与对象级所有权后再直接创建；
5. 返回原任务，不自动启动下一项工作。

全局枚举只由负责人明确触发：当负责人要求查看或选择下一项工作时，Agent 可以读取公开 Issue 列表，排除未重新激活的迁移索引，用问题求解方法提出一个有界候选。没有明确激活语句时只返回 proposal，不创建 Issue、不派发、不实施。

迁移前关于“协调者自主续航”、私有经营 Project、预授权合并和自动收口的条款只作历史研究对象，不在本公共仓当前执行入口生效。若要恢复，必须建立公开、自足的方案 Issue，重新验证成本、权限和失败边界，并由负责人明确确认。

## 当前自动化边界

当前由负责人通过 TUI 启动或恢复 Agent。GitHub 是可审阅观察面，但不会主动唤醒当前 Agent Session；经营组合维护是明确请求下的直接行为，不是轮询、Webhook、Actions、Hook、调度器或常驻服务。

当前不授权自动规划、自动派发、自动启动、自动暂停或自动合并。迁移前的自主续航、条件合并预授权与谓词收口只保留在历史证据中，不能从旧决定、开放对象或状态字段恢复。

后续只观察自然任务中的维护成本、遗漏、重复对齐、状态错误和负责人纠偏。没有必要为此建设独立评测平台或精确成本遥测。
