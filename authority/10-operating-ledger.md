## 当前问题

短期实施 Issue 关闭后，负责人仍需要看见 Agent 系统的长期诉求、未满足能力、当前投入、等待决定事项、证据和父子关系。只保存在权威、活动任务或历史记录中，会让“当前一批交付完成”被误读成“整个系统已经完成”，也会提高跨 Session 恢复和人工纠偏成本。

## 期望结果

负责人能够在一个低维护、跨仓、可追溯的观察面中看清：

- 当前有哪些目标、诉求和能力缺口；
- 哪些未满足、部分满足、正在投入或等待负责人；
- 哪些计划、实验和交付正在处理；
- 它们怎样服务上层目标，当前证据最多支持什么；
- 哪些只是待评估候选，尚未进入正式产品边界。

第一版只提供可信观察面和人工触发的 Agent 维护行为，不自动经营公司。

## 已确认的组合边界

长期可以有一个统一入口，但“建设 Agent 系统”和“使用 Agent 系统完成实际工作”必须保持清楚分区。当前 Project 只覆盖 Agent 系统建设组合；未来实际业务组合是否进入同一 Project、另一个 Project 或其他产品，需要新的证据和负责人决定。

仓库只表示资产归属，不能反向切割产品诉求。Project 可以跨 `agent-control`、`agent-plugins` 和未来相关仓观察事项；它不是新的仓库边界或永久平台决定。

## 总账准入

经营总账只保留三类内容：

1. 负责人已经确认的目标、诉求和重要能力；
2. 可能影响路线、投入或边界，值得继续评估的重要候选；
3. 真实存在的计划、实验、交付和维护事项。

零散想法先进入 Project 收件箱草稿，不能自动升级成正式诉求。低影响、一次性、容易重新获得或与 Agent 系统经营无关的内容可以不保存。不要把每句话、研究步骤、组件清单、Agent 数量或每个 PR 机械转换成 Issue。

## 四种正式节点

- **目标／诉求**：希望长期改变的现实结果；可以长期开放；
- **能力缺口**：当前缺少、会妨碍一个或多个诉求的能力；
- **计划／实验**：为减少关键未知或验证假设而进行的有界投入；
- **交付任务**：可独立实施、验证和关闭的工作。

每个下级节点必须能说明怎样服务上级。GitHub 原生父子关系只保留一个主要父级；横向贡献可以在正文说明，不为此建设多父知识图谱。子 Issue 完成比例只表示已列工作进度，不表示上层诉求满足，也不证明没有遗漏能力。

## 三类状态必须分开

### 执行状态

只用于计划／实验和交付任务：

```text
收件箱 → 待决定／就绪 → 进行中 → 验收中 → 完成
```

- `待决定` 表示下一步确实依赖负责人；
- Agent 内部工作或核验仍是 `进行中`；
- 证据已经形成并等待负责人接受时才进入 `验收中`；
- “等待负责人”视图同时包含 `待决定` 和 `验收中`；
- 长期目标／诉求和重要能力默认不填执行状态。

Project Workflow 可能让字段变化影响 Issue 开关状态。把条目设为 `完成` 前必须确认关闭已获授权，写入后重新读取实际 Issue 状态。

### 诉求状态

目标／诉求和能力缺口使用：`待澄清`、`未满足`、`部分满足`、`当前满足`、`暂缓`、`不再需要`；计划和交付使用 `不适用`。

Agent 可以根据证据提出判断，但一级诉求、重要能力和产品边界的状态变化由负责人确认。实现完成、当前交付验收、样本有效或全部已列子项关闭，都不能自动把上层诉求标为 `当前满足`。

### 证据等级

```text
尚无实现 → 实现完成 → 当前交付验收 → 样本有效 → 产品采用 → 长期依赖
```

箭头只表示证据强度增加，不是必须逐级完成的流程。每一档需要自己的证据；前一档不自动推出后一档。`产品采用` 和 `长期依赖` 必须由负责人决定。没有适用判断的事项使用 `不适用`，未知值不得伪造。

## 四类载体的职责

- **权威文件**：保存负责人确认的长期产品边界、原则和不变量；
- **`work/current.md`**：恢复指针壳，只保存主线入口、各来源 observedAt 水位和未解决冲突标志，不承载目标、授权、阶段或下一步（按 D2 后半降级，见「产品事实三分」）；
- **GitHub Issue**：保存持久的目标、能力、实验或交付合同，以及主要父子关系；
- **GitHub Project**：投影跨仓全局状态和视图，是观察面，不是权威或授权源。

Project、Issue 与权威冲突时不能静默猜测。先以当前权威、当前任务和负责人最新明确决定为准，再修正观察面。条目存在、状态为就绪或负责人看见它，都不自动授权实施。

## 维护行为

Agent 系统任务出现值得跨 Session 保留的新诉求、重要候选、决定、计划／实验、交付、验收或证据变化时，加载可用的 `operating-ledger-maintenance` Skill。它负责：

1. 恢复权威、当前授权和远端事实；
2. 判断退出、进入收件箱、更新正式事项或路由到交付工作流；
3. 分开维护执行状态、诉求状态和证据等级；
4. 从远端复核关系、字段和副作用；
5. 返回原任务，不自动启动下一项工作。

需要把已对齐目标建立为父／子交付图时路由到 `objective-to-issues`；交付单个 Issue 或整合 PR 时继续使用对应 GitHub 协作 Skill。经营总账维护不能复制或替代完整交付流程。

全局枚举只由负责人触发：当负责人明确要求选择下一项工作、扩大当前并发面、增加并行投入或选择下一波次时，Agent 才读取整个经营总账的未满足／部分满足诉求和远端观察面，并用 `adaptive-problem-solving` 只形成或选择一个有界 Issue；没有会改变排序的新证据时不重复全量分析。

**244-D1 修订（2026-08-13，[关联 #244（协调者自主续航）决定回执](https://github.com/Eridanus117/agent-control/issues/244#issuecomment-5281754399)）**：在上述负责人触发之外，协调者获授权自主续航——当在跑为零且存在价值门通过的候选时，可自主读取经营总账未满足／部分满足诉求与远端观察面，形成有界 Issue、派发、核验，并按既有条件预授权执行合并与三条件谓词收口；开波与收口回执照落远端。价值门＝候选直接服务某个开放诉求的未满足成功条件且有证据支撑；同一阶段没有新证据不重复全量扫描。节流阀：自主并发面默认不超过一个波次（≤6 席）；负责人任一纠偏即回落「等待点火」模式并复盘，负责人随时可「停」；运营台观察面须实时反映在跑面。仍需负责人的类别不变：方案／产品取舍拍板、验收步、外向发布、计费／升级、用户级配置安装、权威核心修改、诉求状态升级、谓词边界外关闭。

一个已授权父 Issue 需要续航而“就绪”子集为空，只能触发当前来源链内的恢复：Agent 从当前任务合同、刚产生的证据或已经有效的来源链定位明确、开放且仍获授权的父 Issue 及其未满足成功条件，再在该来源链内形成或选择有界 Issue；这不把候选枚举源扩大到整个经营总账，也不扫描队列找活。无法定位这样的父级时退出。两条路由都不表示经营总账维护会自动规划、派发或实施，也不扩大当前授权。

## 当前自动化边界

当前由负责人通过 TUI 启动或恢复 Agent。GitHub 是可审阅观察面，但不会主动唤醒当前 Agent Session。经营总账 Skill 是条件性行为，不是轮询、Webhook、Actions、Hook、调度器或常驻服务。

是否建设事件入口只在自然使用反复证明以下条件时重新评估：遗漏或延迟造成的损失明显，事件频率足够，且预期收益高于实现、维护、误触发和平台依赖成本。按 244-D1（2026-08-13）：协调者在自主续航边界内（见「维护行为」节 244-D1 修订段）的价值门规划、派发、启动，以及既有条件预授权覆盖的合并与谓词收口，不再逐次请求负责人；自动暂停仍未授权；轮询、Webhook、Actions、常驻调度器仍未授权。

**被替代的内容**：原文「当前不授权自动规划、自动派发、自动启动、自动暂停或自动合并」——其中规划／派发／启动三项已由 244-D1 在自主续航边界内置换，合并由在先的条件合并预授权与本次边界共同覆盖，自动暂停维持未授权原状。
