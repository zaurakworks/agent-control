# Orca 注入 `CODEX_HOME` 下的 Codex 权威入口桥接：方案探索

## 输入与边界

本文件以同目录 `research.md` 为事实基线，探索方案而不实施。当前问题已从“有没有桥”收敛为：**是否把当前已观察到的 Orca 受管副本拓扑正式选为长期桥，以及怎样补齐来源、刷新、验证和失效边界，使它不依赖偶然一致。**

共同约束：

- `entrypoints/agent-system.md` 始终是版本化权威来源。
- Codex 在设置 `CODEX_HOME` 时只从该 home 的全局 `AGENTS.override.md`/`AGENTS.md` 发现入口；项目文件不能替代跨仓库全局入口。
- 当前任务不能修改宿主、配置或受跟踪文件；下述内容都是后续候选。
- 入口正文受体积守恒约束；桥接机制不应复制出第二套可独立编辑的正文。
- 普通 Windows 与当前 Orca 两条启动路径都必须可验证。

## 方案 A：正式采用 Orca 受管普通文件副本

### 核心思路

把当前事实拓扑明确为合同：仓库源投影到普通 `~/.codex/AGENTS.md`，Orca 的资源复制机制再把该普通入口维护为专用 `CODEX_HOME/AGENTS.md` 的普通文件副本；仓库 `entry_sync` 只生成和校验，不与 Orca 争夺其运行目录的写入所有权。

### 优点

- 与当前本机真实状态完全一致，不要求改 Orca 启动参数、Hooks、运行目录或文件类型。
- 当前副本有 `.orca-resource-copies/AGENTS.md.json` 来源标记，且今天的源、普通入口、Orca 入口和 staging 哈希一致。
- 保留 Orca 对运行 home 的所有权；仓库侧不成为第二写者。
- 普通文件兼容性最好，不依赖 Windows 符号链接权限，也不会把 Orca 运行目录和仓库 worktree 绑死。
- 当前 `entry_sync check --scope installed` 已能低成本暴露内容漂移。

### 风险与代价

- 当前只能从运行目录事实推断资源复制行为；没有读到 Orca 对刷新时机、原子性、失败可见性和跨版本稳定性的正式合同。
- 仓库检查能报错但不能修复，且没有证据证明每次入口变更后都会自动运行。
- `targets.json` 把 Orca home 写成固定 `%APPDATA%` 相对路径；若 Orca 改 profile 或运行目录，验证可能检查旧路径。
- 普通入口仍是中间副本；若仓库源到普通入口的安装动作漏做，Orca 可以忠实复制一个过期版本。

### 与现有架构的适配

最高。它沿用单一版本化来源、声明式 targets、只读 installed 检查和宿主受管资源，不引入新的持久语言或执行器。

### 验证影响

- 静态门：三份入口规范化内容相同；Orca 来源标记指向普通入口；当前 `CODEX_HOME` 与受检目标一致；不存在非预期 `AGENTS.override.md`。
- 动态门：在下一次真实且已授权的入口更新后观察 Orca 副本是否刷新，再用一个新 Orca 会话确认加载来源。不要为了测试而改写真正权威。
- 失败门：副本缺失、来源标记改变、路径不匹配或哈希漂移时，不声称桥仍有效；保留最后可用副本并报告阻塞。

## 方案 B：由仓库提供显式双目标安装命令

### 核心思路

扩展现有 Python `entry_sync`，在明确授权下提供安装子命令，把生成内容原子写入普通 `.codex/AGENTS.md` 和当前 Orca `CODEX_HOME/AGENTS.md`，随后回读校验并保留可恢复备份；Orca 的资源复制不再是主桥，或需要被证明不会与安装器冲突。

### 优点

- 从版本化来源到两个实际入口的动作可重复、可测试、可在一次命令中得到明确成功/失败结果。
- 可以直接解析当前 `CODEX_HOME`，不必依赖固定 Orca 路径。
- 能定义原子替换、备份、回滚、源哈希和错误码，失败语义由仓库掌握。

### 风险与代价

- 当前工具有意“不写用户目录或 `%APPDATA%`”；改变它会扩大产品边界和写权限，需要负责人决定。
- Orca 已表现为该运行目录的资源管理者；仓库安装器直接写同一文件会形成两个写者，存在覆盖顺序、时间竞态和升级兼容风险。
- 需要处理进程正在启动、文件占用、部分写入、备份生命周期和异常恢复，维护成本显著高于只读校验。
- 如果 `CODEX_HOME` 被恶意或意外指向其他目录，安装命令需要非常严格的目标确认，不能仅因环境变量存在就写入。

### 与现有架构的适配

中等。语言和声明式配置可复用，但会推翻当前 CLI 的重要安全边界，并改变共享用户配置写入所有权。

### 验证影响

需要新增原子写、目标白名单/确认、部分失败、回滚、并发写者和路径逃逸测试；还需在真实 Orca 生命周期中验证宿主不会随后覆盖安装结果。

## 方案 C：在 Orca 启动 Codex 前动态复制

### 核心思路

在 Orca 启动链中增加一个前置步骤：每次启动前，从认可的普通入口或仓库生成物复制到本次实际 `$env:CODEX_HOME/AGENTS.md`，校验成功后才启动 Codex。路径完全以本次注入值为准。

### 优点

- 天然覆盖 Orca profile、版本或便携目录变化。
- 刷新时机与 Codex “每次运行构建指令链”对齐；成功后新会话看到的副本是可解释的。
- 可以选择失败即阻止启动，避免新会话在缺失全局入口时静默运行。

### 风险与代价

- 需要修改宿主启动链，明确超出当前授权，也是对 Orca 的高耦合扩展。
- 每次启动增加 I/O 和失败点；如果来源暂时不可用，可能阻断整个 IDE 使用。
- 仍需决定来源是仓库文件还是普通 `.codex/AGENTS.md`；前者要求 Orca知道仓库位置，后者仍保留中间副本。
- 宿主升级可能重置或绕过前置步骤；必须有产品级可发现入口，而不是本机临时脚本。

### 与现有架构的适配

中低。它最适合 Orca 本身提供正式、可配置的启动资源同步钩子；若只能维护本地补丁，长期成本偏高。

### 验证影响

要覆盖成功、来源缺失、目标不可写、复制后校验失败、启动取消/继续策略、并发启动和宿主升级后的钩子存续。

## 方案 D：用符号链接或硬链接消除副本

### 核心思路

让 Orca `CODEX_HOME/AGENTS.md` 链接到普通 `.codex/AGENTS.md`，从而共享同一物理内容；可选文件符号链接或同卷硬链接。

### 优点

- 不存在内容复制后的陈旧窗口；普通入口变化可立即反映到链接目标。
- 机制概念简单，静态一致性检查成本低。

### 风险与代价

- 当前 Orca 明确使用普通文件副本并保存资源复制元数据；链接可能在宿主刷新时被替换或拒绝。
- Windows 符号链接可能受权限/开发者模式影响；硬链接只在同一卷可用，来源替换文件时可能断开同 inode 关系。
- 把两个 home 的生命周期耦合起来；普通入口删除、替换或权限变化会同时影响 Orca。
- 链接本身不能解决仓库源到普通入口的安装可靠性，也不提供新会话加载证据。

### 与现有架构的适配

低。虽然 Orca 已对目录型 `skills`/`plugins` 使用 junction，但对 `AGENTS.md` 选择了受管普通文件，这一差异是反对把目录策略类推到入口文件的直接证据。

### 验证影响

需要跨 Windows 权限模式、源文件原子替换、Orca 刷新和升级测试；验证面大于当前问题的收益。

## 显式比较

| 维度 | A：Orca 受管副本 | B：仓库双目标安装 | C：启动前复制 | D：链接 |
| --- | --- | --- | --- | --- |
| 与当前实况一致 | 高 | 中 | 低 | 低 |
| 单写者清晰度 | 高（Orca 拥有 runtime） | 低，除非先消除 Orca 写者 | 中 | 中低 |
| 动态 `CODEX_HOME` 适配 | 中低 | 高 | 高 | 中 |
| 对宿主改动 | 无/很低 | 中 | 高 | 中 |
| 刷新可解释性 | 中，待核验 | 高 | 高 | 高 |
| Windows 可移植性 | 高 | 高 | 高 | 低至中 |
| 失败可见性 | 当前为中低 | 可设计为高 | 可设计为高 | 低 |
| 实施与维护成本 | 低 | 中高 | 高 | 中高 |
| 可逆性 | 高 | 中 | 中低 | 中 |

影响选择最大的事实是：当前 Orca 已经在运行 home 中维护普通副本及来源标记，而仓库工具已把该实际路径纳入只读校验。方案 B、C、D 都必须先证明它们的额外收益足以补偿与宿主资源管理器形成竞争或耦合的成本。

## 推荐方向（供后续规划，不是权威决定）

推荐以**方案 A：Orca 受管副本**为基线，目标不是重造复制器，而是把已运行的拓扑从“偶然事实”提升为“有边界、可验证、失效会暴露的合同”：

1. 由负责人解决 `authority/00-map.md` 与其他当前权威/现状的表述冲突，明确是否采用现有受管副本。
2. 保持运行目录单写者为 Orca；仓库只维护版本化源、目标声明和只读校验。
3. 补上“当前 `CODEX_HOME` 是否就是受检目标”“来源标记是否仍指向普通入口”“何时必须重验”的观察面。
4. 用下一次真实入口更新做自然动态验证；在没有证据前，证据等级只到当前样本一致。

若出现任一翻转条件，再转向方案 C 或 B：Orca 不再生成来源标记、不能稳定刷新、运行 home 路径开始多样化且固定目标频繁失真、或宿主提供正式且可配置的启动前同步接口。方案 D 仅在 Orca 官方明确支持文件链接且能证明不会被资源管理器替换时再考虑。

## 规划前仍需回答的问题

1. 负责人是否把“支持当前固定 Orca runtime home”视为足够，还是要求覆盖任意宿主注入的 `CODEX_HOME`？两者会改变 A 与 C 的优先级。
2. Orca 资源复制是正式受支持能力，还是当前实现细节？本机标记不足以回答跨版本承诺。
3. Orca 在源更新、源缺失、目标被改和复制失败时分别怎样处理？是否有可见错误或只保留最后成功副本？
4. 普通 `.codex/AGENTS.md` 的安装动作由谁拥有、何时发生？桥接只解决第二跳，不能掩盖第一跳漂移。
5. 当前入口规范化 10,314 字节与权威上限 10,241 字节的冲突应由哪个已授权事项收敛？这不应被桥接实现顺带改写。
6. 若只允许低成本增量，是否接受“静态三方一致 + 下一次真实更新自然验证”，而不为本问题单独建设模拟平台？
