# Plan：建立三份可交接的最小资产合同

## 目标与选择

在一个独立 PR 中，只修改 `README.md`、`docs/asset-model.md`、`docs/conformance.md`，让仓库本身能够回答：

- 这个仓现在负责什么、还没有什么；
- 方法资产的各部分分别由谁负责；
- 首次试验的决定与尚未验证的结论怎样区分；
- 后续 C1 需要什么证据，失败时怎样回退。

采用 Options 的“三文件分责”方案。B1 不实现、安装或运行 `grilling`，不修改 Codex / Claude 配置。

## 写作合同

三个文件共同遵守：

1. 每份文件先用三到五句话给出人话结论，再进入表格或细节。
2. 中文主词优先；必要英文在首次出现时用括号解释，Provider 字段、路径与命令保留原文。
3. 不使用难懂的内部代号、单字母方案名或未经解释的术语。
4. 一个定义只保留一个正文位置；其他文件用相对链接引用，不复制整段内容。
5. 对结论使用四种明确状态：
   - **产品合同**：用户可见行为的稳定约束；
   - **已批准试验输入**：首次试验按此开始，但可被证据推翻；
   - **待验证**：没有运行证据，不能写成事实；
   - **失败回退**：待验证项失败后采用的可逆方向。
6. 明确写出 `grilling` 只是首个试验样本，与期待的完整“升级思考”有差距，不是最终方法或唯一方法。

## 文件一：`README.md`

### 目的

让首次进入仓库的人在一分钟内知道当前状态和阅读入口。

### 内容顺序

1. 仓库名称与一句中文定位：保存可跨 Codex / Claude 恢复的方法 Plugin 资产及其来源、验证和回滚边界。
2. **当前状态**：现在只有 B1 合同，没有可安装 Plugin；`grilling` 将在后续 C1 作为首个样本验证。
3. **这个仓负责 / 不负责**：用短列表区分资产分发与产品合同、知识库、用户配置。
4. **从哪里开始读**：
   - 链接 `docs/asset-model.md`；
   - 链接 `docs/conformance.md`；
   - 链接外部方法介入合同与父 Issue #1。
5. **当前交付顺序**：一句话说明 `B1 → C1 → D1`，不复制父事项完整 Plan。

### 禁止写入

- 尚不存在的安装命令、版本、目录或兼容承诺；
- 旧 Marketplace / Orrery 架构；
- 把 `grilling` 写成完整“升级思考”或已证明有效。

## 文件二：`docs/asset-model.md`

### 目的

给资产 ownership 一个唯一、可审查的正文位置。

### 内容顺序

1. **人话结论**：共同方法正文只保存一次；Provider 的真实差异分开保存；缓存和配置不是权威来源。
2. **适用范围**：当前以 `grilling` 为首个样本，但模型面向未来方法资产。
3. **责任表**：按以下对象列出“负责什么 / 不负责什么”：
   - 产品合同；
   - 共同 Skill；
   - Provider 元数据；
   - Plugin manifest（清单文件）；
   - Marketplace（发现与安装目录）；
   - 来源记录；
   - conformance（符合性证据）；
   - 安装缓存与用户配置；
   - GitHub Issue。
4. **调用与同意的区别**：
   - 已批准试验输入：允许 Agent 自动调用 / 加载；
   - 产品合同：未经用户直接请求或明确接受，不能开始问询；
   - 手动命令入口保留；
   - Provider 开关只控制加载能力，不代表用户同意。
5. **当前物理候选**：展示 `plugins/grilling/` 候选树，但标题和邻近文字必须标记“待 C1 验证”，不得称为最终目录。
6. **已确定 / 待验证 / 失败回退表**：
   - 已确定：共同正文一次、Provider 差异显式、包自包含、来源和许可随包；
   - 待验证：双 manifest 同根、frontmatter 兼容、Marketplace 投影、调用守卫；
   - 回退：生成两个自包含包、分离 Marketplace、逐 Provider 收紧为命令入口。
7. **何时升级资产模型**：只有第二个真实资产、稳定重复或路径维护数据证明需要时，才比较生成器、双包全文或整仓 Fork。

### 边界

- 不复制产品合同全文，只链接并提取对资产的影响。
- 不记录实验结果或运行日志；它们属于后续证据。
- 不把 GitHub 中“保存了”写成“已经可信”；可信性由对应证据门槛决定。

## 文件三：`docs/conformance.md`

### 目的

用人话说明“符合性检查”是什么：每类证据能支持哪些结论，不能支持哪些结论。

### 内容顺序

1. **人话结论**：格式正确、能够安装、行为符合合同和方法产生收益是四件不同的事。
2. **证据层级表**：
   - 来源与许可证；
   - Agent Skills 公共格式；
   - Codex 包装与安装；
   - Claude 包装与安装；
   - 生命周期（版本、缓存、卸载、回滚）；
   - 产品行为；
   - ROI 观察。

   每行同时写“需要的证据”“通过能说明什么”“不能说明什么”。
3. **C1 最小行为场景**：
   - 用户直接请求后进入；
   - Agent 建议、用户明确接受后进入；
   - 普通或仅仅复杂的任务不直接开始问询；
   - 用户拒绝后，同一理由不重复建议；
   - `/grilling` 与 `$grilling` 手动入口可用；
   - 进入后可以降级、换方法或退出，并保留已确认内容。
4. **自动调用的首次试验**：两端先允许模型调用，但场景结果而不是配置字段决定是否合格；误触发或守卫失败时逐 Provider 回退到命令入口。
5. **结构与安装失败回退**：
   - 双 Provider 单根失败 → 保留共同源，生成两个自包含包；
   - Marketplace 共享失败 → 保留 Provider 各自投影；
   - 隔离配置试验不可行 → 停止并请求明确、可恢复的用户配置授权。
6. **结果记录边界**：本文件定义证据要求，不保存某次执行日志；运行证据应进入对应 C1 Issue / PR 或后续获批位置。

### 禁止越权的表述

- `validate` 通过 ≠ 另一 Provider 兼容；
- 安装成功 ≠ 调用行为正确；
- 场景通过 ≠ `grilling` 有正 ROI；
- 首个样本有效 ≠ 已得到完整“升级思考”方法；
- 内容进入 GitHub ≠ 自动成为可信知识。

## 实施顺序

1. 从干净的默认分支创建 Issue #2 的独立工作分支；开始前确认没有用户未提交的相关改动。
2. 改写 `README.md`，先建立短入口和明确“当前无可安装 Plugin”。
3. 新建 `docs/asset-model.md`，固定术语、ownership、状态和候选 / 回退边界。
4. 新建 `docs/conformance.md`，引用资产模型术语并定义证据层级和 C1 场景。
5. 回读三个文件，删除重复定义、未经解释的英文词和任何把待验证项写成事实的句子。
6. 执行静态检查并记录结果；不安装 Plugin、不修改 Provider 配置。

## 验证策略

### 工作树与范围

- `git status --short`
- `git diff --name-only`
- 结果只允许 `README.md`、`docs/asset-model.md`、`docs/conformance.md`。
- `git diff --check`

### 链接与结构

- 核对所有仓内相对链接目标存在。
- 核对 README 能到达两个 docs，两个 docs 能回到 README 或相互找到所依赖的定义。
- 核对核心 ownership 表只存在于 `asset-model.md`，证据权限表只存在于 `conformance.md`。

### 语义检查

逐项回答并引用仓内位置：

1. 什么只保存一次？
2. 什么必须按 Provider 分开？
3. 自动调用与进入问询有什么区别？
4. 哪些是当前批准的试验输入，哪些仍待 C1 验证？
5. 六类以上证据各自能证明和不能证明什么？
6. 双根、Marketplace 或调用守卫失败后如何回退？
7. 为什么 `grilling` 不等于最终“升级思考”？

真实的新 Session 冷读证据在 PR 自审 / 审查阶段完成；B1 实现本身不为此建立 Agent 测试框架。

## 兼容、迁移与回滚

- B1 没有运行时、数据或配置迁移。
- 回滚是还原三个 Markdown 文件；不会触碰 Codex、Claude、Marketplace、Skill 或缓存。
- 外部产品合同仍是用户行为权威；B1 只建立本仓资产与证据边界。
- C1 若产生与 B1 候选不同的实测结果，应更新“待验证 / 结果”状态，而不是保留错误目录以维护文档稳定。

## 风险与处理

- **文档过长或难读**：人话结论在前，中文主词优先，定义单点保存，细节只写会改变 C1 的内容。
- **把当前试验固化为最终设计**：显式使用状态词；自动调用是首次试验输入，行为可靠性仍待验证。
- **把 `grilling` 等同于完整方法产品**：在 README 与资产模型中明确它只是首个样本，并把方法演进留给后续独立需求。
- **证据越权**：conformance 每层同时写能证明与不能证明的结论。
- **重新引入旧架构**：不引用旧目录、Schema、语言或 Lint；只有当前合同和父事项有权威。
- **真正验证不足**：B1 不伪造 Provider 证据；所有运行时结论明确留给 C1。

## 阻塞与开放问题

- 当前没有需要负责人再选择的 B1 结构分岔。
- 仓库没有 Markdown 工具链；B1 使用 Git 检查、链接存在性和人工语义检查，不为三个文件新增工具。
- 真正的新 Session 冷读将在 PR 自审 / 审查阶段形成证据，不在本计划阶段运行。
- C1 的 Plugin 结构、Provider 配置最终值、安装试验和 `grilling` 内容改造均不属于本 Issue。

## Definition of Done

- 只修改约定的三个 Markdown 文件。
- 新读者能从 README 找到资产与验证合同，并知道当前没有可安装 Plugin。
- `asset-model.md` 对每个对象给出明确的责任与非责任，且把共同正文、Provider 差异、首次试验、待验证和回退分开。
- `conformance.md` 对每类证据同时写出可支持与不可支持的结论，并覆盖 C1 最小行为场景。
- 文档明确：允许自动调用，但未经同意不能问询；手动命令保留；失败可逐 Provider 收紧。
- 文档明确：`grilling` 是首个样本，不等于最终“升级思考”，价值尚未证明。
- 相对链接、精确文件范围与 `git diff --check` 通过。
- 没有新增 Plugin、Skill、配置、Schema、语言、Lint、脚本或安装状态。
