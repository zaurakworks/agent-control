# Options：B1 三文件怎样最小而足够

## 输入与评价维度

本比较只使用 `research.md` 的事实。B1 的目标不是建立文档体系，而是让后续 C1 不依赖旧仓或 Issue 历史也能正确实施与验证。

评价维度：

1. **交接完整性**：新 Session 能否找到并理解边界。
2. **责任清晰度**：资产 ownership 与证据权限是否容易审查。
3. **状态诚实性**：已批准、首次试验、待验证和失败回退是否不会混淆。
4. **阅读成本**：负责人和 Agent 是否能快速找到所需信息。
5. **维护成本**：C1 变化时需要同步多少位置和判断。
6. **防过度设计**：是否避免 Schema、生成器、Lint 或文档平台。
7. **未来适应性**：`grilling` 不是最终“升级思考”时，文档是否仍可容纳其他方法。

## 方案零：只保留 Issue，不新增仓内合同

### 核心

维持当前一句 README；C1 每次从父 / 子 Issue 与本地规划附件恢复上下文。

### 优点

- 没有仓库 diff，也没有文档维护成本。
- Issue 能保存讨论时间线和方案变化。

### 风险与代价

- 新 Session 必须识别最新有效 marker，并从较长历史中区分旧结论和当前决定。
- Issue 不是安装包的一部分；跨 Host checkout 不能只读仓库恢复边界。
- 旧评论中已经存在被后续修正的“硬显式调用”方案，误读风险是实际存在的。
- C1 的首份实现会事实性决定 ownership 与证据层级，难以独立审查这些决定。

### 验证含义

只能检查 Issue 历史是否完整，无法证明仓库本身能独立交接。

## 方案一：README 导航 + 资产模型 + conformance 合同

### 核心

保留 Issue #2 的三个文件，每个文件只回答一个问题：

- `README.md`：这是哪个仓、当前有什么、从哪里开始读；
- `docs/asset-model.md`：什么对象拥有什么责任、哪些内容只保存一次、哪些只是物理候选；
- `docs/conformance.md`：每类证据能证明什么、C1 怎么测、失败怎样回退。

共同术语只在资产模型中定义；conformance 用链接引用而不复制 ownership 表。产品行为以 `agent-system-foundry` 合同为权威，本仓只记录其对资产和验证的影响。

### 优点

- 阅读路径与问题边界直接，负责人不必先读完整设计史。
- ownership 与证据权限分开，能减少“安装成功 = 方法有效”等越权结论。
- README 很短，两个合同文件也可分别保持短小。
- `grilling` 可以明确标为首个样本；未来其他方法复用模型时不必改成 `grilling` 专用架构。
- 不需要新增工具或格式。

### 风险与代价

- 三个文件可能重复术语、状态或链接。
- `asset-model.md` 若写入过多物理目录，会把 C1 未知伪装成架构。
- `conformance.md` 若收录实验日志，会随试验持续膨胀。

### 控制方式

- README 只做入口，不复制合同表。
- 每个核心定义只有一个正文位置；其他文件用相对链接。
- 已确认、首次试验、待验证、失败回退使用明确状态词。
- conformance 只定义证据要求和场景，不保存运行日志或声称结果。

### 验证含义

检查三文件范围、相对链接、术语唯一来源、状态词、证据层级和新 Session 交接。

## 方案二：一个完整设计文档 + README

### 核心

把 ownership、物理候选、调用边界、证据层级、场景和回退全部写进一个 `docs/design.md`；README 只链接它。为满足当前 Issue，可让另一个 docs 文件只做短索引。

### 优点

- 一个正文减少跨文件同步和相对链接。
- 顺序阅读能看到从问题到验证的完整叙事。
- 当前内容总量不大，单文档仍可管理。

### 风险与代价

- 资产事实、实验协议和价值判断更容易混在一起。
- 为了满足三文件范围而创建一个几乎空的索引没有独立价值。
- C1 更新验证策略时更容易顺手改动已稳定的 ownership，评审边界变差。
- 随未来方法增加，单文档可能成为新的大而全设计文档。

### 验证含义

主要检查章节完整性；较难机械确认一项结论属于资产合同还是验证合同。

## 方案三：机器可读合同 + 生成 Markdown

### 核心

用 JSON / YAML 表达对象、责任、证据层级和状态，再生成 README 与 docs。

### 优点

- 可机械检查枚举、链接、重复和状态。
- 未来多个 Plugin 可以共享验证工具。
- 文档与规则有单一结构化来源。

### 风险与代价

- 立即引入 Schema、生成语言、生成命令、产物策略和漂移检查。
- 自由文本中的产品边界、未知和回退仍难由 Schema 正确表达。
- 当前只有一个尚未实现的两文件 Skill，没有重复数据证明这种机制有收益。
- Agent 每次修改都需要判断源 / 产物同步和生成器语义，正好增加用户担心的思考成本。

### 验证含义

除了内容审查，还必须验证 Schema、生成可重复性和工作树无漂移；显著超出 B1。

## 显式比较

| 方案 | 交接完整 | 责任清晰 | 状态诚实 | 阅读成本 | 维护成本 | 防过度设计 | 未来适应 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 0 仅 Issue | 低 | 中 | 低 | 低 | 中 | 高 | 低 |
| 1 三文件分责 | 高 | 高 | 高 | 高 | 中高 | 高 | 高 |
| 2 单一设计文档 | 高 | 中 | 中 | 中 | 中 | 中 | 中 |
| 3 结构化生成 | 高 | 高 | 高 | 中 | 当前低 | 低 | 未经证明 |

当前约束最支持方案一。它不是因为文件最少，而是三个文件分别对应发现、ownership 与证据三种不同读者问题；继续合并会降低责任边界，继续结构化会增加没有证据支持的工具成本。

## 方案一中的内容边界选项

### 把调用配置写成最终答案

可直接写 Codex `true`、Claude `false / omitted`。优点是明确，缺点是 B1 会越权声称 C1 尚未验证的 Provider 行为。

### 把首次试验输入与最终结论分开

记录“首次试验允许自动调用”是已批准输入；“自动调用后能否稳定守住同意门禁”仍待 C1 验证。失败时逐 Provider 收紧为命令入口。

第二种写法能同时保存当前决定和可逆性，不把试验配置伪装为永恒合同。

## 进入 Plan 前保留的开放点

1. 三个文件应控制在多短，没有仓库原生行数门槛；应以不重复和可交接为完成条件，而不是任意字数。
2. 新 Session 交接检查是人工评审证据，不应在 B1 建设自动 Agent 测试框架。
3. 外部产品合同链接可能随分支变化；B1 可链接默认分支，但不能复制整份合同形成第二权威。
4. `grilling` 与完整“升级思考”的差距需要在 C1 / 真实任务观察后进入新切片，B1 只能明确不等同。
