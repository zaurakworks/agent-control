# Issue #4 Options：`grilling` 双运行端 Plugin

输入：同目录 `research.md`、Issue #4、父 Issue #1 与已合并资产合同。

## 评价维度

本轮用以下维度比较，不把尚未运行的体验结果伪装成 ROI：

- 共同方法正文的可编辑来源数量；
- Provider 差异是否诚实且能独立失败；
- 首次新增文件与工具机制；
- 每次更新需要做多少人工同步判断；
- 是否能在一个 PR 中形成“可合并或明确失败”的闭环；
- 安装、清理和回退能否只触碰本资产；
- Windows 原生当前版本能否验证。

## 资产布局方案

### A. 一个双 Provider Plugin 根 + 两个原生 Marketplace 投影

核心：`plugins/grilling/` 中只有一份 `skills/grilling/SKILL.md`，同时放两个薄 manifest；仓根分别放 OpenAI 与 Claude 的原生 Marketplace 文件，两者都指向同一个 Plugin 根。

可数资产：

- 1 份可编辑方法正文；
- 2 个薄 manifest；
- 2 个 Provider Marketplace 文件；
- 1 份上游说明与 1 份许可证副本；
- 0 个生成器、0 份生成正文。

优势：

- 与当前资产合同直接一致；两端只在真实差异处重复少量元数据。
- 两个 Marketplace 不依赖“Codex 兼容读取 Claude 路径”这一过渡能力。
- 若一个 Provider 失败，可以保留共同正文并只改变失败端包装。
- 当前上游闭包小，不需要先选择生成语言或产物提交策略。

风险与代价：

- 双 manifest 同根仍需实际验证；Claude `validate --strict` 或 Codex 安装可能拒绝另一端目录。
- 两个 Marketplace 的版本、名称和相对路径要做一次人工一致性检查。
- 一个包的发布版本同时代表两个 Provider；某端修复可能仍要求包整体升版。

验证含义：两个原生 Marketplace、两个 manifest、同一 Skill 的哈希与两个缓存结果都必须分别核对。

### B. 一份 canonical source + 生成两个自包含 Provider 包

核心：仓内保留一个方法源，再由生成步骤产出 Codex 包与 Claude 包；每个包只有自己的 manifest、Marketplace 语义和一份生成后的 Skill。

可数资产：

- 1 份可编辑方法源；
- 2 份派生 Skill 副本；
- 2 个 Provider 包与 2 个 Marketplace 文件；
- 至少 1 个生成器、1 个防漂移检查和 1 个产物提交策略。

优势：

- Provider 校验面完全隔离；另一端的目录或字段不会进入当前包。
- 两端可独立发布、回滚和升版。
- 当 Provider 差异扩大时，包内结构更容易解释。

风险与代价：

- 首个两文件 Skill 就引入“源 → 产物”的新层；需要选择实现语言、换行 / 编码规则、产物是否提交和如何验证未手改。
- 每次改正文都会产生两份派生 diff；审查者要区分源变更与机械产物。
- 当前没有第二个资产或双根失败证据，新增机制的收益尚未实测。

验证含义：除两个 Provider 测试外，还要证明两个产物来自同一源且没有漂移。

### C. 两个 Provider 包各自维护完整正文

核心：Codex 与 Claude 各有完整 Plugin 目录和手写 `SKILL.md`。

可数资产：2 份可编辑方法正文、2 个包、2 个 Marketplace、0 个生成器，但每次语义变更至少有 2 个独立人工判断点。

优势：每个包直观、自包含、可独立发布；不需要生成工具。

风险与代价：同意、拒绝、退出等产品语义从第一天就可能漂移；“两个文件看起来相同”不能消除持续同步判断。它直接违反已批准的单一正文资产决定。

验证含义：即使当前字节相同，也要长期增加跨包语义比对。

### D. 保持上游或 Provider 原生旁加载，不建设本仓 Plugin

核心：Claude 用 `--plugin-dir` 或原生 Skill，Codex 直接安装上游 / Skill；本仓只保存说明或固定引用。

优势：首次文件最少，能最快看到上游原行为。

风险与代价：上游正文不满足本地产品合同；Codex 没有等价的未安装旁加载入口；跨 Host 恢复仍依赖外部当前状态与本机配置。本方案不能交付 Issue #4 的来源、派生与生命周期目标。

### E. 一个共享 `.claude-plugin/marketplace.json`

核心：利用 Codex 对 legacy Claude Marketplace 路径的兼容读取，让两端共用同一个目录文件。

优势：少维护 1 个很短的 JSON 文件。

风险与代价：两端主路径、必填政策字段、source 形状和严格校验不同；节省的是少量静态文本，新增的是每次 Schema 更新都要判断交集的持续成本。兼容读取位置也可能被误写成共享 Schema 保证。

这不是独立包方案，而是方案 A 的 Marketplace 子变体；它的收益不足以抵消耦合。

## 调用策略方案

### I. 两端首次都允许模型调用，Skill 内守住同意边界

- Codex 明确 `policy.allow_implicit_invocation: true`；Claude 不设置 `disable-model-invocation: true`。
- Skill 被加载不等于立刻开始问询：直接请求或明确接受建议才进入；否则最多给一次带普通出口的建议并等待。
- 两端都保留真实的手动命名空间入口。

优势：能验证用户已经自然语言同意后是否无需再输入命令；符合已批准的首次试验输入。

风险：行为门禁由模型执行，必须用新会话覆盖误触发、拒绝与重复建议；格式和配置通过不能证明守界。

### II. 两端都锁成手动命令

优势：调用边界最确定，描述不进入模型可选择上下文，误触发面小。

风险：用户已经直接请求或接受建议后仍可能多做一步；Claude Plugin 的真实命令至少是 `/plugin:skill`。它把失败回退提前变成共同默认，没有使用本轮实验收集证据。

### III. 先允许两端模型调用，失败端单独锁命令

这是 I 的渐进结果：首测配置与 I 相同，但裁决按 Provider 独立。某端未经同意问询、不能稳定抑制拒绝或接受后仍要求第二次命令，该端才切换到显式入口；另一端不因无关失败被同步收紧。

代价是最终可能形成两套调用政策；收益是差异由实际行为而不是预判产生。

## 运行验证与认证边界方案

### V1. 独立根验证生命周期，认证行为测试分层

- 两端的 Marketplace、安装、缓存、移除和清理先在空的独立配置根中完成，不需要登录。
- Claude 行为先使用会话级 `--plugin-dir`；它不安装 Plugin，但仍需记录正常认证配置中其他规则可能产生的干扰。
- Codex 先完成独立根的无认证生命周期验证。若仍找不到“保留认证但隔离 Plugin”的入口，就在修改真实 Codex 配置前停下，请求一次临时安装授权；获准后必须先快照相关 Plugin 状态，并在同一切片恢复。

优势：把无须授权的证据尽量提前，真实配置写入成为明确而晚出现的门禁。

风险：Claude 旁加载行为和 Marketplace 安装身份不是同一条证据；Codex 可能在中途等待人类授权。

### V2. 从一开始就在真实用户配置中安装和测试

优势：最接近最终使用状态，认证可用，命令短。

风险：会修改已有 Marketplace、Plugin 配置和缓存；并发会话可能读取中间版本；清理遗漏会污染后续结果。本次规划批准不包含该权限。

### V3. 只做静态与安装检查，把行为留给后续 PR

优势：本 PR 较快完成，避免模型调用成本。

风险：默认分支会先得到一个不知道是否遵守同意合同的自动调用 Skill；行为失败将变成下一 PR 的前置事实。它削弱了“一个 PR 一个可合并结论”。

## 首次版本的回退语义

### R1. 把“回退”定义为恢复测试前状态

首个正式版本没有旧正式版本。可观察状态是：测试前不存在本 Marketplace / `grilling`；测试后安装固定版本；清理后 Marketplace、启用记录、缓存与其他 Plugin 回到事前快照。相同固定版本还要能再次安装，证明来源可恢复。

它证明首次引入可撤销、可重建，但不声称证明了“从 v0.2 降回 v0.1”。后者只有第二个发布版本出现后才适用。

### R2. 人为制造一个 v0.0 再升级和降级

优势：可以演示版本切换命令与缓存行为。

风险：v0.0 不是曾经交付的产品版本；若使用未改造上游，它还不满足行为合同。测试会混合“版本机制”与“不可用旧产品”，容易产生过强结论。

## 当前领先组合与成立条件

`A + III + V1 + R1` 最符合已批准输入：一个 Plugin 根、一份正文、两个原生 Marketplace、两端先允许模型调用、失败端单独回退、生命周期优先在独立根验证、首次版本只声称恢复事前状态。

这个领先结论依赖以下可推翻条件：

- 任一 Provider 严格校验或真实安装拒绝双 manifest 同根；
- 相同 Plugin 根在两端缓存中丢失共同文件、许可证或来源说明；
- Codex 真实行为测试没有安全授权路径；
- Skill 的同意守卫在任一端不稳定。

前两项成立时，方案 B 是结构回退；第三项触发人类授权门禁而不是静默扩大权限；第四项只把失败端切换到显式命令。

## 进入 Plan 前仍需具体化

- 两个 Provider manifest 与 Marketplace 的最小字段集合和共同版本号。
- `SKILL.md` 中哪些上游语义保留、替换或新增，怎样逐项写进 `UPSTREAM.md`。
- 独立根生命周期命令、前后状态快照和允许删除的精确路径。
- Claude 旁加载行为与安装后行为怎样分开记录。
- Codex 临时真实安装授权出现在哪个停止点，授权后怎样保证只触碰新增 Marketplace / Plugin。
- Issue / PR 中的行为结果表怎样让人直接读懂，不使用“臂”等实验术语。
