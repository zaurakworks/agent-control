# Options：`grilling` 的跨 Provider 资产模型

## 输入与边界

本比较只使用 `research.md` 的事实，目标是探索如何让一个经过本地改造的 `grilling` 同时服务 Codex 与 Claude，并能从 GitHub 恢复。

当前不比较通用 Plugin 平台、其他 Skill 迁移、自动上游同步、WSL 全局迁移或知识格式。

## 共同评价维度

1. **产品合同一致性**：能否在问询前取得可观察同意，并表达普通出口、成本、拒绝抑制、降级和退出。
2. **单一语义**：是否避免两端方法正文静默分叉。
3. **Provider 诚实性**：是否如实保存 manifest、调用政策、安装和验证差异。
4. **跨 Host 恢复**：新 Host 是否能从 GitHub 固定版本恢复。
5. **首次成本**：需要新增多少目录、工具和机制。
6. **持续成本**：上游变化、Provider 变化和 Agent 判断带来的长期负担。
7. **可逆性**：试验失败时能否卸载、回滚或删除规则。
8. **第二个资产适应性**：未来真实出现第二个 Skill 时是否仍可用。当前权重最低，因为它尚未发生。

## 方案零：维持现状，按 Host 直接安装上游 Skill

### 核心

Codex 与 Claude 各自从上游或本地目录安装 `grilling`；GitHub Issue 记录所用提交，不建立本地可分发包。

### 优点

- 首次成本最低。
- 不需要本仓的 manifest、Marketplace 或构建机制。
- 删除本地目录即可回到安装前状态。

### 风险与代价

- 上游正文不满足已经合并的产品合同，无法只靠安装方式修复。
- Codex 与 Claude 的调用政策需要分别落在宿主配置；若直接选择硬命令入口，会把一次自然语言同意变成额外命令步骤并随 Host 漂移。
- 来源、许可证、本地修改和回滚依赖人工记忆或 Issue，仓库不能重建运行状态。
- 每次恢复都需要 Agent 重新判断安装路径和 Provider 差异。

### 验证含义

只能验证上游原版是否能被两个 Provider 发现，不能验证本地产品语义。

## 方案一：一个自包含双 Provider Plugin，正文只存一次

### 核心

一个安装单元同时包含：

- `skills/grilling/SKILL.md`：唯一共同方法正文；
- `skills/grilling/agents/openai.yaml`：Codex 调用政策与 UI 元数据；
- `.codex-plugin/plugin.json`：Codex 包身份；
- `.claude-plugin/plugin.json`：Claude 包身份；
- 包内许可证、来源提交和本地修改说明；
- Provider 各自需要的 Marketplace 入口。

安装包本身就是共同正文的权威，不再额外建立一个“canonical 源目录”再复制进去。两个 Provider manifest 手写并保持很薄。

### 优点

- 运行时正文只有一份，最直接消除语义漂移。
- 两个 Provider 的差异仍有明确位置，不需要假装 manifest 相同。
- 单个目录自包含，符合两端缓存复制和根目录边界。
- Git 固定提交即可恢复全部内容；回滚是回到旧包版本。
- 对只有一个 Skill、两个很薄 manifest 的当前样例，生成器不会先于问题出现。

### 风险与代价

- `SKILL.md` 中的 Claude 扩展字段需要确认 Codex 会安全忽略。
- 同仓同时出现两种 Marketplace 文件时，Codex 也会读取 legacy Claude 路径；重复发现、优先级与 Schema 兼容需要实测。
- 两个手写 manifest 仍可能发生元数据差异，只是差异面很小。
- 一个目录能否由当前两端原生安装、卸载和版本识别，需要真实验证。

### 验证含义

- 公共 Skill 格式校验。
- 两个 manifest 的字段与路径检查。
- Codex / Claude 分别安装、列出、进入、拒绝、卸载和回滚。
- 行为用五类场景区分：用户直接请求时进入；Agent 建议且用户接受后进入；只有复杂度或关键词时不进入；用户拒绝后不重复建议；命令始终可作可靠回退入口。
- 安装缓存逐文件哈希与来源包比对。

### 调用策略子选项

**A. 宿主硬性命令入口**

- Claude 设置 `disable-model-invocation: true`，Codex 设置 `allow_implicit_invocation: false`。
- 优点是边界确定、容易测试；代价是用户已经用自然语言说“同意”后，仍可能必须再输入 `/grilling` 或 `$grilling`。
- 适合作为某个 Provider 无法可靠执行同意守卫时的回退，不应在没有行为证据前成为共同默认。

**B. 同意感知的模型调用（当前优先验证）**

- 允许模型发现或加载 Skill，但共同正文规定：只有用户直接请求，或用户明确接受 Agent 的一次建议后，才能开始方法问询。
- 复杂度、关键词匹配或 Agent 认为方法有用都不构成同意；用户拒绝后按同一理由抑制再次建议。
- 命令入口继续存在，作为确定性入口和宿主判断失败时的回退。

这里的“显式”修饰用户授权，不等于必须使用显式命令。两种子选项共享同一方法正文与资产模型，C1 应以跨 Provider 场景结果裁决，不能只看配置字段。

## 方案二：仓内 canonical source，生成两个 Provider 安装包

### 核心

把共同正文、来源记录和产品规则放在独立源目录；用生成器产出 `dist/codex/...` 与 `dist/claude/...` 两套完整安装包。两个 Marketplace 只指向对应产物。

### 优点

- Provider 包可以完全独立，目录和 frontmatter 不需要依赖“另一端忽略未知字段”。
- 生成器可以机械保证公共正文、版本和来源信息一致。
- 如果以后有很多 Skill 或复杂 Provider 差异，规则可集中执行。
- Provider 安装与发布可以独立演进。

### 风险与代价

- 立即引入源 / 产物双层、生成语言、脚本、生成漂移、提交产物策略和新的验证责任。
- 安装包必须自包含，因此生成结果需要提交或发布；只保存源不足以直接安装。
- 每次小改动都要判断是否重新生成、是否提交产物、两个产物为何不同。
- 当前只有一个 1872 字节 Skill，机制规模显著大于已观察问题。

### 验证含义

- 除 Provider 验证外，还要验证生成可重复、工作树无漂移、产物来源可追溯、两个包的公共语义等价。

## 方案三：两个 Provider 包分别维护完整 Skill

### 核心

Codex 与 Claude 各有独立 Plugin 目录，每个目录都复制一份经过适配的 `grilling/SKILL.md`，不使用生成器。

### 优点

- 每个包完全服从自己的 Provider 合同，安装和 Marketplace 路径最直观。
- 一个 Provider 的变更不会机械影响另一个 Provider。
- 不需要生成工具或跨端兼容字段假设。

### 风险与代价

- 方法正文从第一天起有两份；代码审查、上游同步和行为修改都必须判断两边是否同步。
- “有意差异”和“遗漏同步”难以区分，必须新增正文等价检查或人工审查。
- Agent 在每次变更中承担更高的选择与说明成本。
- 跨 Host 能恢复文件，但不能自动证明两份语义仍一致。

### 验证含义

必须加入正文或行为等价检查，并分别运行全部场景。

## 方案四：完整 Fork `mattpocock/skills`，在 Fork 内适配

### 核心

创建或使用整个上游仓的 GitHub Fork，通过原生 Fork 关系跟踪上游，在其中修改 `grilling` 并补 Provider 包装。

### 优点

- GitHub 原生展示上游关系，获取和比较所有上游提交直接。
- 若未来大比例吸收上游 Skill，合并路径清晰。
- 不需要另行记录“从哪个仓派生”这一层关系。

### 风险与代价

- 当前只采用一个两文件 Skill，却把约 35 个 Skill 及其变更噪声纳入默认审查面。
- 上游目录和 Marketplace 结构会重新取得本仓架构影响力。
- 每月检查需要区分大量无关变化；用户和 Agent 的判断成本增加。
- 仍然没有解决本地产品合同与上游正文的差异，只改变同步工具。
- 新增 Fork 仓与当前 `agent-plugins` 的 ownership 关系需要额外管理。

### 验证含义

除 `grilling` 验证外，还需证明无关上游内容不会被打包、安装或误判为本地支持资产。

## 上游纳管方式的独立比较

资产布局之外还有来源维护方式：

### 只保存来源坐标，运行时直接取上游

- 本地文件最少。
- 无法保存满足产品合同的本地改造版本；上游删除或改写也会影响重建。

### 把获批文件复制进自有包，并记录来源与修改

- Git 提交完整拥有运行所需内容；许可证、上游 commit、blob 和修改说明可同包保存。
- 每次上游回顾需要路径级比较，但当前路径只有两个文件。

### Git subtree / submodule

- 能保留仓级来源关系。
- subtree 会引入更多上游历史或目录；submodule 的安装包不能依赖父仓外部 checkout，而且新 Host、缓存复制和离线构建多一步初始化。

### 整仓 GitHub Fork

- 上游关系最显眼。
- 对当前单一路径引入大量无关审查面；是否值得取决于未来路径级维护的实测成本。

## 当前领先候选

当前事实最支持“方案一 + 只复制获批文件并记录来源”：

- 共同正文直接位于自包含安装包中，只保存一次；
- 两个 Provider manifest 与调用政策显式但很薄；
- 产品合同固定“问询前有可观察同意”，但不提前固定为硬命令入口；优先验证同意感知的模型调用，失败的 Provider 可单独回退到硬命令入口并记录体验成本；
- Marketplace 是否一份或两份留给安装实验决定，不能从路径相似直接推出；
- 不引入生成器、第二个发布仓或整仓 Fork；
- 完整上游来源、MIT 许可证和本地修改记录与包一起版本化；
- 第二个真实资产出现后，再用实测重复量判断是否升级到生成模型。

这仍是 Options 候选，不是实施授权。

## 进入 Plan 前需保留的未知

1. 双 manifest 同根与 Claude 扩展 frontmatter 在 Codex 中的兼容性，需要成为第一实现切片的门禁，而不是 Plan 中假装已证明。
2. Codex 同时看到 `.agents/plugins/marketplace.json` 与 `.claude-plugin/marketplace.json` 的行为未被官方文档说明；不能预先承诺共享或分离方式。
3. 当前 Codex 无原生 Plugin validator，Plan 需要把“格式检查”和“真实安装检查”分开。
4. 真实方法 ROI 由后续运行切片验证；资产模型只证明可控、可恢复和可撤销。
5. 自然语言同意在两个 Provider 上是否能稳定通过、普通复杂任务是否会误触发，需要用新 Session 场景验证；配置开关本身不能代替该证据。
