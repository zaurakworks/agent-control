# 两层研发记忆 MVP 设计报告

> 状态：供负责人和主 Agent 审查的候选设计，不是当前权威、可信知识或实施授权。
> 范围：只定义“原始记录索引层”和“可读记录层”的最小文件职责、字段、读取规则与维护成本。
> 依据：`README.md`、`authority/00-map.md`、`authority/01-knowledge.md`、`authority/03-thinking-methods.md`、`authority/08-mvp-implementation-direction.md`、`work/current.md`。

## 一、要解决的问题

当前仓已经能回答“现在确认了什么”和“当前做到哪里”，但不能稳定回答：

- 当时为什么这样理解问题；
- Agent 曾经怎样偏离，负责人怎样纠正；
- 哪些方案被比较或拒绝，依据是什么；
- 做过哪些实验，实际观察到什么；
- 哪些长期资产由哪些事实和纠正产生。

研发记忆 MVP 的目的不是保存一切，也不是让历史自动指导未来，而是让负责人和后续 Agent 能够低成本复查重要工作的因果过程，并在需要时追溯原始材料。

## 二、推荐的最小目录

每个长期工作主题使用一个稳定目录：

```text
work/records/<日期>-<主题>/
├── record.md                 # 可读记录层，默认阅读入口
├── raw/
│   ├── index.md              # 原始记录索引层
│   └── ...                   # 只有需要本地保存时才放入的原始附件
└── agent-reports/
    └── ...                   # 并行 Agent 的独立报告
```

不要求每次任务都建立目录。满足下列任一条件时才值得建立：

- 工作跨 Session 或预计持续较久；
- 负责人作出会改变方向的重要纠正；
- 产生影响系统提示词、Skill、知识或权威的候选；
- 进行了以后可能需要复核的实验或外部调研；
- 多 Agent 并行，必须保留独立推演和交接依据。

## 三、原始记录索引层

### 文件职责

`raw/index.md` 不重写过程，也不解释结论。它只回答：原始材料是什么、在哪里、是否真正保存、覆盖到什么范围、怎样核对完整性。

原始材料可以包括：

- Session 或会话导出；
- 关键命令输出、实验日志和截图；
- 调研原文或难以再次取得的必要副本；
- Git 提交、差异和跨仓资产；
- 子 Agent 未经主 Agent 综合的原始报告。

### 每项最少字段

| 字段 | 含义 |
| --- | --- |
| 来源编号 | 在可读记录中引用的稳定编号，例如 `S01` |
| 材料类型与范围 | 是会话、实验、提交还是报告；覆盖哪段时间或哪项工作 |
| 定位方式 | 仓内相对路径、提交号、Session 标识或可访问位置 |
| 保存状态 | 已随 Git 保存、仅当前主机可用、外部可取、已经缺失 |
| 核对信息 | Git 提交号或内容摘要值；无法核对时明确写“未提供” |
| 限制 | 缺失区间、访问条件、可能被覆盖的内容或其他已知限制 |

“与什么结论有关”不是原始索引的必填字段，由可读记录反向引用来源编号即可，避免维护双向关系。

### 保存规则

1. 能用稳定提交、仓内文件或可恢复导出定位的，不复制第二份。
2. 只有材料难以再次取得，或复核依赖精确输入、配置、输出时，才把副本放进 `raw/`。
3. 当前无法导出完整会话时，记录 Session 标识、可用位置和缺失范围，不伪造“完整原始记录”。
4. 体积大、包含敏感内容或不适合进入 Git 的材料，只登记受限位置与保存状态；是否建立其他存储机制不由本 MVP 决定。
5. 原始材料保持原样。解释、纠错和结论写入可读记录，不静默改写原始材料。

## 四、可读记录层

### 文件职责

`record.md` 是负责人和后续 Agent 的默认阅读入口。它不是逐字转录，而是保留足以复查方向、纠偏和产物来源的因果记录；每个重要事实或事件尽量引用原始来源编号。

### 最少字段

| 区块 | 最少内容 |
| --- | --- |
| 记录身份 | 主题、起止状态、维护者、最后更新时间 |
| 原始问题 | 要解决的原始问题；不能被中途方案替代 |
| 当前授权与边界 | 当时允许做什么、明确不做什么；引用当前权威或任务 |
| 关键过程 | 按发生顺序记录改变方向或理解的事件，不记录普通工具调用 |
| 纠正 | 纠正前的理解、负责人的纠正、错误原因、纠正后如何改变工作 |
| 决定与取舍 | 决定内容、理由、被拒绝或暂缓的主要替代方案、决定状态 |
| 实验与观察 | 实际操作、可观察结果、限制；把观察与解释分开 |
| 形成的资产 | 文件、提交、Skill、系统提示词或报告的位置及其状态 |
| 未知与待办 | 尚未证实的内容、风险、需要谁决定以及恢复工作的最小入口 |
| 提炼候选 | 可能进入权威、知识、系统提示词或 Skill 的候选；明确仍需各自准入 |

### 推荐的事件写法

每个关键事件只需一个短块：

```text
事件 E03｜负责人纠正“验证是核心问题”
- 纠正前：Agent 把下一步中心放在跨 Session 验证。
- 新信息：负责人指出长期讨论未被沉淀，自我优化缺少输入材料。
- 原因诊断：现有文件偏重结论与状态，缺少研发过程的稳定承载。
- 工作变化：先定义研发记忆，再讨论下游验证。
- 来源：S02。
- 状态：负责人已确认纠正；具体载体仍是候选。
```

这种写法保存因果关系，同时避免把整段聊天重新抄写一遍。

## 五、读取规则

1. 新 Session 仍按 `README.md` 读取权威总图和 `work/current.md`，研发记忆不成为全局默认上下文。
2. 只有 `work/current.md` 或某项权威明确链接到一份记录，或当前工作需要复查其来由时，才读取对应 `record.md`。
3. 默认只读 `record.md`。出现争议、摘要缺少关键因果、高风险决定需要复核、准备修改长期资产时，才按来源编号读取 `raw/index.md` 和具体原始材料。
4. 当前权威与研发记忆冲突时，以当前权威为准；研发记忆只能说明历史过程或提出纠正候选。
5. 可读记录中的“提炼候选”不能直接影响未来任务。它必须分别通过知识、系统提示词、Skill 或权威的现有准入与授权。
6. 不默认遍历全部历史记录。先按当前任务的显式链接读取，避免历史方案重新制造漂移。
7. 负责人审查时可以从“纠正、决定、实验、资产、未知”几个区块快速阅读，需要时再追到原始材料。

## 六、维护方式与成本控制

### 谁维护

- 当前主 Agent 负责 `record.md` 的整体一致性和最终综合；
- 子 Agent 只提交独立报告和必要来源信息，不并发改写主记录；
- 负责人提供纠正或决定后，主 Agent 在继续大规模推进前记录产生的方向变化。

### 何时更新

只在以下事件更新，不按每条消息或每次工具调用更新：

- 原始问题、理解、授权或边界改变；
- 负责人作出关键纠正或决定；
- 方案被选择、拒绝或暂缓；
- 实验或证据改变下一步；
- 形成长期资产、发生重要失败、交接或结束。

并行工作开始前记录原始问题和边界；子 Agent 返回后分别保留报告；主 Agent 综合时记录采纳、拒绝与理由。这使“独立推演”和“最终决定”不会互相覆盖。

### 成本上限思路

- 一个工作主题只维护一份可读主记录，不为每个小任务建档。
- 一个重要事件写一个短块；已有报告和提交只链接，不重复总结全部内容。
- 原始层优先做索引，不默认复制大文件或逐字整理会话。
- 可读层以“足以复查和复用”为停止条件，不追求还原所有心理过程。
- 如果记录成本开始明显阻碍任务推进，优先减少普通过程记录，而不是删去纠正、决定、实验和未知。

首个样本应由 Agent 人工维护，用真实使用观察成本；当前证据不足以授权 Hook、自动转录、数据库、知识图谱或自动提炼。

## 七、这套记录不能推出什么

1. **保存不等于可信。** 原始记录和可读记录都不是知识库；未经可信门核验的内容不能作为当前事实复用。
2. **记录不等于权威。** 记录中的决定候选、用户表达和 Agent 解释，只有按权威规则确认后才改变系统方向。
3. **记录不等于授权。** 历史上允许过某项操作，不代表当前任务仍然允许。
4. **过程完整不等于方向正确。** 完整日志只能帮助发现和解释错误，不能自动防止漂移。
5. **结果相关不等于方法有效。** 某方法之后任务成功，不能单独证明成功由该方法造成，也不能自动升级成 Skill 或系统提示词。
6. **没有记录不等于没有发生。** 原始会话、工具输出或主机材料可能无法完整恢复，必须把缺失写明。
7. **可读摘要不等于原始材料。** 出现关键争议时必须追溯来源，不能让摘要反向覆盖原始内容。
8. **两层文件不推出技术平台。** 当前不需要图数据库、日志服务、工作流引擎或新的独立产品。
9. **一个样本不推出长期投入产出。** 本 Session 的回填只能检验可读性、可追溯性和维护负担，不能证明长期收益。

## 八、首个回填样本的建议范围

本 Session 适合作为第一份记录，因为它包含多次可辨认的方向漂移、负责人纠正、边界确认、实际资产创建和跨仓变更。

首个 `record.md` 不应试图逐字重建全部对话，建议只回填：

1. 原始四个目标领域和总目标怎样被确认；
2. 从“状态恢复／验证”到“研发记忆缺失”的纠正链；
3. 从长期抽象到“高层建模—最小可逆资产—真实反馈”的纠正；
4. `self-improvement` 系统提示词与 Skill 的产生过程、授权和提交；
5. 当前两层研发记忆边界、仍未知内容和下一步。

原始索引先登记实际可恢复的 Session、关键提交、现有调研文件和各 Agent 报告；无法恢复的部分明确标记缺失。这样可以在不伪造完整历史的前提下，马上形成一个可审查样本。

## 九、结论

最小可行设计不是“保存更多文档”，而是让两份文件承担不同职责：

```text
raw/index.md：证明原始材料在哪里、保存到什么程度
record.md：解释关键过程怎样导致纠正、决定和资产
```

这两层补足的是自我优化的可审查输入，不是自我优化本身。只有后续把记录中的候选按现有边界转化为系统提示词或 Skill，才会改变 Agent 的长期行为。
