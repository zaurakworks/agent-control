# 本 Session 研发回顾（草稿）

> 日期：2026-08-09
> 性质：非权威研发记录；用于负责人和后续 Agent 复查本 Session 如何形成当前方向。
> 信息范围：本次可见对话，以及 `agent-control` 当前权威与活动任务。
> 限制：本文没有、也不声称恢复 Agent 的隐藏思维链。文中的“推演”只重建对话中明确表达的理由、决定、纠正和可观察行动；会话早期若缺少结果记录，会明确标为未知。候选内容不会因为写在本文而成为权威。

## 一句话回顾

本 Session 从“是否重新吸收旧 Orrery／九仓、怎样建设知识库”开始，逐步识别出负责人真正要建设的是一个能以低对齐成本承接长程目标、由多种 Agent 协作、能够积累知识并改进自身工作方式的 Agent 系统。最大的反复不是缺少概念，而是讨论得到的纠正长期停留在上下文、摘要和局部文档中，没有及时变成可跨 Session 使用的系统提示词、Skill 或可复查研发记忆，导致 Agent 在多轮对话后重复漂移。

## 1. 原始诉求

### 1.1 最初进入本 Session 的问题

负责人最初考虑从已经脱离的 Orrery 中重新吸收有价值的部分，并询问应该拆成多少个仓。很快又明确了两个前提：

- 旧仓已经历过多次重构和九仓合并，其中的需求、知识、语言设计、代码结构、Lint 和架构判断都可能有误；
- 本次沟通应成为新的需求基准，旧仓、旧 Issue 和旧文档只能作为待核验材料，不能反向约束新系统。

因此，任务从“基于旧仓重建”改为“建立新权威，再选择性吸收旧资产”。这是后续所有工作的第一个根本转向。

### 1.2 负责人明确提出的三个核心诉求

负责人后来把希望得到的东西归纳为三个相互关联的诉求：

1. **知识**：有价值的调研和结论可以被后续任务复用；以后先读已有知识，只对变化、冲突和缺口做增量调研，避免反复进行大规模研究。
2. **多 Agent／多 Session 协同**：Codex、Claude，以及将来可能加入的其他模型和多个并行 Session，可以共同推进互不依赖的工作并完成交接。
3. **工作方式**：形成一种支持长程工作的可复用工作流；当时加载的 Plugin 和 Issue 流程只是范例，不是预设答案。

### 1.3 随对齐浮现的总目标

负责人进一步把期望形容为一个由不同模型员工组成的“公司”：人在必要时做负责人决定，系统在不需要人判断时自主推进，在风险、不确定性或决定价值较高时低成本对齐，并长期保持方向正确。还希望按资源、Token、额度和实际收益管理投入。

当前权威已经把它固化为：人能够把长程目标委托给由不同 Agent 组成的系统；系统根据风险、不确定性和决定价值，以总体低成本持续对齐，自主推进或及时请求决定，并保持方向正确、结果可验收。

### 1.4 后来被明确指出的更深诉求

负责人不只希望系统完成任务，还希望系统能够**自己优化自己的工作**。具体表现包括：

- 能识别原始问题、衍生问题和解决方案，不把负责人的表达方式或背景误当成正确答案；
- 能发现当前思考方式不够，重新界定问题，选择、组合、升级、降级或退出方法；
- 能在高层建模之后主动形成最小、可逆、可检验的现实资产，而不是长时间停留在抽象讨论；
- 能把有跨任务价值的纠正转成系统提示词或 Skill，而不是只写进当前聊天摘要；
- 能保留工作过程，让负责人和其他 Agent 事后检查做了什么、为什么这样做、哪里信息不足、哪些实验改变了方向。

## 2. 衍生诉求怎样产生

下面的关系用于解释需求来源，不表示已经决定产品或仓库结构。

```text
重复大规模调研
└─ 需要可复用知识
   ├─ 需要区分可信知识与研究材料
   ├─ 需要增量调研和失效复核
   └─ 需要公共知识与工作私域知识的不同边界

长程目标需要更多执行容量
└─ 需要多 Agent／多 Session 协同
   ├─ 需要任务拆分、交接、汇总和并发处理
   ├─ 需要跨 Host 可恢复的共享资产
   ├─ 需要处理并发提交和推送冲突
   └─ 需要核验 Windows、Orca、Claude 与可能的 WSL 环境能力

长程工作反复偏离原始问题
└─ 需要可纠偏的工作方式
   ├─ 需要权威根与唯一活动任务
   ├─ 需要元方法：管理“当前怎样理解和解决问题”
   ├─ 需要把稳定触发器放入系统提示词
   └─ 需要把条件性、可重复行为做成 Skill

负责人无法事后还原 Agent 为什么走到这里
└─ 需要研发记忆
   ├─ 原始记录用于追溯
   ├─ 可读记录用于复查和复用
   └─ 从记录中综合知识、方法、Skill 或规则候选

能力很多、建设代价可能无限扩张
└─ 需要 ROI、MVP 和渐进投入
   ├─ 获取可观测数据也要计算成本
   ├─ 先用人工和最小资产获得现实反馈
   └─ 真实问题反复出现后再自动化
```

## 3. 关键阶段、漂移与纠正

### 阶段 A：从吸收旧仓转为建立新权威

**当时方向**：调研 Orrery／九仓并考虑重新吸收。
**负责人纠正**：旧仓已被多次重构和合并，连原始需求都可能错误；不能继续假定其架构、语言、Lint、代码结构或仓库划分正确。
**方向变化**：以本次沟通为基准建立新仓和新权威；旧材料默认降级为待核验输入。
**保留影响**：当前 `authority/00-map.md` 明确禁止旧仓、旧 Issue、旧知识反向定义需求。

### 阶段 B：从仓库设计转为产品／问题建模

**当时方向**：讨论统一知识仓、分仓、工具仓、知识仓和 Plugin 仓。
**负责人纠正**：仓库是实现答案，必须先区分诉求、由何种问题衍生的诉求，以及哪些需求虽然存在但不值得纳入当前产品边界。纳入需求会增加 Agent 判断、操作和维护成本，不能因为可以做就默认做。
**方向变化**：先把知识、协同和工作方式放在同一总目标下理解，再按问题领域分别对齐；引入 ROI、MVP、暂缓和退出概念。
**后来形成的权威**：四个领域为知识、长程工作、思考模式与元方法、多 Agent／多 Session 协同；资源与运营是横向保障领域。领域划分不决定产品、仓库或组件划分。

### 阶段 C：知识不是“所有调研材料”

**当时冲突**：负责人希望高成本调研被保存，又坚持“保存就是可信”；Agent 一度把保存材料与知识准入混在一起。
**负责人纠正与共同澄清**：高成本调研应该保留，但已经发生的成本不能自动证明它值得成为长期知识；不可信内容不能以“低可信知识”的形式进入知识库。
**方向变化**：形成两道门——未来复用价值和逐条可信；原始材料、推论、失败实验进入任务证据或研发记忆，只有可信、仍适用、易理解、足以复用的结论进入当前知识。
**进一步边界**：私人电脑当前没有私域知识样本；工作电脑的私域知识可能必须保存完整内容并需要结构化和权限边界，但是否使用知识图谱仍未知。

### 阶段 D：`codex-work` 暴露的其实是跨 Host 与并发问题

**当时方向**：讨论 Codex Marketplace Skill 把工作资产保存在本地 `codex-work` 的规则。
**负责人纠正**：真正关心的是这些资产是否有长期价值、是否应该跨 Host 可见；最简单的候选是直接 GitHub 化，而不是让每次 Skill 单独判断如何保存。
**后续问题**：多个 Agent 同时提交和推送会产生并发冲突；知识库与工作资产同步成为两条相关但不同的线。
**方向变化**：开始明确知识内容、任务／研发记录、工具或 Plugin 源码各有职责；没有因此确认它们必须位于同一仓。并发策略仍未确认。

### 阶段 E：Issue／Flow 提供状态，却没有阻止方向漂移

**当时实验**：使用 Issue、`flow`、`flow-loop` 和 PR 工作流推进；负责人曾批准受限循环：合并一个 PR、把一个事项推进到 ROI 决策点，不自动实现自动化，也不关闭父事项。
**负责人观察**：批准越来越频繁，实验报告难读，术语中出现“臂”等不自然表达；更重要的是，工作持续进入细节，逐渐远离最初任务。Issue 虽然追踪了事项，却没有保持原始问题和需求链。
**方向变化**：确认“状态记忆不等于方向控制”；流程不能因为已有下一步就替 Agent 决定下一步值得做。随后从旧仓和 Issue 工作重新回到本 Session 的原始诉求。
**当前未知**：早期 PR 与 D1 的完整执行结果没有在当前权威中保留，本文不把它们视为已完成事实。

### 阶段 F：从“根据负责人背景设计”纠正为“从原始问题推导”

**Agent 漂移**：一份现状文档把负责人提到的“互联网产品背景”写成系统应采用的表达或设计依据。
**负责人纠正**：背景只是输入，不代表方法偏好，更不保证负责人正确。最重要的是原始诉求，以及为解决原始诉求而产生的能力依赖；“解决需求的需求”也要能追溯到根问题。
**方向变化**：不要求负责人只提问题、不提诉求；Agent 负责把问题、诉求、假设、方案和背景拆开，并逐步确认。由于一个文档同时包含太多内容导致多处未对齐，之后改为更慢、更细粒度地固化。

### 阶段 G：明确总目标，但对齐后的内容被裁剪过度

**对齐成果**：逐步确认长程工作、知识、思考模式和协同协作四个方面，以及“多模型员工、负责人做必要决定”的整体形态。
**Agent 漂移**：对齐完成后立即开始派发工作，且固化文档只保留了高度压缩的结论。
**负责人纠正**：对齐结束后应先把内容固化为可传递的基准；不能聊了很多轮、确认了很多次，最终文档却把关键联系裁掉。
**方向变化**：重新用多份权威文档固化四个领域和总关系，确认概念对齐本身是首个 MVP 的组成部分。

### 阶段 H：首个 MVP 聚焦“最小防漂移闭环”

**候选很多**：知识库、协作平台、方法系统、配置管理、Hooks、MCP、Plugins、资源监控都可能建设。
**共同选择**：先用版本化文件和人工运行，建立权威、活动任务、授权、证据、验收和更新候选的闭环；不先建设平台和自动化。
**负责人担忧**：专门复现漂移、证明漂移被消灭可能非常昂贵。
**方向变化**：早期验证只检查已知漂移是否更难发生、更早暴露、发生后更容易恢复，并附着在真实任务上；不单建评测平台。
**表达纠正**：不采用 ASD-STE100 或正式受控语言体系；只使用轻量中文表达规则，目标是容易理解且足以复用。

### 阶段 I：真实入口、恢复能力与运行环境

**实施／实验**：建立 `agent-control` 新仓；配置最小 Codex／Claude 入口；验证普通 Windows Codex 与 Orca 注入专用 `CODEX_HOME` 的恢复路径；建立私有 GitHub 远程并做临时克隆恢复检查；安装并验证 `grilling`。
**环境问题**：Claude 跨 Session 消息要求更高版本且不支持原生 Windows，这使 Windows 与 WSL 的选择成为潜在系统问题；Codex TUI 升级还出现过 Windows sandbox／终端问题并临时处理。
**负责人决定**：当前机器主要服务于本系统，Codex 使用 `never + danger-full-access`，Claude 使用 `bypassPermissions`，不做权限沙箱试点。
**仍未决定**：是否迁移 WSL、怎样统一 Orca／Claude／Codex 的协同运行、Claude 的跨 Session 能力如何获得，以及临时 TUI 问题的长期处理。

### 阶段 J：`grilling` 有用，但不是期待的“升级思考”

**试用结果**：`grilling` 能通过结构化提问暴露候选方案边界，知识 MVP 的“高成本调研是否进入知识”等冲突因此被发现。
**负责人纠正**：它只是边界澄清方法，不是最初期待的上位能力。
**方向变化**：转而定义“Agent 管理当前如何理解和解决问题”的能力。具体方法只能是可选工具，必须能选择、组合、升级、降级、退出，不能把一个 Skill 的固定流程当成正确工作方式。

### 阶段 K：元方法定义经历攻防和独立反证

**初始候选**：问题界定、方法编排、双循环、图结构／阶段／步骤，以及把方法挂载到研发流程节点。
**负责人要求**：不要复述负责人的图结构表达，要独立重述并尝试反证。
**反证结果**：真正得到支持的是状态可恢复、做法可纠正、权威变更仍由人决定、长期资产需独立准入；没有证据证明必须有图数据库、工作流引擎、独立上位控制器、统一方法插件接口或自动方法演化。
**方向变化**：保留“思考模式与元方法”作为独立问题领域，但不推出独立产品；其可纠偏行为可以体现在长程工作中。

### 阶段 L：用户指出，根本问题不是验证，而是讨论没有沉淀

**Agent 再次漂移**：把当前缺口说成“纠正是否能在新 Session 验证为行为改变”。
**负责人纠正**：验证不是中心。更早的问题是长期讨论、推演和纠偏没有持续沉淀，因而自我优化连可靠原料都没有。
**方向变化**：区分权威、知识、研发记忆和行为改变：

- 权威保存当前确认结论；
- 知识保存可信且值得复用的内容；
- 研发记忆保存非权威但可追溯的过程、纠正、证据和未知；
- 当前 Agent 的长期行为改变，只按系统提示词／项目指令和 Skills 两类载体考虑。

负责人确认研发记忆采用两层保存：原始记录尽量保留但默认不加载；可读记录按问题、推演、纠正、决定、实验、未知和结果整理，并可追溯原始记录。

### 阶段 M：用户再次指出，保存还没有变成自我优化

**Agent 方向**：继续讨论研发记忆边界。
**负责人纠正**：眼前的问题是，已经发生的多轮纠正没有进入系统提示词或 Skill；继续聊几轮，Agent 仍会漂移。
**方向变化与实施**：

- 在系统提示词中加入纠偏触发、重新锚定、持久记录、调用自我改进 Skill 和返回原任务的短规则；
- 创建并安装 `self-improvement` `0.1.0`，用于保存纠正、诊断断点、选择系统提示词或 Skill、判断投入产出并按授权实施；
- 同步到普通 Codex、Orca Codex 和 Claude；
- 没有同时建设 Hook、MCP、自动评测或复杂方法库。

这是本 Session 第一次把跨任务纠正直接变成可长期复用的 Agent 行为资产。

### 阶段 N：从“高维思考”纠正为“高层与现实资产往返”

**负责人解释**：最初没有直接要求做 Skill，是希望 Agent 从高维问题关系出发，自己推导合适载体，而不是等待负责人给出实现答案。
**Agent 失败模式**：把高维思考执行成持续抽象，迟迟不形成现实资产。
**新的候选工作方式**：

```text
高层建模 → 最小可逆资产 → 真实反馈 → 修正高层模型
```

负责人已批准第二个行为补丁：主动识别“概念不断增加，但关键不确定性没有减少、没有形成决定或可检验资产”的抽象循环，并把上述往返写入自我改进工作方式。该补丁正在主任务中实施，本文不替主 Agent 宣称完成。

## 4. 已形成或已验证的资产

以下只列当前权威或活动任务明确记载的结果。

| 资产／实验 | 当前结果 | 不能推出 |
| --- | --- | --- |
| `agent-control` | 新建的版本化权威与当前任务控制仓；私有 GitHub 远程可恢复 | 不是完整知识库、协作平台或最终架构 |
| 权威根与四领域文档 | 固化总目标、领域、关系和部分边界 | 不决定最终仓库数、技术栈或产品组件 |

| GitHub 临时克隆恢复 | 当前权威仓能跨 Host／新目录恢复到一致提交 | 不等于用户配置、Session、凭据和缓存都可恢复 |
| K1 可信知识包 | 负责人认为内容容易理解且足以复用 | 尚未证明自然复用成本长期低于重新调研 |
| `grilling` | 三端安装与发现通过；能辅助边界澄清 | 不是完整元方法或自动升级思考能力 |

| 权限策略 | 选择 Codex 全权限、Claude 绕过权限询问 | 不表示风险为零；环境变化后仍需重新比较 ROI |

## 5. 被拒绝、撤回或明确暂缓的方向

### 已拒绝或被纠正

- 以旧 Orrery、九仓、旧 Issue 或旧知识作为默认需求与架构权威；
- 把负责人背景、术语或早期表达直接当成正确方法；
- 因为调研昂贵就把其全部内容视为知识；
- 把保存的非权威材料命名为“低可信知识”；
- 把 Issue 中事项齐全等同于方向不会漂移；
- 让固定 Flow、Skill 或方法流程自动创造下一步工作；
- 把验证当作当前自我优化缺口的中心；
- 把完整问题领域整体塞进一个 Skill；
- 把高维思考等同于长期抽象而不做最小资产。

### 当前仅为暂缓或必要性未证

- 图数据库、工作流引擎、固定研发流水线；

“暂缓”表示当前收益证据不足或实现顺序未到，不等于永久否定。

## 7. 本 Session 暴露出的重复失败模式

1. **把实现载体当成需求**：从仓库、Issue、Flow、图或 Skill 开始，而没有先追溯它解决哪个原始问题。
2. **状态恢复替代方向控制**：文件和 Issue 能说明做到哪里，却不能判断继续做是否仍值得。
3. **摘要替代研发记忆**：保留当前结论，却丢掉纠正的原因、被拒方案和证据变化。
4. **收到纠正后只更新当前对话**：没有及时判断它是否值得修改系统提示词或 Skill。
5. **抽象层持续上升**：概念与候选越来越多，关键不确定性没有减少，也没有最小现实资产。
6. **方法反向支配问题**：因为已经加载某个 Skill 或流程，就按照它预设的步骤制造选项和批准点。
7. **一次固化内容过多**：把多个未经逐项确认的推论一起写入文档，负责人难以发现每个小偏差。
8. **过度依赖负责人持续纠偏**：负责人已经表达清楚，但 Agent 没有把理解转成稳定行为，几轮后重复出现相同问题。

## 8. 每次纠正实际改变了什么

| 负责人纠正 | 后续方向改变 |
| --- | --- |
| 旧仓和原始需求都可能错 | 新建权威仓，旧资产默认待核验 |
| 先看诉求、衍生诉求和 ROI | 从仓库设计转为问题领域与渐进投入 |
| 保存就是可信 | 将任务证据／研发记忆与当前知识分开 |
| Issue 齐全仍然漂移 | 不再把流程完整性当作方向正确性的证明 |
| 互联网背景不代表正确方法 | 从原始问题和依赖链推导，不从用户画像推导 |
| 对齐后先固化，不要裁剪过度 | 建立权威根与分领域权威，减小单次确认粒度 |
| `grilling` 不是期待的升级思考 | 定义管理理解和解法的上位能力 |
| 不要被 Skill 带着跑 | 方法与流程必须能被拒绝、跳过或退出 |
| 自己重新表达并反证 | 图、独立控制器和统一方法接口从结论降为未证候选 |
| 重点不是验证，而是讨论没沉淀 | 引入非权威、双层研发记忆概念 |
| 只有系统提示词和 Skills 能长期改行为 | 把知识／研发记忆与行为载体分开 |
| 现在仍未优化系统提示词和 Skill | 实施第一个 `self-improvement` 行为补丁 |
| 高维思考不该等负责人给实现答案 | 批准主动识别抽象循环和最小可逆资产往返 |
| 可以更快，但过程必须可复查 | 启动受限并行批次，要求独立可读报告并由主 Agent 综合 |
