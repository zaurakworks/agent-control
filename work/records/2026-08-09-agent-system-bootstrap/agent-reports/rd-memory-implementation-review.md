# 双层研发记忆实施审查

> 状态：独立只读审查报告，不是权威、知识或实施授权。
> 审查时间：2026-08-09。
> 审查对象：`authority/09-rd-memory.md`、`work/records/README.md`、本批次 `record.md`、`raw/index.md` 和 `work/current.md`。
> 审查目标：核验双层职责、资产边界、默认读取、因果可读性、来源追溯、候选状态和当前任务清晰度；不重新设计研发记忆。

## 结论

**通过，可进入负责人审查；没有阻断项。**

这组文件已经把“当前权威／当前状态／研发过程”分开：权威文件保存已确认边界，`work/current.md` 保留当前状态和下一决定，研发记录保存可回看的因果过程。保存的过程没有被描述成可信知识、权威或历史授权；知识维护与协作 Skill 仍明确是候选。

当前主要不足不是边界错误，而是部分来源只追到一份很大的活动 Session，尚不能低成本定位某一次关键纠正。它不会让当前记录失真，但会提高负责人或其他 Agent 深入核查时的成本。

## 阻断项

无。

没有发现以下会阻止交付的问题：

- 原始记录与可读记录职责颠倒；
- 历史记录覆盖当前权威；
- 未确认候选被写成已批准实施；
- 旧授权从研发记忆自动恢复；
- 新 Session 被要求默认加载全部历史；
- 来源编号没有任何落点或报告摘要值与文件不符。

## 非阻断项与最小修正

### N1｜关键会话事件缺少精确定位锚点

**现象**：E01–E12 多数使用 `[S01][S02]`。S01 能追到根 Session 文件，但根文件在观察时约 37.7 MiB、仍在增长；只凭线程和文件路径，复核者需要在大量 JSONL 中重新寻找具体纠正。S02 又只能证明文件演变，不能完整证明当时的口头理由。

**影响**：来源存在，因此不构成“无来源”；但“可追溯”目前偏向理论可追，而不是低成本可核查。最关键的 E05、E07、E10、E11、E12 正是本系统要从中学习的纠正，定位成本不应过高。

**最小修正**：不复制会话正文，也不为全部事件做精细标注。只在 `raw/index.md` 增加一个“关键事件定位”小表，为上述五个事件各保存：

- 事件编号；
- 来源编号；
- 一段足以搜索的负责人原话短语，或消息时间／JSONL 行号范围；
- 如果当前无法稳定定位，明确写“只有文件级指针”。

这能显著提高核查效率，不需要自动转录、数据库或新工具。

### N2｜活动来源和本批次资产尚未形成稳定结束快照

**现象**：S01 明确标记“仍在增长、未计算 SHA-256”；S02 与 S03 仍写本批次内容待主 Agent 提交。限制已经如实披露，因此当前没有把活动来源冒充固定快照。

**影响**：本批次提交后，索引中的“当前分支”“待提交”会成为时间点描述，后续核查者还需自己寻找首次包含这些资产的提交。

**最小修正**：完成两个仓的提交后，做一次机械收尾：

- S02 记录首次包含本批次研发记录的 `agent-control` 提交；
- S03 记录包含 `self-improvement 0.1.2` 的 `agent-plugins` 提交；
- S01 保持活动文件身份，不强求哈希；保留观察时间、当时完整行数和“仍在增长”的限制即可。

如果不值得为自引用的索引再做一次提交，可把稳定核对方式写成 `git log -- <文件路径>`，不必追求索引文件包含自己的提交号。

### N3｜来源编号目前能查找，但不便直接跳转

**现象**：`record.md` 中的 `[S01]`、`[R01]` 等是文本编号；原始索引中的 Agent 报告路径也是代码文本，而不是直接链接。

**影响**：不影响真实性或编号对应关系，但增加人工导航步骤。

**最小修正**：在 `record.md` 末尾增加 Markdown 引用定义，让 `Sxx` 跳到 `raw/index.md`，让 `Rxx` 直接跳到对应报告；不改变正文内容，也不复制来源说明。若标题锚点在不同渲染器中不稳定，所有 `Sxx` 统一链接到 `raw/index.md` 已足够。

### N4｜本审查报告加入后，独立报告清单需要一次机械更新

**现象**：审查前原始索引和 `record.md` 正确记录了六份 Agent 报告。本文件创建后将成为第七份独立报告，但按任务约束，本审查 Agent 不修改正式索引和主记录。

**影响**：若主 Agent 直接提交而不登记，本报告会存在于目录中但不在来源清单内；不影响原六份材料，却会让本批次“所有独立报告已索引”的表述过时。

**最小修正**：主 Agent 综合本审查时，把本文件登记为 `R07`，更新其大小／SHA-256，并把“六份报告”改为“七份报告”。如果主 Agent 不采纳本报告，则删除本报告或明确标为未纳入来源，而不是让它处于无状态。

## 对正式文件的最小修正顺序

建议只做以下机械收尾，不再扩展产品设计：

1. 先补 R07 清单和报告数量；
2. 为五个最关键纠正补事件级搜索锚点；
3. 两仓提交后补稳定提交定位；
4. 有余力再把来源编号改成可点击链接。

第 1 项用于保持当前清单事实正确；第 2 项最直接服务负责人的事后复查；第 3、4 项提高恢复和阅读效率。它们都不改变已确认权威，也不授权下一项 Skill 或 Orca 试用。

## 最终判断

当前实现已经完成了两层研发记忆的最小产品闭环：

```text
当前任务显式链接 → 默认读取可读因果记录
→ 有争议时按来源编号追原始索引
→ 只把通过独立准入的候选转成权威、知识或行为资产
```

剩余问题集中在追溯效率和批次收尾，不需要因此退回重新设计，也不应借机建设自动记录平台。
