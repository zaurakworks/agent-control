## 1. 原始问题与总目标

本 Session 起点是：是否从已经脱离的 Orrery／九仓吸收有价值部分，应该拆成多少个仓，以及能否建设一个让后续 Agent 先读已有成果、只做增量调研的知识库。

很快出现一个根本前提：旧仓经历过多次重构和合并，其中的原始需求、知识、语言、Lint、代码结构和架构判断都可能错误。因此，本次沟通成为新的需求基准；旧仓、旧 Issue 和旧知识只可作为待核验材料，不能定义新系统。[S01][S02]

逐步确认的总目标是：负责人能以总体较低的对齐成本，把长程目标委托给由 Codex、Claude 和未来其他模型组成的系统；系统在不需要负责人判断时自主推进，在决定价值、风险或不确定性值得时及时对齐，并保持方向正确、结果可验收。[S01][S02]

为实现总目标，当前分成四个问题领域，而不是四个预设产品：

1. 知识；
2. 长程工作；
3. 思考模式与元方法；
4. 多 Agent／多 Session 协同协作。

资源与运营是横向保障。系统提示词、Skill、仓库、Plugin、Issue、Orca 或其他工具都是可能的载体和实现，不是原始诉求。[S02]

## 2. 当前授权和边界

本批次获得的授权是：实施第二个主动防抽象循环行为补丁；建立最小双层研发记忆并回填本 Session；并行形成知识维护 Skill 和协作 Skill 的候选报告。允许加快速度和事后纠正，但要求决定、证据、Agent 报告和产物可重新阅读核查。[S01][S02]

本批次没有授权：创建正式知识维护 Skill、正式协作 Skill、自动调度器、Hook、MCP、评测平台、知识图谱、WSL 迁移，或吸收旧 `orchestration` Skill。[S02]

## 3. 关键过程与纠正

### E01｜旧仓从基础变为待核验材料

- 起点：准备调研并重新吸收 Orrery／九仓。
- 新信息：旧仓连原始需求和基础架构判断都可能错误。
- 变化：新建 `agent-control`，以本 Session 确认内容为权威；旧材料默认降权。
- 影响：后续不能因为旧 Issue 完整、代码已存在或架构看似成熟就恢复旧方向。
- 来源：[S01][S02]。

### E02｜从仓库设计退回需求与产品边界

- 起点：讨论统一知识仓、分仓、工具仓和 Plugin 仓。
- 负责人纠正：仓库是实现答案；要先说明原始诉求、由什么问题产生的衍生诉求，以及纳入某项需求会增加的判断和维护成本。
- 变化：建立总目标、四个领域、ROI／MVP／暂缓／退出的渐进投入原则。
- 遗留：最终仓库数量与职责仍未决定。
- 来源：[S01][S02][R02]。

### E03｜“高成本调研应保留”不等于“全部进入知识”

- 冲突：一方面希望昂贵调研不丢失；另一方面坚持知识中不能有不可信内容。
- 澄清：原始材料和失败实验可以进入任务证据或研发记忆；知识只保存同时通过未来价值门与逐条可信门的当前结论。
- 变化：形成“保存不等于进入知识”；当前知识仍坚持“进入即可信”。
- 影响：后续知识维护行为必须先复核、只做增量调研，再逐条准入。
- 来源：[S01][S02][R03]。

### E04｜`codex-work` 问题被重新界定为长期价值与跨 Host 恢复

- 起点：讨论 Marketplace Skill 把资产保存在本地的规则。
- 负责人纠正：关键不是每次判断存哪里，而是资产是否有长期价值、是否应跨 Host 可见；最简单候选可能是 GitHub 化。
- 新问题：多 Agent 同时提交和推送会发生并发冲突。
- 变化：知识正文、研发过程、Plugin 源码和运行工具开始按职责区分；没有因此决定它们必须同仓。
- 来源：[S01][R02]。

### E05｜Issue 和 Flow 保留状态，却没有保持方向

- 实验：用 Issue、`flow` 和 `flow-loop` 跟踪和推进工作。
- 观察：事项仍在，但 Agent 进入越来越细的工作，批准频率升高，表达变难读，原始目标被细节替代。
- 纠正：流程完整不等于方向正确；已有下一步不能证明下一步值得做。
- 变化：暂停从旧 Issue 继续推进，重新回到原始诉求和需求链。
- 来源：[S01][R02]。

### E06｜负责人背景不是设计依据

- 偏差：把负责人提到的“互联网产品背景”写成系统表达或设计偏好。
- 负责人纠正：背景只是输入，负责人也可能错误；最重要的是原始问题及为解决它产生的能力依赖。
- 变化：Agent 负责分开问题、诉求、假设、背景和方案；不要求负责人只提出问题。
- 来源：[S01][R02]。

### E07｜对齐后过度压缩，丢失关键联系

- 偏差：多轮确认后立即开始派工，固化文档只保留高度压缩的结果。
- 负责人纠正：对齐结束先固化；不能确认很多轮后又把重要联系裁掉。
- 变化：总目标和四个领域分别权威化；概念对齐本身成为首个 MVP 的组成部分。
- 后续限制：权威保存当前结论，但不能承担全部研发过程。
- 来源：[S01][S02][R02]。

### E08｜`grilling` 有用，但不是完整的“升级思考”

- 实验结果：`grilling` 能暴露一个候选中的边界冲突，例如知识准入中的隐藏矛盾。
- 负责人纠正：它主要帮助澄清边界，和期望的上位思考能力有明显差距。
- 变化：根概念改为“Agent 管理当前如何理解和解决问题的上位能力”；具体方法必须可选择、组合、升级、降级或退出。
- 来源：[S01][S02][R02]。

### E09｜图、固定阶段和统一方法接口没有得到证明

- 候选：用图结构或研发流水线把知识、资产和方法放入节点、转换或阶段。
- 负责人要求：不要复述其表达，要独立重新表达并反证。
- 反证结果：已得到支持的是状态可恢复、做法可纠正、权威变化需人决定、长期资产需独立准入；没有证据证明必须建设图数据库、工作流引擎或统一方法插件接口。
- 变化：“图”保留为表示候选，不再成为默认实现。
- 来源：[S02][R02]。

### E10｜根本缺口从“验证”纠正为“研发过程没有沉淀”

- 偏差：把下一步中心放在证明新 Session 是否避免漂移。
- 负责人纠正：更早的问题是长期讨论、推演、错误和纠正没有持续沉淀，自我优化缺少可靠材料。
- 变化：区分权威、知识、研发记忆和行为资产；确认研发记忆使用原始记录与可读记录两层。
- 影响：验证仍有价值，但不能替代保存、综合和行为修改。
- 来源：[S01][S02][R01][R02]。

### E11｜保存过程仍不等于 Agent 已经自我优化

- 偏差：继续讨论研发记忆边界，却没有改变系统提示词或 Skill。
- 负责人纠正：多轮纠正只留在上下文和文档中，几轮后 Agent 会再次漂移。
- 变化：建立首个 `self-improvement` 行为补丁；系统提示词承载常驻触发器，Skill 承载条件性、多步骤改进流程。
- 影响：知识、协作和元方法领域不整体 Skill 化，只有其中可重复行为可能成为 Skill。
- 来源：[S02][S03][R02]。

### E12｜高层思考必须和最小现实资产往返

- 负责人解释：没有早早给出 Skill 答案，是希望 Agent 从高层问题关系自主推导载体。
- 失败模式：Agent 把高层思考执行成持续增加抽象概念，并等待负责人给实现答案。
- 新工作方式：`高层建模 → 最小可逆资产 → 真实反馈 → 修正高层模型`。
- 实施：系统入口增加主动抽象循环信号；`self-improvement` 增加最小资产步骤，并要求 Agent 自己提出载体。
- 来源：[S01][S02][S03][R05]。

### E13｜独立审查发现主动入口没有真正闭环

- 初版问题：入口描述能识别抽象循环，但编号流程和 Skill 前三节仍只明确处理“负责人纠正”；Agent 可能停下来却不加载 Skill 或不产生最小资产。
- 审查结论：这是发布阻断项，不是文字偏好。
- 修正：主动信号与用户纠正合并进入同一流程；主动入口没有用户纠正时，记录原始问题、阶段停止条件、关键未知、无进展证据和暂停路径，不虚构纠正。
- 防误触：明确获准的发散探索在其停止条件内不触发。
- 结果：修正版发布为 `self-improvement` `0.1.2`，同步普通 Codex、Orca Codex 和 Claude；Claude 需重启后使用新版本。
- 来源：[S03][R05]。

### E14｜本批次不是 Orca orchestration

- 原计划表达：使用 Orca／多 Agent 协调，加快独立任务。
- 实际执行：主 Agent 使用了 Codex 原生协作工具；当前没有创建或绑定 Orca Run。
- 审计结果：不能把本批次称为 Orca orchestration。独立 Agent 报告和 Git 文件仍可复查，但没有 Orca 的 Run／Task／Dispatch 来源链。
- 处理：不为补标签重跑。以后只有在派工前创建或绑定 Orca Run，才称为 Orca 协调；否则如实标记真实后端。
- 来源：[R04]。

### E15｜知识行为从候选进入三端 Skill

- 新授权：负责人明确批准先实施最小 `knowledge-maintenance` Skill。
- 实施：把“先找当前知识、最少复核、只列变化／冲突／缺口、增量核验、逐结论通过价值门与可信门、按结果路由、自然复用时记录轻量投入产出”做成 `0.1.0`；低成本一次性事实、原始记录保存、私域结构、定时全量重查和旧仓整体导入明确不触发。
- 资产边界：Skill 承载可重复行为，不承载知识正文、研发记忆、任务状态、授权或检索工具；没有认可的当前知识入口时只形成候选和缺口，不发明知识平台。
- 独立复核：首轮审查发现“无法完成最少复核”只停止使用、却没有明确退出当前知识，是一个发布阻断；修正后三端重新安装，窄复查确认与知识权威及失效路由一致，没有剩余阻断。
- 运行结果：普通 Codex、Orca Codex 与 Claude 均已安装启用；三份安装缓存与版本化 `SKILL.md` 的 SHA-256 同为 `498A495831F69E70639AEF4B7BBD640F5B9804B68F994AA1B307BE5AA27AB219`；源码提交为 `d35ff98`。
- 发现规则纠正：当前 Codex 原生仓级清单位于 `.agents/plugins/marketplace.json`，Claude 清单位于 `.claude-plugin/marketplace.json`。共享 Plugin 正文不表示两端清单格式相同；本仓现分别维护两份清单。
- 限制：静态安装一致性不能证明自然复用收益，下一次范围匹配的真实任务才记录读取、补查和维护成本。
- 来源：[S01][S02][S03]。

### E16｜第一次正式 Orca Run 处理真实跨 Session 碰撞

- 触发：负责人报告另一个浮动 Session 已经修改共享控制文件，并要求两个 Session 通过 Orca 协同。
- 冻结与盘点：主 Session 创建 Run `run_d6bfb82e9782`，先派发只读碰撞盘点。协作 Session 确认只改动 `work/current.md`，没有提交、推送或开始删除；主 Session 接管该文件和两个受保护仓的写入。
- 有限执行：后继 Task 只允许移除已复核的 8 个完成 worktree 和 2 个空目录，保留两个开放 PR worktree，禁止远端、分支、Session、记录和源码仓改动。最终目标目录与 Orca／Git 登记符合预期。
- 中途行为：`orca worktree rm` 连带删除 5 个本地分支；协作 Session 因任务合同写了“禁止删除分支”，依据操作前保存的提交值立即重建。主 Session 随后核对全部 8 个分支、两个保留 worktree 和移除结果。
- 当前推论：Orca orchestration 适合作为跨 Session 的 Run／Task／Dispatch／消息与归属后端；Orca TUI 是人可观察和输入的界面，不是协调状态本身；Skill 应规定何时协作、如何拆分、声明所有权、预检工具语义、验收和综合，并动态读取 Orca 当前指南，不能复制一套会过时的命令。Orca 不可用时只能显式降级为无持久协调保证的方式，不能冒称等价能力。
- 限制：这是一个 Windows、两个 Codex 浮动 Session 的样本；尚未验证 Claude、跨 Host 或大量并发，也不能因任务最终完成就忽略中途误解和无必要动作。
- 来源：[S06][R04]。

### E17｜把 Agent 自加约束误当成负责人目标

- 原始问题：负责人只希望移除 Orca 侧边栏里的无用 worktree，让界面恢复整洁。
- 偏差：临时 Session 把“不删除本地或远端分支”写进共享当前任务；主 Session 接管后沿用了该约束，并把 `orca worktree rm` 删除本地分支称为事故。
- 负责人纠正：不需要重建分支；清理 worktree 才是目标。
- 原因：协作任务合同没有标明“用户目标、必要安全约束、Agent 为保守而增加的假设”三者来源，Agent 自己的方案被提升成了需求。
- 影响：已经重建的分支暂时保留，因为再次删除是新的破坏性动作且不改善侧边栏；不再追加恢复工作。正式协作 Skill 必须要求任务规格标注约束来源，并在恢复副作用前判断它是否真的破坏用户目标。
- 来源：[S01][S06]。

### E18｜协作行为进入最小正式 Skill

- 授权与选择：负责人明确协作 Skill 必须存在，并要求两个浮动 Session 走 Orca 协同；这授权了最小可逆实现，不证明 Orca 是最终唯一供应商。
- 实现边界：`orchestrated-collaboration` 负责授权与收益门、目标和约束来源、唯一协调者、写入所有权、子任务合同、破坏性操作预检、交付确认、独立验收和综合。它不提供通信、终端或进程能力。
- 后端选择：跨 Session 需要持久来源链时默认动态读取 Orca 当前 orchestration 指南；Orca TUI 只负责观察与输入；原生协作和无 Orca 路径必须如实标记，后者没有等价持久保证。
- 独立复核：没有发布阻断。审查指出“派发前确认 Dispatch 已建立”有时间顺序歧义，已改成发出派发后先确认 Dispatch 指向预期执行者再视为任务开始；完整合同对极小只读任务的成本留给自然使用观察。
- 运行结果：`0.1.0` 已安装到普通 Codex、Orca Codex 与 Claude；三份安装缓存和版本化 `SKILL.md` 的 SHA-256 同为 `FE7C746154963F9DDF697F7144EB736327E18DA120B1DF6245E88DE7A4105309`；源码提交为 `e84975c`。
- 仍未知：Claude、跨 Host、大量并发、完整所有权移交及自然触发成本没有在本轮得到证明。
- 来源：[S02][S03][S06][R04]。

### E19｜成功试用不能替代协调产品采用决策

- 偏差：第一次正式 Orca Run 成功后，主 Session 直接在 `orchestrated-collaboration` `0.1.0` 中写入“跨 Session 默认使用 Orca”，把当前实现选择升级成了长期产品方向。
- 负责人纠正：此前没有系统调研 Orca 的协调能力，只知道它存在并看过 Agent 使用；以后仍需要比较直接依赖、自己维护／Fork 和自建。负责人同时观察到 Orca 当前能力很生产化、成熟。
- 判断：成熟度和本次成功来源链是采用 Orca 的强正面证据，但没有回答长期维护责任、版本变化、跨供应商与跨 Host 覆盖、锁定、退出、故障恢复和自建机会成本。
- 变化：`0.1.1` 保留后端中立的协作合同；只有当前任务已经选择 Orca 时才动态读取 orchestration 指南。Skill 不替负责人决定长期依赖、Fork／维护、自建或更换，也不因可控诉求自动进入自建。
- 独立复查：确认不再把 Orca 写成永久默认，且授权、收益门、所有权、验收和综合没有被削弱；没有剩余发布阻断。
- 运行结果：`0.1.1` 已更新到普通 Codex、Orca Codex 与 Claude；三份安装缓存和版本化 `SKILL.md` 的 SHA-256 同为 `BED9A6A90F4F42C53666ED49A19E30356323091CBFD3F20F70A241E1D458A24C`；源码提交为 `389eda3`。Claude 需重启后应用新版本。
- 下一证据：先在自然任务中继续把 Orca 作为已选择的可用后端，记录低成本可见的协调收益、人工介入、故障和限制；只有决定价值高于调研成本时，再做一次受限产品比较。
- 来源：[S01][S03][S06]。

### E20｜关键节点检查不能代表完整元方法

- 起点：为“问题求解治理能力”提出一个 `problem-solving-checkpoint`，在对齐、假设变化、高成本行动和阶段交接等节点检查问题、漂移、方法与执行配置；负责人批准了最小实施。
- 负责人纠正：早期已经对齐过多种思考方式及其上位选择关系；当前方案把完整能力收缩成了任务内方向检查。
